# 小说库相似度比对服务：当前基础方案

## 1. 方案目标

当前基础方案的目标不是一次性做完“全量自动巡检平台”，而是先建立一个最小可行、结构正确、后续能扩展的独立服务。

短期目标：

- 能接入样本小说库
- 能接收桌面端导出的字幕结果
- 能完成候选召回
- 能输出可复核的证据片段

## 2. 基础架构建议

推荐按四层拆分：

### 2.1 数据接入层

职责：

- 接收小说库导出数据
- 保留原始字段和原始文件
- 记录导入批次

输入来源建议：

- `CSV`
- `XLSX`
- `Parquet`
- 数据库只读导出

输出：

- 原始书表
- 原始章节表
- 导入批次记录

### 2.2 标准化处理层

职责：

- 文本清洗
- 章节结构校验
- 字段映射
- 生成统一标准字段

最低标准字段建议：

- `book_id`
- `book_name`
- `author_name`
- `chapter_id`
- `chapter_index`
- `chapter_title`
- `content_clean`
- `updated_at`

清洗动作建议：

- 去广告
- 去无关声明
- 统一空白
- 统一常见标点
- 统一数字和章节序号格式
- 保留章节边界

### 2.3 检索比对层

职责：

- 建章节级或片段级索引
- 处理字幕提交
- 做候选召回
- 做精排比对
- 输出证据片段

推荐三层链路：

1. 粗召回
2. 精排比对
3. 证据输出

### 2.4 服务接口层

职责：

- 提供字幕提交接口
- 提供任务状态接口
- 提供结果查询接口
- 提供复核写回接口

## 3. 推荐的比对路线

## 3.1 第一层：粗召回

目标：

- 从全量小说库里先找出少量高可疑候选

推荐方法：

- 章节级 `BM25`
- 字符级 `2-gram / 3-gram`
- 倒排索引

当前阶段不建议直接依赖中文分词作为唯一主方案。因为字幕文本存在这些问题：

- ASR 错字
- 台词口语化
- 人名别名变化
- 轻微改写

因此粗召回优先建议使用字符级方案。

## 3.2 第二层：精排比对

目标：

- 对粗召回候选做更细的证据定位

推荐方法：

- `n-gram overlap`
- `Jaccard`
- `RapidFuzz`
- 局部序列对齐
- 最长公共子串或相似片段定位

这一层输出的不是单一分数，而是：

- 命中的候选书
- 命中的候选章节
- 命中的文本片段
- 命中的字幕时间范围
- 覆盖率和命中段数量

## 3.3 第三层：语义补召回

目标：

- 处理“意思接近，但字面改写较多”的情况

推荐做法：

- 文本 embedding 召回
- 只作为补召回

当前阶段不建议把语义相似度当成最终判定依据，因为法务和版权流程最终仍然需要落到具体文本证据。

## 4. 比对单元设计

## 4.1 小说侧切分

建议保留两种粒度：

- 章节全文
- 章节滑窗片段

滑窗建议：

- 先按 `150-300` 字测试
- 邻接窗口保留 overlap

原因：

- 章节过长时，直接全文比对噪音太大
- 太短则上下文不足

## 4.2 字幕侧切分

建议同时保留：

- 完整字幕文本
- 分段字幕
- 句群聚合片段

并保留：

- `start_ms`
- `end_ms`
- 原始文本

## 4.3 结果单元

最终结果不要只输出一个“相似度 87%”。

最少应输出：

- `task_id`
- `candidate_book_id`
- `candidate_book_name`
- `candidate_chapter_id`
- `candidate_chapter_title`
- `subtitle_start_ms`
- `subtitle_end_ms`
- `subtitle_text`
- `novel_text_hit`
- `score`
- `coverage`
- `hit_count`
- `review_status`

## 5. 推荐的最小系统实现

## 5.1 服务形态

当前建议先做单体服务，不急着一开始拆微服务。

推荐起步形态：

- 一个 API 服务
- 一个后台 worker
- 一个离线导入与建索引脚本集

## 5.2 推荐技术栈

第一阶段建议：

- Python
- FastAPI
- PostgreSQL
- OpenSearch 或 Elasticsearch
- RapidFuzz

说明：

- PostgreSQL 用于存元数据、任务、结果、复核状态
- OpenSearch/Elasticsearch 用于章节或片段级召回
- RapidFuzz 等工具用于精排和证据定位

如果前期只做样本验证，也可以先退一步：

- Python
- FastAPI
- SQLite 或 PostgreSQL
- 本地索引

但这只适合样本验证，不适合长期主方案。

## 5.3 建议的内部模块

- `service/api/`
  - 接口层
- `service/core/ingest/`
  - 数据接入
- `service/core/normalize/`
  - 清洗标准化
- `service/core/index/`
  - 建索引
- `service/core/retrieval/`
  - 粗召回
- `service/core/rerank/`
  - 精排比对
- `service/core/evidence/`
  - 证据输出
- `service/core/review/`
  - 复核状态管理

## 6. 与桌面工具的接口建议

桌面工具不参与小说库存储和索引，只提交字幕任务。

建议提交数据格式：

```json
{
  "source_type": "video_clip",
  "source_path": "E:/.../clip.mp4",
  "subtitle_text": "完整字幕文本",
  "subtitle_segments": [
    {
      "start_ms": 0,
      "end_ms": 2200,
      "text": "第一段字幕"
    }
  ],
  "metadata": {
    "platform": "douyin",
    "share_url": "",
    "series_title": "",
    "episode_number": 1
  }
}
```

建议返回结果格式：

```json
{
  "task_id": "cmp_20260421_001",
  "status": "completed",
  "top_candidates": [
    {
      "book_id": "b123",
      "book_name": "示例小说",
      "chapter_id": "c456",
      "chapter_title": "第12章",
      "score": 0.86,
      "coverage": 0.64,
      "subtitle_start_ms": 1800,
      "subtitle_end_ms": 6200,
      "subtitle_text": "字幕命中片段",
      "novel_text_hit": "小说命中文本"
    }
  ]
}
```

## 7. 建议的阶段推进

## 7.1 阶段一：样本验证

规模建议：

- `500-2000` 本小说

目标：

- 跑通导入
- 跑通清洗
- 跑通索引
- 跑通召回
- 跑通证据输出

## 7.2 阶段二：全量接入

目标：

- 接入 10 多万本小说
- 支持增量同步
- 支持批量字幕比对

## 7.3 阶段三：法务整合

目标：

- 和桌面工具联调
- 支持字幕一键提交
- 支持候选书单输出
- 支持法务复核状态回写

## 8. 当前最关键的待确认项

正式开发前，必须先确认：

1. 小说库目前由哪个系统管理
2. 能否提供稳定的 `book_id` 和 `chapter_id`
3. 交付的是整本还是章节级数据
4. 是否能给到 `book + chapter + content`
5. 数据是一次性全量，还是后续要增量同步
6. 数据访问限制和权限边界是什么

## 9. 当前基础结论

当前最稳妥的基础方案是：

- 独立工作区
- 独立服务
- 先样本验证
- 先做字符级召回和证据级精排
- 桌面工具只做上游字幕生产和结果展示

这个方案足够清晰，也能支撑后续继续演进为正式法务检索服务。
