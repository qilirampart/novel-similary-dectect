# 短剧字幕匹配 Phase 3：候选聚合结果

## 已完成内容

在已完成的字幕窗口词法索引之上，新增 `scripts/search_drama_subtitle_candidates_v1.py`。

该脚本不再直接把窗口级命中作为最终结果，而是先检索字幕窗口，再按 `book_id + episode_order` 聚合为剧集候选。每个候选保留词法得分最优的字幕窗口，输出以下可复核信息：

- 剧名与 `book_id`
- 命中集数与 `episode_uid`
- 在本次词法检索范围内命中的窗口数
- 最佳词法得分
- 最佳证据窗口的字幕行范围、时间范围、摘要和完整文本（按需输出）

这使短剧字幕结果具备了可直接用于后续精排、任务结果保存和人工复核的稳定结构，同时避免同一集的重叠窗口重复占据候选列表。

## 检索口径

长查询使用 SQLite FTS5 的 `trigram` 索引，按 BM25 得分从高到低取窗口，再做剧集聚合。少于 3 个汉字的短查询无法构造三元词，因此自动回退到 `LIKE` 检索；该模式主要用于人工核验，不作为大批量检测的主要路径。

当前默认先取前 200 个窗口命中再聚合，目的是限定候选收敛成本。候选内的 `retrieved_window_count` 表示本次检索窗口池中该集的命中数，不表示全库中的绝对命中总数。

## 验证结果

已使用真实字幕片段验证：

```text
大哥这是横店吗你们是不是在拍戏
```

聚合后的 Top 1 为：

- `book_id`: `41000010048`
- 剧名：`农女致富`
- 第 1 集
- 证据窗口：第 1 至 16 行，`00:00:12,720` 至 `00:00:51,920`

证据窗口中包含完整台词“哎 大哥 这是横店吗 / 你们是不是在拍戏”。短查询“横店”的 `LIKE` 回退也能返回同一剧集的同一证据窗口。

## 后续推进

下一阶段接入独立的短剧字幕语义向量集合。语义召回将只面向 `drama_subtitle_windows`，不复用小说章节或小说语义块集合；结果仍先收敛到 `book_id + episode_order`，再与词法候选合并并进行精排。
