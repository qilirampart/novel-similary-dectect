# 2026-07-03 双 Worker 受控基准

## 目的

验证在已完成一轮业务库写放大削减后，当前批量任务执行链路是否已经具备安全的 `2 workers + item_parallelism=2` 运行条件，同时确认不会出现任务重复执行。

## 基准方法

- 脚本：`scripts/benchmark_task_worker_concurrency_v1.py`
- 数据形态：合成任务，避免外部 embedding API、Qdrant 和真实语料波动影响结果
- 场景参数：
  - `task_count = 4`
  - `items_per_task = 8`
  - `item_parallelism = 2`
  - `sleep_seconds = 0.05`
- 命令：

```powershell
python scripts\benchmark_task_worker_concurrency_v1.py `
  --worker-counts 1,2 `
  --task-count 4 `
  --items-per-task 8 `
  --item-parallelism 2 `
  --sleep-seconds 0.05 `
  --output-json docs\59_task_worker_concurrency_benchmark_latest.json
```

## 本轮修复背景

在首次 `2 workers` 试跑时，暴露出一个正确性问题，而不只是性能问题。

根因是 `claim_next_compare_task()` 每次 claim 前都会调用 `_recover_interrupted_tasks_on_conn()`，而旧逻辑会无条件回收所有 `running / cancel_requested / pause_requested` 任务。这样在双 worker 场景下，worker A 进入 claim 流程时，可能把 worker B 正在正常执行且心跳仍然新鲜的任务重新回收到 `queued`，最终导致重复执行。

本轮修复在 `service/business_store.py` 中为恢复逻辑增加了心跳陈旧判断：

- 新增 `DEFAULT_TASK_RECOVERY_STALE_SECONDS = 120.0`
- 仅当 `last_heartbeat_at` 超过阈值后，才允许执行中断恢复
- 保留原有恢复能力，不直接关闭 recover 机制

## 回归验证

已通过以下测试：

```powershell
python -m pytest tests/test_batch_task_smoke.py -q
python -m pytest tests/test_api_auto_worker_smoke.py -q
```

结果：

- `tests/test_batch_task_smoke.py`: `32 passed`
- `tests/test_api_auto_worker_smoke.py`: `6 passed`

新增或覆盖的关键回归点：

- 双 worker 可以并发处理两个独立任务，且不会重复执行
- 有新鲜心跳的 `running` 任务不会被误恢复
- 原有中断恢复语义仍成立：真正孤儿任务仍可被恢复

## 结论

本轮修复后，双 worker 场景下没有再出现任务重复执行，也没有出现 `completed_total > accepted_total` 或 `compare_call_count` 异常膨胀。说明此前的并发问题已经被 stale-heartbeat 恢复保护正确拦住。

在当前这组受控合成场景下：

- 总耗时从 `2.134s` 降到 `1.012s`
- 总耗时下降约 `52.6%`
- 吞吐从 `14.99 items/s` 提升到 `31.64 items/s`
- 吞吐相对基线提升约 `110.97%`

这说明在已经削减任务热路径写压力的前提下，`2 workers` 具备明确的继续验证价值。

## 现阶段判断

可以继续推进下一轮更严格验证，但还不建议直接把生产或云端默认 worker 数切到 2。下一阶段应该继续验证：

- `pause / resume / cancel` 在双 worker 下是否仍然语义稳定
- 长耗时真实任务下，`120s` 心跳陈旧阈值是否足够保守
- 真实批量任务中，业务库写锁竞争是否仍会成为新的瓶颈

## 拓展观察：4 Worker 试探

在完成双 worker 正确性修复后，又补做了一轮更强的合成并发观察，用来判断下一个瓶颈更像“硬性写锁上限”还是“短任务下的调度成本”。

### 场景 A：短 compare

- 参数：
  - `worker_count = 1,2,4`
  - `task_count = 8`
  - `items_per_task = 16`
  - `item_parallelism = 2`
  - `sleep_seconds = 0.05`

结果摘要：

- `1 worker`: `8.847725s`, `14.47 items/s`, `max_active_compare_calls = 2`
- `2 workers`: `3.666743s`, `34.91 items/s`, `max_active_compare_calls = 4`
- `4 workers`: `2.400410s`, `53.32 items/s`, `max_active_compare_calls = 6`

这里的关键现象是：

- `4 workers` 仍然继续提速
- 但理论上 `4 workers * item_parallelism 2 = 8` 个 compare 槽位，并没有被完全跑满，只达到 `6`

这说明系统在短 compare 场景下已经开始受到调度、状态写入和任务切换开销影响。

### 场景 B：更重的 compare

- 参数：
  - `worker_count = 4`
  - `task_count = 8`
  - `items_per_task = 16`
  - `item_parallelism = 2`
  - `sleep_seconds = 0.2`

结果摘要：

- `4 workers`: `4.523685s`, `28.30 items/s`, `max_active_compare_calls = 8`

这里的信号很明确：当 compare 自身更重时，4 worker 可以把理论上的 `8` 个 compare 槽位跑满。

## 拓展结论

当前系统并不是“根本无法扩到 4 worker”。更准确的判断是：

- 当单条 compare 较短时，业务库写入、状态同步和调度开销占比会上升，导致并发槽位吃不满
- 当 compare 本身更重时，这些开销被摊薄，系统仍然能够把更高并发跑起来

因此，下一个值得优化的点，不再是“能不能并发”，而是“短任务下的协调成本还能不能继续压低”。

## Profiling 后的热路径优化切片

为避免继续靠猜，基准脚本补充了函数级计时，输出文件：

- `docs/59_task_worker_concurrency_profiled_latest.json`
- `docs/59_task_worker_concurrency_profiled_large_latest.json`

这轮 profiling 之后，确认短任务场景下最明显的热点集中在两类写路径：

- 成功结果持久化：`save_task_item_success()`
- 提交阶段的 running 标记：原先逐条 `_mark_task_item_running()`

### 本轮已落地的两刀

1. `save_task_item_success()` 复用执行器手里的输入项元数据

执行器现在会把 `result_id / query_text / created_at` 传回成功持久化函数，避免每条成功结果再额外回表做一次 `SELECT result_id, query_text, created_at`。

2. 提交阶段改为按批次标记 running

执行器新增 `submit_input_batch()`，并通过 `mark_task_items_running()` 一次性标记当前批次要提交的 item，而不是逐条开连接、逐条提交 running 状态。对于默认 `item_parallelism = 2` 的场景，这一刀直接减少了 submit 热路径上的事务数和连接往返。

3. 完成结果改为按 `done` 批次合并持久化

执行器不再对每个已完成 future 单独调用一次成功/失败持久化，而是把同一轮 `done` 里的 success / failure 结果收集后，通过 `save_task_item_outcomes_batch()` 一次性提交。这样进一步压缩了短任务场景下的事务数和连接往返。

4. 运行态轮询切到轻量查询

执行器新增轻量的 `get_compare_task_runtime_state()` 用于 pause / cancel 轮询和进度计数读取，避免在热轮询路径上反复读取完整任务详情。

### 观测结果

使用同一组大样本 profile 场景：

- `worker_count = 1,2,4`
- `task_count = 8`
- `items_per_task = 16`
- `item_parallelism = 2`
- `sleep_seconds = 0.05`

在继续完成 outcome-batch 和轻量 runtime-state 两刀后，`4 workers` 的一组最新观测值为：

- `wall_seconds = 1.866154`
- `throughput_items_per_second = 68.59`
- `max_active_compare_calls = 8`
- `hot_write_seconds = 2.716474`
- `mark_task_items_running`: `75 calls`, `0.459468s`, `6.13ms avg`
- `save_task_item_outcomes_batch`: `77 calls`, `2.006676s`, `26.06ms avg`
- `get_compare_task_runtime_state`: `85 calls`, `0.148490s`, `1.75ms avg`

与优化前上一轮同类 profile 样本相比，单次运行存在波动，但整体方向已经比较清楚：

- `4 workers` 总耗时从约 `2.48s` 降到约 `1.87s`
- 吞吐从约 `51.65 items/s` 提升到约 `68.59 items/s`
- 热写路径总耗时从约 `4.38s` 降到约 `2.72s`
- 短任务场景下的 compare 槽位已能打满 `8/8`

### 当前判断

这说明前面的判断是对的：下一层瓶颈确实主要在短任务的协调写路径，而不是 compare 本身。而在这几轮热路径削减之后，短任务场景已经能够把 `4 workers * item_parallelism 2` 的理论 `8` 个 compare 槽位跑满。

在完成这两刀后，系统已经把最明显的 submit 热点压下去一截。下一阶段更值得继续看的点是：

- `claim_next_compare_task()` 每次 claim 前的 recover / claim 成本
- `save_task_item_outcomes_batch()` 剩余的 payload/结果写入成本
- 是否还需要继续把 `4 workers` 默认化，还是先把 `2 workers` 作为更保守的正式配置

## 运行时默认值说明

基于这几轮结果，当前本地 API 运行时已经把 auto-worker 默认值从 `1` 提升到了 `2`，并引入了显式配置项：

- 环境变量：`NOVEL_SIMILARITY_AUTOWORKER_COUNT`
- 当前默认值：`2`
- 目的：把已经验证过的 `2 workers` 作为本地保守默认，而不是继续停留在单消费者

同时保留 `4 workers` 作为 synthetic benchmark 上限参考，不直接作为第一轮运行时默认值。
