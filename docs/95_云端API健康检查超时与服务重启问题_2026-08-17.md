# 云端 API 健康检查超时与服务重启问题

日期：2026-08-17
范围：`novel-similarity-api.service`、Qdrant、Nginx、watchdog、任务 worker

## 事件结论

2026 年 8 月 17 日，云端 API watchdog 记录到连续健康检查失败并触发自动重启，共触发 `33` 次。当前 API、Qdrant、Nginx 均已恢复，Qdrant 主要集合状态为 `green`，当前发布版本为 `20260808-deepl-video-translation-fix-1`。

本次不是 Qdrant 数据损坏，也不能直接归结为健康接口执行了重查询。`/api/v1/health` 当前只返回固定健康响应，不访问 SQLite、Qdrant 或外部模型 API。更合理的故障链是：API 进程内部线程或同步请求阶段性阻塞，watchdog 在 8 秒超时、连续 2 次失败后立即重启；而停止阶段 worker 仍可能卡在 SQLite 锁等待或外部 API 调用中，导致 systemd 等待约 90 秒后才发送 `SIGKILL`。

## 现场证据

- watchdog 每 30 秒检查一次，单次健康检查超时为 8 秒，连续 2 次失败即执行 `systemctl restart`。
- 8 月 17 日日志重复出现 `health_failed count=1`、`health_failed count=2`、`restarting service`、`recovered service`。
- API 停止时多次出现 `stop-sigterm` 超时，约 90 秒后由 systemd 强制结束进程。
- 线程栈出现 `claim_next_compare_task`、`run_next_queued_task`、`_run_worker_loop`，以及 `connect_business_db` 和 SQLite 访问路径。
- SQLite 连接配置为 `timeout=60`、`busy_timeout=60000`、WAL；任务 claim 和恢复扫描使用 `BEGIN IMMEDIATE`。
- 当前运行时启动 2 个 API worker，每个小说任务内部默认再开 2 个 item worker，外部 embedding、Qdrant、翻译调用均可能持续数十秒。

## 影响评估

本次重启可能造成以下影响：正在执行的任务被中断；重启后的恢复扫描可能将任务重新入队；如果原 worker 尚未真正退出，存在旧 worker 与新 worker 同时完成同一条输入的风险；用户侧会看到任务长时间不动、取消中或进度回退。当前检查到的近期任务均已完成，没有发现新的 queued/running 任务，但历史上仍有 paused 和 partial_failed 任务，会干扰运维判断。

## 临时处置与后续原则

当前先保持服务可用，不在本事件文档中直接修改 watchdog 或生产配置。后续修复必须先在本地验证：健康探针分级、worker 可中断停止、外部调用总预算、任务 lease/幂等恢复、SQLite 锁等待上限，再通过灰度发布和旧 release 回滚验证。watchdog 不应把一次短暂的应用层阻塞直接升级为重启；重启前还应确认服务确实失去 liveness，并保留足够的失败窗口和退避。

## 关联代码位置

- `api/runtime_worker.py`：worker 与 recovery sweeper 的生命周期。
- `api/config.py`：worker 数量、恢复阈值、外部 API 超时配置。
- `service/business_store.py`：SQLite 连接、任务 claim、heartbeat、恢复与进度写入。
- `service/task_executor.py`：任务内并发和 `ThreadPoolExecutor` 退出行为。
- `service/drama_subtitle_task_executor.py`：字幕任务串行处理以及翻译回退链路。
- `scripts/install_cloud_health_watchdog_v1.py`：云端 watchdog 的检查与重启策略。
