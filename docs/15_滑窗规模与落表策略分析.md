# 滑窗规模与落表策略分析

更新时间：2026-04-29

## 1. 这份分析解决什么问题

当前已经完成：

- 两批小说正文入正式 V2 库
- `self_short_novels` 全量 `evidence_windows` 落表
- 异常重复文本样本导出

接下来的关键决策是：

**`online_owned_novels` 要不要也按 `200 / 50` 参数全量落 `evidence_windows`。**

这个问题不能靠感觉判断，要看三类真实数据：

- 当前库已经膨胀到多大
- `self_short_novels` 全量滑窗到底产出了多少窗口
- 如果不预生成，而是“候选章节现切”，速度到底够不够

## 2. 当前正式库现状

正式库文件：

- `data/novel_similarity_v2.sqlite3`

实测：

- 文件大小：约 `12.51 GB`
- `page_size=4096`
- `page_count=3279714`
- `freelist_count=0`

当前表规模：

- `datasets=2`
- `ingest_batches=2`
- `raw_manifest_rows=555892`
- `books=32549`
- `chapters=555892`
- `chapter_contents=555313`
- `terminal_failures=579`
- `evidence_windows=6036674`

其中：

- `555892` 是两批章节总数
- `555313` 是真正拿到正文并成功入库的章节数
- 差值 `579` 正好对应源端固定 `404`

## 3. 当前滑窗参数

V1 当前定版参数：

- `window_size = 200`
- `step_size = 50`

原因很直接：

- 它处在之前约定的 `150-300` 字建议区间内
- `200 / 50` 的 overlap 大约是 `75%`
- 对证据比对来说，宁愿窗口稍密一点，也不要把可能命中的句群切断

这层滑窗挂在：

- `content_clean`

而不是：

- `content_retrieval`

原因是证据层后面要回指具体文本位置，`content_retrieval` 经过额外压缩空白和换行，offset 不够稳。

## 4. `self_short_novels` 全量落表结果

已全量落表数据集：

- `self_short_novels`

实测结果：

- 正文章节数：`112846`
- 全量滑窗数：`6036674`

平均到每章：

- 平均窗口数：`53.49`
- 中位窗口数：`51`
- `P95` 窗口数：`94`
- 最大窗口数：`3513`

说明：

- 绝大多数章节窗口数并不夸张
- 但存在极少数超长章节，会把窗口数瞬间拉高
- 例如最长异常章节 `char_count_clean=175768`，单章就切出了 `3513` 个窗口

这类长章不是主流，但它们会明显拉大总表体积和索引负担。

## 5. `online_owned_novels` 全量落表规模预估

`online_owned_novels` 当前正文情况：

- 正文章节数：`442467`
- `sum_char_count_clean=579413132`
- 平均每章字符数：`1309.51`

按同样的 `200 / 50` 参数估算：

- 预计滑窗总数：`10477720`

每章窗口分布：

- 平均窗口数：`23.68`
- 中位窗口数：`21`
- `P95` 窗口数：`41`
- 最大窗口数：`449`

和短篇这批相比，线上小说这批单章平均更短，所以平均窗口数反而更少。

但问题不在“单章多不多”，而在：

- 章节总数太大

所以只要全量落表，总窗口数还是会直接破千万。

## 6. 为什么不建议现在直接把第二批全量落表

### 6.1 当前库已经不轻

现在正式库约 `12.51 GB`，其中已经包含：

- 两批正文
- 一批 `self_short_novels` 的 `6036674` 条滑窗

也就是说，现在这 `12.51 GB` 不是“纯正文库”，已经被滑窗明显抬重了。

### 6.2 第二批再全量落表，库体积会继续显著上升

粗估比例：

- 当前 `6036674` 条窗口对应一个 `12.51 GB` 的整体库
- 如果第二批再补 `10477720` 条窗口，总窗口量会来到 `16514394`

哪怕按非常保守的比例估计，后续也大概率会把这个 SQLite 库继续推高很多 GB。

这会直接带来三个问题：

- 本地开发机磁盘占用继续上升
- SQLite 备份、复制、压缩、抽样都会变慢
- 后续很多查询会越来越依赖正确索引和更细的取数策略

### 6.3 证据滑窗不是当前粗召回主路径

我们之前已经定过一个原则：

- `150-300` 证据滑窗用于证据比对
- 不作为第一版全库向量化对象
- 也不是第一版粗召回的主索引对象

这意味着：

- `evidence_windows` 更像“精比对阶段的二级材料”
- 而不是“所有章节都必须预生成的一级索引”

既然它不是主召回层，就没有必要一上来就把第二批也全量铺满。

## 7. 现切到底慢不慢

这个问题必须用真实数据回答。

### 7.1 单章现切其实非常快

实测：

- `self_short_novels` 典型章：`2671` 字，现切 `51` 个窗口，耗时约 `0.000037s`
- `self_short_novels` 最长章：`175768` 字，现切 `3513` 个窗口，耗时约 `0.001353s`
- `online_owned_novels` 典型章：`1309` 字，现切 `24` 个窗口，耗时约 `0.000606s`
- `online_owned_novels` 最长章：`22569` 字，现切 `449` 个窗口，耗时约 `0.000227s`

一句话：

- **切窗本身几乎不慢**

### 7.2 真正慢的是“怎么把候选正文拿出来”

如果直接用一条不够友好的 SQL：

- 按 `dataset_key` 过滤
- `join chapter_contents`
- 再 `order by chapter_uid`

那么 100 章取数会慢到：

- `self_short_novels` 约 `11.84s`
- `online_owned_novels` 约 `57.53s`

但这不是“现切不行”，而是“取数方式不对”。

### 7.3 两段式取数后，现切是可行的

改成两段式：

1. 先从 `chapters` 里拿 `chapter_uid`
2. 再按 `chapter_uid in (...)` 去 `chapter_contents` 取正文

同样取 100 章正文，实测：

- `self_short_novels` 约 `1.24s`
- `online_owned_novels` 约 `3.37s`

而切窗本身几乎可以忽略不计。

也就是说：

- **候选章节现切是完全可行的**

尤其在第一版里，精比对一般不会一次处理几万章候选，而是几十章到几百章。

## 8. 当前预生成和现切的对比

### 方案 A：继续全量预生成 `online_owned_novels`

优点：

- 命中候选后可直接查窗口表
- 证据比对阶段取窗口更直接

缺点：

- 再增加约 `1047` 万窗口
- SQLite 继续显著增重
- 本地开发验证、复制和维护成本都上升
- 当前阶段还没证明这部分全量窗口一定值得长期保留

### 方案 B：第二批先不全量落表，改成“候选章节现切”

优点：

- 不再立刻把库体积推高
- 切窗计算本身足够快
- 更符合“证据层按需生成”的角色定位
- 更适合第一版边跑边验证

缺点：

- 精比对阶段需要多一步取正文 + 现切
- 对取数 SQL 和章节缓存策略要求更高

## 9. 当前推荐结论

当前推荐：

**不要立刻对 `online_owned_novels` 全量落 `evidence_windows`。**

建议分两步走：

1. 保留当前 `self_short_novels` 全量滑窗结果，作为真实样本库
2. `online_owned_novels` 改成“候选章节现切”

更具体一点：

- 粗召回阶段：
  - 仍基于章级 / 词法级 / 后续中粒度结构来做
- 精比对阶段：
  - 拿到候选章节后，按 `chapter_uid` 取正文
  - 现场切成 `200 / 50` 证据窗口
  - 再做 `RapidFuzz / overlap / Jaccard / 局部对齐`

这样做更符合现在这个阶段的工程目标：

- 先跑通链路
- 先拿到可复核证据
- 先控制本地资源

而不是提前把整个库做成一个很重的证据窗口仓库。

## 10. 建议的下一步

建议按这个顺序继续：

1. 输出一版 `F5` 入库完成统计摘要
2. 新增“候选章节现切”脚本或函数
3. 先不继续全量落 `online_owned_novels` 的 `evidence_windows`
4. 开始做第一版粗召回链路
5. 在精比对阶段直接接入“按 `chapter_uid` 取正文 -> 现切 -> 对齐”

如果后面验证发现：

- 候选章节数量很大
- 现切阶段成为稳定瓶颈

再回头把第二批按需补落到 `evidence_windows`，也完全来得及。
