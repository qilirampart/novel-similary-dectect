# Web 可视化系统 V1 非功能设计

## 1. 这份文档解决什么

`docs/33_Web可视化系统V1规划.md` 解决的是“产品形态和页面怎么做”。

这份文档补的是另一半问题：

- 你图里提到的那些问题要不要考虑
- 要考虑到什么深度
- 哪些是 V1 现在就必须处理的
- 哪些可以先记账，后面再升级

一句话说，这份文档解决的是：

- 系统不只是“能跑”
- 而是“上线后不容易乱、不容易卡、不容易把自己拖死”

## 2. 先给结论

这些问题都需要考虑。

但不需要一上来就按“大厂完整平台版”一次做满。

更合理的做法是分两层：

- V1 现在必须处理：会直接影响可用性、稳定性、结果可信度的问题
- V2 再升级：会提升治理能力，但不做也不会立刻把系统跑坏的问题

当前项目最需要优先处理的，不是“页面好不好看”，而是下面 6 件事：

- 同步接口和异步任务边界要切清楚
- 检索库、业务库、向量库要分职责
- `rewrite` 模式的外部依赖要能降级
- 大文本和批量文件不能直接硬塞进接口
- 系统要有限流、超时和任务状态
- 日志、健康检查、失败原因要能看见

## 3. 这些问题是否需要考虑

| 问题 | 是否要考虑 | V1 处理深度 |
| --- | --- | --- |
| 高并发/高吞吐 | 要 | 做轻量限流和并发上限，不做复杂弹性扩容 |
| 异步任务 | 要 | 批量任务必须异步，单条检测可以同步 |
| 内容安全 | 要 | 先做内网隔离、轻登录、日志脱敏，不做重 DLP |
| 资源安全 | 要 | 做内存边界、超时、候选上限、任务并发控制 |
| 存储架构 | 要 | 检索库、业务库、向量库、文件存储分开 |
| 大文件处理 | 要 | 上传落磁盘，分批解析，禁止整文件进内存 |
| 权限体系 | 要 | V1 轻量处理，V2 再做细粒度 RBAC |
| 监控告警 | 要 | V1 先做健康页、任务日志、失败统计 |
| 多机扩容 | 要考虑但可后置 | V1 先单机或单节点部署，保留升级边界 |

## 4. V1 必须现在处理的非功能项

### 4.1 同步接口和异步任务边界

这件事必须先定死。

否则后面会变成：

- 单条检测也很慢
- 批量检测堵死接口
- 前端一直转圈
- 出问题时不知道是“请求慢”还是“任务慢”

当前建议边界：

- `单条检测`：
  - 允许同步接口
  - 适合粘贴一段短剧文案，立刻看结果
- `批量检测`：
  - 必须异步
  - 上传文件后创建任务，后台慢慢跑
- `超长单条输入`：
  - 不继续走同步接口
  - 直接转成后台任务更稳

可以把它理解成：

- 单条检测像“前台现查”
- 批量检测像“提交工单，后台排队处理”

### 4.2 并发模型和限流

V1 不需要一开始就追求特别高并发，但必须防止“无限并发把自己压死”。

当前链路里最重的部分不是前端，而是：

- SQLite FTS 检索
- 候选章节现切
- 细比对
- `rewrite` 模式下的语义召回
- 语义召回依赖的 embedding 服务和 Qdrant

所以 V1 必须有并发上限。

推荐做法：

- API 层对单条检测做并发闸门
- `reuse` 和 `rewrite` 最好分开限流
- 批量 worker 并发度单独控制，不和在线接口抢同一批资源

建议的首版口径：

- `reuse` 在线检测：先控制在小并发
- `rewrite` 在线检测：并发更保守，因为会额外依赖语义侧
- 批量任务：先从 `单 worker + 小并发` 起步

这里不要一上来把参数拉满。

原因很简单：

- 当前阶段更怕“不稳定”
- 不怕“先保守一点再慢慢放量”

### 4.3 任务系统必须独立于页面请求

批量任务不能继续沿用“页面发一个大请求，然后等它跑完”的思路。

V1 应该至少有：

- 任务表
- 任务状态
- 任务进度
- 失败原因
- 输出文件路径

推荐状态：

- `queued`
- `running`
- `completed`
- `partial_failed`
- `failed`
- `cancelled`

推荐的最小任务模型：

- 前端上传文件
- 后端落盘并写入任务表
- worker 轮询任务表取任务
- 一条一条或一批一批执行
- 执行结果写回结果表和导出文件

第一版不一定非要上 `Celery / Redis`。

当前更实际的顺序是：

- 先用“业务库任务表 + worker 轮询”跑通
- 后面任务量上来，再升级消息队列

### 4.4 存储架构必须拆职责

这是非常关键的一条。

如果把所有东西都塞进一个库，后面一定会越来越乱。

当前建议拆成 4 层：

#### 1. 检索库

职责：

- 小说元数据
- 章节正文
- FTS 索引
- 证据窗/语义切片元数据

当前可继续复用：

- `data/novel_similarity_v2.sqlite3`

注意：

- 这个库尽量偏“读多写少”
- 不要让前台任务日志、用户操作记录、大量结果 JSON 也往这里塞

#### 2. 业务库

职责：

- 任务表
- 检测结果表
- 复核标记
- 导出记录
- 操作日志

V1 可选两种方式：

- 小范围内测：单独一个轻量 SQLite 业务库
- 真准备多人使用：直接上 PostgreSQL

更推荐的判断是：

- 如果只是你们自己少数人开发联调，业务库用 SQLite 也能先走
- 如果准备给较多同事日常使用，业务库最好尽早切 PostgreSQL

原因不是“PostgreSQL 更高级”，而是：

- SQLite 写锁简单粗暴
- 多人同时写任务、写结果、写复核状态时更容易顶住

#### 3. 向量库

职责：

- `rewrite` 模式下的语义候选召回

当前建议继续：

- `Qdrant`

因为它的职责很清楚：

- 不管任务表
- 不管页面
- 只管向量检索

#### 4. 文件存储

职责：

- 上传原文件
- 解析后的中间文件
- 导出 CSV/JSON
- 错误文件

第一版建议：

- 文件落本地磁盘目录
- 数据库里只存元数据和路径

不要把大文件直接放进数据库 BLOB。

## 5. 大文本和大文件处理

### 5.1 单条检测要有输入边界

单条检测虽然是“粘贴文本”，但也不能无限长。

否则问题会非常直接：

- 页面提交慢
- 接口超时
- 语义召回成本飙升
- 细比对候选变大

V1 应该定一个清晰边界：

- 普通单条检测：限制在一个合理字符数以内
- 超过上限：提示用户改走批量任务

这和前台医院挂号很像：

- 普通门诊现场处理
- 特别复杂的情况转住院流程

### 5.2 批量文件不能整包进内存

批量上传支持：

- `txt`
- `csv`
- `xlsx`

但处理方式必须是：

- 先落磁盘
- 再分批解析
- 一批一批写入结果

不要做成：

- 文件一上传
- 全量读进内存
- 全量展开
- 全量等待完成

这在 24G 或 32G 的机器上都容易把自己拖慢。

### 5.3 大结果也不能直接回前端

批量任务结果如果很多，不应该：

- 一次接口返回全部明细

而应该：

- 列表分页查
- 详情单条看
- 导出走文件下载

这个边界越早定，后面页面越稳。

## 6. 资源与稳定性控制

### 6.1 内存控制

当前链路已经有一个很好的方向：

- 不是把整本书搬出来比
- 而是先粗召回，再只切候选章节

V1 要坚持这个原则，不要退回去。

需要继续坚持的控制点：

- 候选章节数量有限
- 每章切窗数量有限
- 返回 top 结果有限
- 大批量任务分批提交、分批落库

### 6.2 超时控制

在线系统必须有超时，不然前端体验和故障定位都会很差。

建议至少分 3 层：

- HTTP 请求超时
- 语义依赖调用超时
- 单任务整体超时

其中最重要的思想不是“超时后报错”，而是：

- 能降级就降级
- 不能降级再失败

### 6.3 降级策略

当前系统已经有一个非常重要的好习惯：

- `rewrite` 语义侧不可用时，可以回退为 `fallback_lexical_only`

这条必须保留，而且要在页面上明确展示。

V1 推荐的降级原则：

- `reuse` 模式优先保证可用
- `rewrite` 模式如果语义侧失败，可以降级到词面链路
- 但必须把状态写清楚，不能假装“这是完整 rewrite 结果”

换句话说：

- 可以退化
- 但不能黑盒

### 6.4 后台任务和在线请求分资源

如果在线接口和批量任务共用同一批重资源，最容易出现的情况是：

- 白天一有人跑批量，页面就开始慢

所以 V1 至少要做到：

- 在线接口有自己的并发上限
- 批量 worker 有自己的并发上限
- 两边不要共享无限线程

如果条件允许，后面甚至可以做成：

- 在线 API 一台
- 离线 worker 一台

但这属于下一阶段增强，不是 V1 必须。

## 7. 内容安全和权限控制

现在已知前提是：

- 小说数据属于半公开数据
- 不需要把安全性做得过重

但这不等于“完全不用管”。

V1 仍然建议做 4 件事：

### 7.1 系统先放内网

第一版不建议直接公网暴露。

默认口径：

- 内网访问
- 固定办公环境使用

### 7.2 做轻量登录或访问控制

V1 可以不做复杂 RBAC，但至少要防止：

- 谁都能进
- 谁都能导出
- 谁都能看到历史任务

最小可接受方案：

- 简单登录
- 或反向代理层鉴权
- 或办公网白名单 + 基础身份标识

### 7.3 日志脱敏

日志里需要保留：

- `request_id`
- `task_id`
- 模式
- 耗时
- 错误类型

但不要把这些东西无脑打进明文日志：

- 完整 token
- 完整大段原文
- 整个返回 JSON

更好的做法是：

- 文本只留预览
- 敏感配置只记来源，不记值

### 7.4 导出要可追踪

批量结果导出后，最好能追踪：

- 谁导的
- 什么时间导的
- 导了什么任务

这不复杂，但很有必要。

## 8. 监控、日志和健康检查

V1 不需要一上来做全套监控平台，但至少要做到“出问题能查”。

最低要求：

- 接口访问日志
- 任务执行日志
- 失败任务清单
- 语义降级次数
- 慢请求记录

系统状态页建议展示：

- 检索库是否可读
- Qdrant 是否可用
- 语义 embedding 服务是否可用
- 最近任务成功/失败数
- 当前排队任务数
- 最近一次导出结果时间

一个很实用的原则是：

- 普通用户看“结果页”
- 维护人看“系统状态页”

## 9. 推荐的 V1 部署拓扑

### 9.1 最小可用拓扑

- 前端 Web UI
- FastAPI 服务
- 任务 worker
- 检索库 SQLite
- Qdrant
- 语义 embedding 后端

其中语义 embedding 后端可以有两种形态：

- 外部 API
- 内部独立语义节点

这样设计的好处是：

- 页面不关心你背后用的是 API 还是本地模型
- 只认统一的语义召回接口

### 9.2 当前阶段更现实的落地方式

对你们现在这套项目，更现实的顺序是：

- 先把 Web UI、API、worker 放在同一台应用机上
- 检索库先本地挂载
- Qdrant 单独跑服务
- `rewrite` 继续复用现在已经打通的语义链路

等后面并发量真的上来，再拆：

- 业务库单独部署
- worker 单独部署
- 语义节点单独部署

## 10. V1 现在不必一次做满的部分

下面这些问题需要记账，但不是现在就必须完成：

- 公司统一 SSO 接入
- 细粒度角色权限
- Redis/Celery 正式任务队列
- 多机水平扩容
- 自动弹性扩缩容
- 对象存储统一归档
- 完整告警平台
- 更重的安全审计和 DLP

这些属于“系统做大以后该补的治理项”。

如果现在一口气全做，反而会拖慢主线。

## 11. V1 推荐的落地顺序

### 第一步

先把“检索库”和“业务库”拆开。

### 第二步

补任务表、结果表、复核表、导出记录表。

### 第三步

补批量 worker 和任务状态流转。

### 第四步

补接口限流、超时和语义降级展示。

### 第五步

补系统状态页和维护日志。

### 第六步

再开始前端批量页、复核页和导出页联动。

## 12. 当前建议结论

你图里那些问题，都不是“以后再想”的问题，而是现在就应该有口径。

但现在最合理的做法不是把它们全部做重，而是：

- 先把系统拆对
- 先把边界定清
- 先把最容易炸的地方控住

当前 V1 最重要的非功能结论可以收敛成 8 句：

- 单条同步，批量异步
- 在线请求和后台任务分资源
- 检索库、业务库、向量库、文件存储分职责
- 大文件落磁盘，不进数据库 BLOB
- 大结果分页查，不一次性回前端
- `rewrite` 可降级，但必须显式标注
- 日志要能查，系统状态要能看
- 权限先做轻量，但不能完全裸奔

如果按这个边界推进，当前 Web V1 方案就是稳的。
