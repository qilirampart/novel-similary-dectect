# Web 可视化系统 V1 规划

## 1. 这份规划要解决什么

当前“小说库相似度比对服务”已经基本跑通了核心能力：

- 小说库接入
- 词面粗召回
- 语义粗召回
- 细比对
- 证据片段输出

下一步不再是继续证明“技术能不能跑”，而是要把它做成一个别人也能稳定使用的内部系统。

这份文档要回答 4 个问题：

- 后续是做桌面软件，还是做 Web 页面
- 第一版页面给谁用
- 第一版到底做哪些页面和能力
- 技术上怎么落，才能尽量复用现在已经写好的 Python 链路

## 2. 先说结论

当前最合适的产品形态不是桌面软件，而是：

- `内部 Web 页面 + 后端服务 + 后台任务`

更准确一点说，是一套内部 B/S 系统，而不是单机工具。

## 3. 为什么当前不建议优先做桌面软件

### 3.1 核心能力天然在服务端

这个项目真正重的部分不是页面，而是：

- 全库检索
- 向量召回
- 细比对
- 结果落库
- 后台批量任务

这些能力都适合集中部署，不适合分散在每个人电脑上各跑一套。

### 3.2 数据和索引需要集中管理

当前系统依赖的数据包括：

- 小说正文库
- FTS 索引
- Qdrant 向量索引
- 任务日志
- 历史检测结果

如果做桌面软件，很容易变成：

- 每个人本地一份环境
- 每个人版本不一致
- 数据和索引状态不一致

这会很快失控。

### 3.3 后续会频繁调规则和调参数

这个项目还处在快速迭代期，后续高概率还会继续调整：

- `reuse / rewrite` 口径
- 证据强弱阈值
- 语义召回参数
- 候选融合逻辑
- 页面展示字段

Web 方案只需要统一更新服务端；桌面软件则会额外带来：

- 发版
- 装包
- 版本追踪
- 客户端兼容

### 3.4 真实使用场景更像“内部审核平台”

这个系统更像：

- 内部搜索平台
- 审核辅助平台
- 任务处理平台

不像：

- 单人本地剪辑工具
- 单机文件处理器

所以形态上更适合网页后台。

## 4. V1 服务对象

第一版系统的主要使用人群可以先按 3 类理解：

### 4.1 直接操作人

通常是实际跑检测的人，负责：

- 粘贴短剧文案
- 上传批量文本
- 查看候选结果
- 导出复核材料

### 4.2 复核人

通常是业务、法务或内容审核同事，负责：

- 查看命中的小说和章节
- 对比证据片段
- 标记“高疑似 / 待复核 / 排除”

### 4.3 维护人

通常是你们自己，负责：

- 管系统参数
- 看任务状态
- 查失败原因
- 做数据更新与索引维护

## 5. V1 产品目标

V1 不追求“大而全”，只追求形成一个别人能实际用起来的闭环。

第一版建议目标只有 4 个：

### 5.1 支持单条检测

用户可以直接粘贴一段短剧文案，选择模式后发起检测。

### 5.2 支持批量检测

用户可以上传一批文本，后台排队跑，最后统一看结果。

### 5.3 支持结果复核

用户能在页面上直接看到：

- 命中的小说
- 命中的章节
- 证据片段
- 相似度标签
- `reuse / rewrite` 结果差异

### 5.4 支持结果沉淀

跑过的任务不能只是“看一眼就没了”，而要能沉淀：

- 任务记录
- 结果记录
- 人工复核结论
- 导出文件

## 6. V1 明确不做什么

为了避免第一版变形，下面这些先不做。

### 6.1 不做桌面安装包

第一版不做 EXE、不做客户端升级体系。

### 6.2 不做数据接入全可视化

小说数据接入、清洗、全量回填、索引重建，第一版继续保留脚本化运维，不放进前台页面。

### 6.3 不做复杂权限系统

如果是内网小范围使用，第一版先做最轻量的登录或简单权限控制，不要一开始就把权限系统做重。

### 6.4 不做“字幕提取一体化”

桌面工具仍然是上游，负责：

- 视频下载
- ASR
- 字幕导出

本系统只负责接收已经准备好的文本，做小说库比对。

## 7. 推荐的 V1 页面结构

### 7.1 页面一：单条检测页

这是第一优先级页面。

核心交互：

- 输入短剧文案
- 选择检测模式：`reuse / rewrite`
- 提交检测
- 展示结果

核心展示：

- top 命中小说
- 章节名 / 章节号
- `fine_score`
- `review_label`
- `confidence_label`
- 证据片段对比
- 语义状态：`semantic_ready / fallback_lexical_only`

这一页的目标很明确：

- 把“脚本能跑”变成“人能看懂”

### 7.2 页面二：结果详情页

单条检测页可以看到摘要，但要有一个详情页看完整信息。

建议布局：

- 左侧：输入文案
- 中间：命中的小说信息
- 右侧：候选证据片段

详情页建议至少展示：

- 候选书名
- 章节
- 最佳命中窗口
- query 片段
- 命中文本片段
- 最长连续命中长度
- `ngram_recall / jaccard / sequence_ratio`
- 最终标签解释

### 7.3 页面三：批量任务页

这一页面向真实使用。

核心交互：

- 上传 txt/csv/xlsx
- 选择检测模式
- 创建任务
- 看任务状态

状态建议有：

- 排队中
- 运行中
- 已完成
- 部分失败
- 失败

任务页还应支持：

- 下载结果 CSV
- 查看任务明细
- 查看失败原因

### 7.4 页面四：结果列表 / 复核页

批量任务跑完后，不能只看原始 JSON。

需要一页专门面向人工复核：

- 一行一条结果
- 支持筛选 `强证据 / 中证据 / 弱证据`
- 支持筛选 `reuse / rewrite`
- 支持人工打标

人工打标字段建议先很简单：

- `确认高疑似`
- `继续复核`
- `排除`

### 7.5 页面五：系统状态页

这一页不是给普通用户的，是给维护人看的。

建议展示：

- 当前小说库规模
- FTS 索引状态
- Qdrant 状态
- 最近任务
- 最近失败日志
- 当前模型链路状态

第一版不用做得很漂亮，但一定要能快速看故障。

## 8. 推荐的系统结构

## 8.1 总体形态

建议结构如下：

- 前端：内部 Web UI
- 后端：Python API 服务
- 后台任务：异步任务队列
- 数据层：业务库 + Qdrant

### 8.2 前端

建议：

- `React`
- `Ant Design`

原因：

- 表单、表格、抽屉、详情页、任务页都很成熟
- 适合内部管理系统
- 开发速度快

### 8.3 后端

建议：

- `FastAPI`

原因：

- 和当前 Python 检索链路天然接近
- 很容易把现有 `service/` 和 `scripts/` 里的能力封装成接口
- 自动生成接口文档，方便联调

### 8.4 后台任务

建议：

- 单条检测可以同步跑
- 批量检测要改成异步任务

第一版可以先用轻量方案：

- 数据库任务表 + worker 轮询

如果后面任务量上来，再升级到：

- Celery / RQ / Redis 队列

### 8.5 数据层

当前开发阶段可以先继续沿用：

- SQLite
- Qdrant

但正式内部多人使用时，更建议：

- 业务结果库迁到 `PostgreSQL`
- 向量继续保留 `Qdrant`

原因很简单：

- SQLite 更适合单机验证
- PostgreSQL 更适合多任务、多用户和历史沉淀

## 9. 推荐的后端接口边界

第一版 API 不需要太多，先收敛成 5 类。

### 9.1 单条检测接口

- `POST /api/v1/compare/single`

入参：

- `query_text`
- `detection_mode`
- 可选参数覆盖项

出参：

- top 结果
- 命中的章节和书籍
- 证据片段
- `reuse_detection`
- `rewrite_detection`

### 9.2 批量任务创建接口

- `POST /api/v1/tasks`

入参：

- 上传文件
- 检测模式
- 可选参数

出参：

- `task_id`

### 9.3 任务列表接口

- `GET /api/v1/tasks`

### 9.4 任务详情接口

- `GET /api/v1/tasks/{task_id}`

### 9.5 结果详情接口

- `GET /api/v1/results/{result_id}`

### 9.6 系统状态接口

- `GET /api/v1/system/health`

## 10. 当前 Python 能力如何复用

现在最重要的不是重写算法，而是把现有能力“包起来”。

当前可复用能力已经比较完整：

- 全库词面检索：
  - `service/global_retrieval.py`
- 语义召回：
  - `service/semantic_retrieval.py`
- 候选章节现切：
  - `service/candidate_slicing.py`
- 细比对：
  - `service/fine_compare.py`
- 双模式口径：
  - `service/detection_modes.py`
- 当前全链路入口：
  - `scripts/run_global_compare_v1.py`

V1 最合理的技术策略不是“前端直接调脚本”，而是：

- 先把脚本里已有逻辑抽成后端 service 函数
- 再由 FastAPI 暴露接口

## 11. 推荐的用户使用流程

### 11.1 单条检测流程

1. 用户进入单条检测页
2. 粘贴短剧文案
3. 选择 `reuse` 或 `rewrite`
4. 提交检测
5. 页面展示 top 命中结果
6. 用户点进详情页看证据片段
7. 用户做人工判断

### 11.2 批量检测流程

1. 用户上传一批文案
2. 系统生成任务
3. 后台逐条跑比对
4. 前端轮询任务状态
5. 任务完成后进入结果列表
6. 用户筛选高疑似结果并导出

## 12. V1 页面最重要的展示原则

第一版 UI 不要追求花哨，优先保证 3 点：

### 12.1 结果可解释

必须让人一眼看出：

- 为什么命中这本书
- 为什么是这章
- 命中的具体证据在哪

### 12.2 模式清晰

必须明确区分：

- 当前是在 `reuse`
- 还是在 `rewrite`

不要把两种模式混成一个黑盒分数。

### 12.3 任务有状态

批量任务一定要能看到：

- 任务是否在跑
- 跑到哪
- 哪些失败了

不能继续停留在脚本控制台思维。

## 13. 推荐的分阶段开发顺序

### 阶段 0：先定接口契约

先不要急着写页面。

先把“单条检测返回什么 JSON”定住。

因为页面怎么画，本质都依赖结果结构。

### 阶段 1：做最小单条闭环

先实现：

- FastAPI
- 一个单条检测接口
- 一个最小单条检测页

目标是：

- 可以在页面上粘贴文案
- 返回 top5 结果

### 阶段 2：补详情页和证据对比页

把命中片段真正展示清楚。

### 阶段 3：补批量任务页

这是第一版实用性的关键节点。

### 阶段 4：补结果复核与导出

让系统真正进入“可协作使用”状态。

### 阶段 5：补系统状态页

让维护人能查问题。

## 14. 当前阶段建议的技术路线

建议按下面这条线推进：

### 14.1 第一版开发环境

- 先在当前工作区内新增：
  - `api/`
  - `web/`

### 14.2 后端先行

先把后端 API 跑起来，再接前端。

原因：

- 现在后端能力强，前端能力还没开始
- 如果不先定 API，前端很容易反复改

### 14.3 前端先做内部管理风格

第一版不追求“产品化外观”，更适合：

- 清晰
- 直接
- 好查结果

不要做成“消费级产品风格”，那是后面的事。

## 15. 当前阶段的风险点

### 15.1 不能把离线脚本和在线接口混成一团

离线任务包括：

- 数据接入
- 全量向量回填
- 建索引

在线任务包括：

- 单条检测
- 批量检测
- 结果查询

这两类东西必须分开，不然系统会越来越乱。

### 15.2 第一版不要过早做复杂权限和工作流

不然很容易把项目从“先能用”拖成“先搭平台”。

### 15.3 批量任务一定要异步

如果把批量任务硬塞进同步接口，前端体验会很差，也不好排错。

## 16. 当前建议结论

当前最稳的产品方向可以明确为：

- 做内部 Web 系统
- 不做桌面软件
- 前端只是展示和交互层
- 后端统一承接现有检索与比对能力
- 第一版先做单条检测闭环，再补批量与复核

## 17. 下一步建议

如果认可这份规划，下一步建议直接进入：

1. 定 `单条检测接口` 的 JSON 结构
2. 新建 `FastAPI` 服务骨架
3. 新建 `React + Ant Design` 前端骨架
4. 先做单条检测页闭环

也就是说，下一阶段不是继续谈“做不做 UI”，而是：

- 按这份规划正式进入 V1 开发
