# V1 粗召回方案与 FTS 成本实验

更新时间：2026-04-29

## 1. 这份文档解决什么问题

当前已经完成：

- 两批小说正文入正式 V2 库
- `self_short_novels` 全量 `evidence_windows` 落表
- `online_owned_novels` 明确改为候选章节现切

下一步必须先跑通一个可用的“粗召回”。

这一步的目标不是直接判断是否侵权，而是先把“像的章节”从几十万章里捞出来，再交给后面的细比对。

所以这份文档要回答三个问题：

1. 第一版粗召回到底用什么技术路线
2. 这条路线在当前数据规模下能不能先跑通
3. 全量章级索引的磁盘成本大概有多大

## 2. V1 粗召回定版路线

第一版当前采用：

- `SQLite FTS5 trigram` 做章级命中定位
- “稀有 `3-gram` 缩圈”做候选召回
- `3-gram overlap` 做候选精排

对应脚本：

- `scripts/build_chapter_fts_v2.py`
- `scripts/retrieve_candidates_v1.py`

设计理由很直接：

- 当前重点是先把文本相似章节从全库里快速拉出来
- 中文文本用默认英文式分词不稳定，`trigram` 更适合首版
- `FTS5` 是 SQLite 自带能力，部署最轻，不需要额外服务
- `3-gram overlap` 可以在中文场景下给一个简单、稳定、可解释的重打分
- 这一版先不引向量化，不引本地模型，先把纯文本粗召回闭环跑通

## 3. 为什么不是一上来就做向量化

不是说向量化没用，而是当前阶段不适合先从向量化开局。

原因：

- 现在还没有正式的验证集，先做 embedding 很容易“做了很多，但判断不了好坏”
- 当前已知第一版重点是“找文字相似”，传统文本召回能更快出结果
- 向量化更适合第二阶段处理“改写明显但语义相近”的洗稿场景
- 先把章节级召回、候选缩圈、细比对链路跑通，后面再把向量召回叠进去更稳

现阶段更合理的路线是：

1. 先用传统文本召回打通第一版
2. 再准备正负样本和评估集
3. 最后再决定向量召回接到哪一层最划算

## 4. FTS 技术选型结论

本机 Python `sqlite3` 已确认支持：

- `FTS5`
- `trigram tokenizer`

关键验证结论：

- 中文短词如 `小说` 这种只有 2 个字的查询，不能直接命中 trigram 索引
- 中文 3 字及以上片段，如 `看小说`、`一起看`、`今天下` 可以正常命中

因此查询时不能直接把原文整段塞进 `MATCH`，而是要先把查询文本转成字符 `3-gram`，再拼成 `OR` 条件送进 FTS。

这也是 `retrieve_candidates_v1.py` 当前采用的实现。

## 5. 第一轮烟雾验证结果

### 5.1 小范围索引验证

- 数据范围：`self_short_novels`

建索引脚本实测：

- 结果：`5000` 章成功入索引

### 5.2 查询验证

从真实章节正文中截取片段做查询，共验证 3 个章节：

- `chapter_uid=1`
- `chapter_uid=2000`

验证结果：

- 3 次查询都把原章节召回到第 `1` 名
- 前几名候选大多来自同书或相似叙事语境

这说明第一版“章级粗召回”最小闭环已经打通。

## 6. 第一轮批量评估与策略修正

### 6.1 首次批量评估为什么失败

后续补了批量评估脚手架：

- `scripts/export_retrieval_eval_queries_v1.py`
- `scripts/evaluate_retrieval_v1.py`

从 `self_short_novels` 中均匀抽了 `200` 条查询片段做第一轮评估。

首次结果非常差：

- `Hit@1 = 0.005`
- `Hit@5 = 0.005`
- `Hit@10 = 0.005`

根因不是数据库坏了，也不是 `overlap` 算法坏了，而是最初那条候选生成策略本身有问题：

- 旧策略：把全部 query `3-gram` 用 `OR` 拼成一个大 `MATCH`
- 再按 `bm25` 截前 `200`

这条路的问题在于：

- 120 字查询往往能拆出 90 到 100 多个 `3-gram`
- 其中很多是高频公共短片段
- `OR` 查询会放进来大量“只命中几个常见 gram”的章节
- 真正的目标章节虽然也匹配，但可能在 `bm25 LIMIT 200` 之前就被淹没

简单说，就是：

- **旧方案不是精排错了，而是候选集先截歪了**

### 6.2 修正后的候选策略

修正后改成两段式：

1. 先统计 query 中各个 `3-gram` 在全库里的文档频次
2. 选出最稀有的 `12` 个 `3-gram` 作为“种子 gram”
3. 用这些种子 gram 做命中汇总
4. 按“命中种子数 + 稀有权重”先缩出候选池
5. 再用 `3-gram overlap` 做最终排序

这条策略更像现实中的排查思路：

- 不是拿一句话里所有字串平均用力
- 而是优先看其中最有辨识度的片段

可以把它想成在人群里找一个人：

- 旧方法像是拿“穿衣服、会走路、两只眼睛”去筛人，结果候选太多
- 新方法像是先抓“左脸有痣、红色帽子、手里拿旧相机”这种更稀有的特征，候选会立刻缩小

### 6.3 修正后的批量评估结果

修正后，用同一批 `200` 条评估查询重跑：

- `Hit@1 = 0.995`
- `Hit@5 = 1.000`
- `Hit@10 = 1.000`
- `MRR = 0.9975`
- `median self rank = 1`
- `p95 self rank = 1`

当前评估结果文件：

- `data_samples/retrieval_eval/self_short_eval_queries_v1.csv`
- `data_samples/retrieval_eval/self_short_eval_results_v1.csv`
- `data_samples/retrieval_eval/self_short_eval_summary_v1.json`

这说明：

- 在“原章正文截片段回查原章”这个自检任务上，当前粗召回已经足够稳定
- 第一版可以进入下一层：准备更像真实业务的正负样本评估

## 7. 首轮性能优化结果

### 7.1 为什么之前会慢到二十多分钟

在策略修正后，虽然准确率已经恢复，但批量评估跑 `200` 条查询仍然很慢。

拆分单次查询耗时后，发现瓶颈非常集中：

- query 预处理很快
- 词频读取很快
- 候选重排很快
- **真正慢点在“候选池 SQL”**

进一步定位后发现：

- FTS 本身按单个种子 `3-gram` 查询几乎是毫秒级
- 真正拖慢的是：为了做 `dataset_key` 过滤，在候选池阶段把 FTS 结果再 `JOIN chapters`

对照实验结论非常明确：

- 带 `JOIN chapters + dataset_key` 过滤：约 `20.7s`
- 直接在单数据集索引上查 `rowid`：约 `0.007s`

也就是说：

- **慢点不是 FTS 搜索本身**
- **慢点是为了做数据集过滤，多做了一次非常重的 join**

### 7.2 这次怎么优化

当前已经把索引作用域写入元数据表：

- 表：`retrieval_fts_indexes`

记录内容包括：

- `table_name`
- `dataset_key`
- `detail`
- `text_normalized`
- `row_count`

这样检索时就能知道：

- 这个 FTS 表是不是只覆盖单一数据集

如果索引本身就只覆盖：

- `self_short_novels`

那查询时就不需要再 `JOIN chapters` 去做一次 `dataset_key` 过滤，而是可以直接使用：

- `rowid -> chapter_uid`

这一步把最重的数据库路径绕开了。

### 7.3 优化后的速度

优化后实测：

- 单条查询：约 `0.085s`
- 连续 `20` 条查询平均：约 `0.213s / 条`

同时重跑 `200` 条评估后，准确率没有下降：

- `Hit@1 = 0.995`
- `Hit@5 = 1.000`
- `Hit@10 = 1.000`
- `MRR = 0.9975`

这说明当前这轮优化是“真正提速”，不是靠砍逻辑换来的假快。

## 8. FTS 索引空间实验

为了判断后面要不要直接建全量章级索引，先拿 `5000` 章做了三组实验。

实验样本：

- `self_short_novels` 前 `5000` 章

实验结果：

- `detail=full`：约 `90.25 MB`
- `detail=column`：约 `73.27 MB`
- `detail=none`：约 `47.85 MB`

实验文件：

- `data_samples/fts_size_experiment/fts_full.sqlite3`
- `data_samples/fts_size_experiment/fts_column.sqlite3`
- `data_samples/fts_size_experiment/fts_none.sqlite3`

结论：

- `detail=none` 最省空间，但 `BM25` 信息退化明显，不适合作为当前默认档位
- `detail=full` 最完整，但空间成本偏高
- `detail=column` 是当前最平衡的选择
  - 比 `full` 明显省空间
  - 仍可保留 `BM25` 打分

因此 `build_chapter_fts_v2.py` 当前默认参数已定为：

- `--detail column`

## 9. 全量章级索引的成本判断

当前正式库正文章节数：

- `555313`

如果简单按 `5000` 章样本线性估算：

- `detail=column` 全量章级索引大约会落在 `8 GB` 左右量级

这不是精确值，但足够说明一个现实问题：

- 全量章级 trigram FTS 索引能做
- 但它会显著增加当前 SQLite 文件体积

因此当前建议是：

- 第一阶段先继续做“小范围验证 + 召回链路验证”
- 等验证集和评估方式准备出来后，再决定是否把 `555313` 章一次性全量建索引

## 10. 当前结论

当前可以明确落下来的结论有五条：

1. 第一版粗召回路线已经定版：`FTS5 trigram + 稀有 3-gram 缩圈 + 3-gram overlap 精排`
2. 这条路线已经在正式库数据上通过了真实文本烟雾验证
3. 这条路线已经在 `200` 条批量评估查询上跑出 `Hit@1=0.995`
4. 当前单数据集索引在消除无意义 `JOIN chapters` 后，查询速度已经降到亚秒级
5. 全量章级索引可以做，但磁盘成本不小，当前更适合先验证效果，再决定是否全量建设

## 11. 下一步建议

推荐下一步按这个顺序推进：

1. 整理一批“已知相似 / 已知不相似”章节样本，做评估集
2. 基于现有粗召回结果，补一轮“跨章节、跨书、非自身”的负样本评估
3. 再决定 `online_owned_novels` 是建独立索引，还是改成混合索引 + 作用域路由
4. 粗召回稳定后，再接“候选章节现切 -> 细比对”
