# 项目对抗性审查与优化任务板

日期：2026-08-17
审查对象：小说相似度比对、短剧字幕匹配、批量任务队列、API、SQLite、Qdrant、前端复核链路

## 审查结论

当前系统的核心召回和批量链路已经可用，但稳定性边界仍偏向“正常网络、少量任务、单进程运行”的场景。最大风险不在单条比对速度，而在任务执行期间的外部依赖、SQLite 写锁、进程重启和任务恢复之间缺少明确的租约与中断协议。8 月 17 日云端 watchdog 触发 33 次重启，说明这不是理论问题，应优先处理运行时稳定性。

以下结论分为三类：标记为“已确认”的问题来自代码或云端日志；标记为“高风险”的问题已经能从代码路径推导出来，但需要压测或故障注入确认；标记为“优化项”的问题不一定立即造成故障，但会在数据量和用户数增长后放大。

## P0：先解决服务不会误重启、任务不会重复执行

### 1. 健康检查与 watchdog 误判重启

状态：**已确认**。watchdog 每 30 秒运行一次，健康检查 8 秒超时，连续两次失败就重启；8 月 17 日实际触发 33 次。健康接口本身是固定响应，因此不能用“健康查询太重”解释全部问题。

风险：短暂的 Python 调度阻塞、线程池耗尽、进程高负载或网络抖动都会被当作进程故障，重启反而增加 SQLite 锁竞争和任务恢复压力。

建议：拆分 liveness 与 readiness；watchdog 只用极轻量 liveness 判断进程是否还活着，依赖检查放入 readiness 和系统状态；将失败窗口改为连续多次并带恢复滞后、重启退避和 StartLimit；重启前记录活跃任务、SQLite 锁等待和外部调用阶段。验收标准是故意制造一次 8 至 20 秒的依赖阻塞时服务不被反复重启，真正停止进程时仍能在预期窗口内恢复。

### 2. worker 停止不可中断，导致 90 秒优雅停止超时

状态：**高风险，已有云端证据**。API worker 使用 daemon thread，但停止时只对线程 `join(timeout=10)`；任务内部的 `ThreadPoolExecutor` 使用上下文管理器，退出时会等待在途 future；embedding、Qdrant、DeepL 请求均是阻塞调用。

风险：停止信号到达后，线程可能继续等待外部 API 或 SQLite，取消和暂停也只能在若干阶段被检查。systemd 因此等待约 90 秒后 `SIGKILL`，任务可能被截断，恢复时状态不确定。

建议：引入进程级 stop event 和任务级 cancellation token；所有外部请求使用可配置的总预算和可中断等待；executor 退出明确区分“停止接收新任务”和“等待当前 item”；shutdown 期间禁止 recovery sweeper 继续写库。验收标准是停止 API 后 10 秒内 worker 进入可观测的 stopping 状态，最长等待不超过配置预算，任务最终只出现一个确定状态。

### 3. stale recovery 与旧 worker 并发完成同一任务

状态：**高风险**。默认 stale 阈值为 120 秒；heartbeat 主要在提交输入、进度刷新和 item 完成时更新。字幕任务在单条处理期间还会经历词法、语义、Qdrant、翻译回退等多个外部阶段。若一次请求超过阈值，recovery sweeper 可能把仍在运行的任务重新入队。

风险：旧 worker 尚未退出时，新 worker 可以 claim 同一任务；旧 worker 后续写入结果会覆盖新状态，或同一输入被重复计算、重复导出。

建议：为任务增加 `claim_epoch`/lease token，所有 item 状态更新都带 worker token 条件；恢复只允许真正失去 lease 的 worker 重新执行；对结果写入使用幂等键和条件更新；stale 阈值应大于单条最大外部调用预算，而不是凭经验固定 120 秒。验收标准是故意暂停网络超过阈值，恢复后同一 `result_id` 只能有一份有效结果，任务计数不重复增长。

## P1：解决 SQLite 锁争用和外部依赖放大

### 4. SQLite 单写者与恢复扫描争锁

状态：**高风险**。业务库使用 WAL，但仍只有一个 writer；连接 `busy_timeout=60s`，claim、恢复扫描、任务控制、进度和结果均会写入同一库。两个 API worker 加上任务内并发后，写入来源不止一个；recovery sweeper 每 15 秒也可能执行 `BEGIN IMMEDIATE`。

风险：一次较长写事务会让其他请求等待 60 秒，表现为健康探针超时、暂停/取消迟迟不生效、进度不更新。WAL 提升读写并发，但不能消除单写者限制。

建议：缩短所有写事务，禁止在事务内做解析、序列化或外部调用；将 claim/recovery/control 写操作集中到轻量 writer 队列，或至少使用更短 busy timeout 并配合有限重试；把大 payload 和运营状态写入分离；对每个写路径记录锁等待时间。验收标准是 2 个任务、4 个 item 并发下，任务控制请求 P95 不超过 2 秒，SQLite busy/locked 次数可统计且无长时间堆积。

### 5. 外部 embedding、Qdrant、翻译缺少统一总预算和熔断

状态：**高风险**。Gitee embedding 默认最多 4 次尝试，每次 timeout 可达 30 秒并带退避；语义检索会按 query chunk 发起多次 Qdrant 查询；字幕翻译回退还可能按目标语言依次调用 DeepL。当前主要是单次调用异常后降级，没有统一的任务级预算、熔断、并发舱壁和近期失败率指标。

风险：外部服务变慢会占满 worker；多个用户同时提交时，重试会形成请求放大，最终表现为排队变长、watchdog 超时和任务误恢复。

建议：为每个 item 设置总 deadline；embedding、Qdrant、翻译分别限制并发；429/5xx/timeout 使用指数退避但限制总次数；连续失败触发短暂熔断；结果中记录每一阶段耗时、超时类型和是否降级。验收标准是外部 API 人为延迟或返回 429 时，系统在固定预算内结束并明确标记，不会无限等待或把超时伪装成命中。

### 6. 短剧批量执行仍是单条串行

状态：**已确认**。`service/drama_subtitle_task_executor.py` 逐条处理字幕 item；小说批量则在任务内使用 item parallelism。短剧链路的单条速度已经可接受，但大量字幕任务会被一个 worker 长时间占用。

建议：在外部 API 并发舱壁约束下，为短剧任务增加可配置的有限并发；或把“语言检测、词法召回、语义召回、翻译回退”拆成阶段队列。验收标准是并发提升后吞吐提高，同时 SQLite 写入、Qdrant 延迟和外部 API 429 不恶化。

## P2：数据、接口和前端的规模化治理

### 7. 任务上传文件、导出文件和软删除记录缺少生命周期

状态：**优化项**。上传接口按任务目录保存文件，任务删除主要是软删除；导出文件持续落在 runtime 目录，当前代码路径未形成明确的保留期、清理和磁盘告警机制。

风险：重复测试和长期运行会让磁盘增长，最终影响 SQLite WAL、导出和服务启动。此前 release 体积已经暴露出重复测试 SQLite 占用问题。

建议：配置上传/导出保留天数、按用户和任务归档、清理前校验任务状态；保留哈希和汇总元数据后再删除原文件；磁盘达到阈值时阻止新上传并给出明确提示。

### 8. 复核详情与导出仍可能放大大 JSON 读取

状态：**高风险**。结果主体已将 payload 放入独立表，但复核详情需要回读完整 `result_payload_json`，导出还会进一步 hydrate 证据文本。大批量结果和长上下文会造成 SQLite 读取、Python 内存和 Excel 生成时间同时增长。

建议：列表只返回摘要；详情按候选、证据窗口和上下文分层分页；限制单次上下文字符数；导出采用流式/分块并记录耗时，必要时将大证据转为文件引用而不是全部塞进 JSON。

### 9. API 边界缺少统一限流、请求体上限和超时策略

状态：**优化项**。上传保存使用 `shutil.copyfileobj`，业务代码没有统一文件大小上限；单条比对、批量创建、证据上下文和导出也没有统一的用户级并发/速率限制。

建议：增加反向代理和应用双层 body size 限制、单用户并发上限、单条文本最大长度、导出并发上限，并为每个请求返回 request id 和阶段耗时。

### 10. 登录会话的生产安全边界偏弱

状态：**优化项，内网场景下仍应补齐**。密码当前为无盐 SHA-256；session cookie 设置 `secure=False`，认证接口没有明显的 CSRF 防护或登录失败限速；每次读取 session 都会更新 `last_seen_at`，会增加 SQLite 写入频率。

建议：迁移到 Argon2id/bcrypt，生产 HTTPS 下启用 Secure、HttpOnly、SameSite，并校验 Origin/CSRF；增加登录失败限速；将 session heartbeat 改为按时间间隔更新或使用内存缓存，减少无意义写入。

### 11. 前端轮询会制造重复读请求

状态：**优化项**。批量页在存在活动任务时每 4 秒刷新任务列表；复核页还会按选中结果单独请求详情。当前已有部分请求去重和选中项保持逻辑，但多标签页、网络延迟、任务数量增加后仍可能出现请求交叉和旧响应覆盖新状态。

建议：统一使用 AbortController/请求版本号，轮询采用退避和页面可见性控制；列表响应只更新变更任务；任务详情和结果列表分离刷新；对 SSE/WebSocket 只在确有实时需求时引入，避免用长连接替代基础分页。

### 12. 历史状态会污染运营指标

状态：**已观察**。历史库中存在 paused、partial_failed 等遗留任务。它们会继续进入任务统计和故障观察，使“当前是否有阻塞任务”与“历史是否曾失败”混在一起。

建议：增加 active/history/archive 维度；看板默认只统计近期和非删除任务；对历史遗留任务做一次明确归档，不直接物理删除业务证据。

## 建议实施顺序

### 状态定义

- `待开始`：已登记，尚未进入开发。
- `进行中`：正在修改代码或补充测试。
- `已验证`：本地代码和测试已通过，尚未同步云端。
- `待云端灰度`：本地已验证，等待带回滚方案发布。
- `已完成`：云端灰度、回归和结果记录均已完成。
- `阻塞`：存在明确外部依赖或环境阻塞，需要记录原因，不得静默跳过。

每个任务完成后必须更新：状态、完成日期、验证命令或压测数据、影响范围、是否需要云端同步。未完成任务不提前标记为完成。

## 发布门槛

在 P0 项目完成前不建议直接把 worker 数量继续上调，也不建议仅通过延长 watchdog 超时掩盖问题。任何云端发布都必须保留当前 release、数据库备份和 watchdog 配置备份，按“部署前健康检查、灰度任务、连续观察、失败自动回滚”的顺序执行。发布验收至少包括：双用户同时批量、暂停/恢复/取消、服务重启恢复、外部 embedding 超时降级、Qdrant 暂不可用、复核分页和导出完整性。
