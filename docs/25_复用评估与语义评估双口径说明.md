# 复用评估与语义评估双口径说明

更新时间：2026-05-02

## 1. 这份文档解决什么问题

当前项目里有两件事容易被混在一起：

- 产品检测模式：`reuse / rewrite`
- 评估查询口径：`reuse / semantic`

前者是在说“系统给业务提供什么检测能力”，后者是在说“我们拿什么样的测试 query 去测这条能力”。

这两层如果不分开，最容易出现的误判是：

- 看到 `rewrite` 模式，就以为必须用同一套短 query 去评估
- 看到 `120` 字 query 的结果不好，就误以为语义链路本身不行

这次验证后的明确结论是：

- `复用评估` 和 `语义评估` 不能再共用同一套 query 口径
- `120` 字左右的短 query 适合测文本复用
- `300` 字左右的长 query 更适合测语义召回 / 洗稿检测

## 2. 为什么一套 query 不够

同样是“拿一段文本去库里找相似章节”，`复用检测` 和 `语义检测` 实际上在看两种不同信号。

### 2.1 复用检测更像“找原句”

它关心的是：

- 原句是否直接复用
- 长片段是否连续复用
- 少量改字后是否还能被词面链路抓住

所以它更像拿一句话去全文检索。query 短一些反而更合理，因为短 query 更接近“证据片段”。

### 2.2 语义检测更像“找同一段剧情”

它关心的是：

- 角色关系是否对应
- 事件顺序是否对应
- 剧情骨架是否对应
- 虽然换了说法，但整体意思是否还是同源

这种情况下，如果 query 太短，就容易只剩一句对白、一个动作或一个套路场景，语义信息不够。

可以把它理解成两个生活例子：

- `复用检测` 像查重，拿一句原话去搜，看有没有人直接抄
- `语义检测` 像找“同一个故事”，你至少要把前因后果讲清一点，别人才能判断是不是同一个剧情

## 3. 当前两套评估口径怎么定义

### 3.1 `reuse` 评估口径

用途：

- 验证文本复用链路
- 验证 FTS / n-gram / compare 这条词面链路

当前默认：

- `query_len = 120`
- 更偏证据片段
- 更适合看 `Hit@1`、`MRR`、强命中率

适合回答的问题：

- 原句复用能不能抓住
- 长片段复用能不能稳定排到前面
- 粗召回到细比对这条纯文本链路是否稳定

### 3.2 `semantic` 评估口径

用途：

- 验证语义召回链路
- 验证 rewrite / 洗稿检测未来是否有落地基础

当前默认：

- `query_len = 300`
- 更偏剧情摘要片段
- 更适合看语义 topK 命中率

适合回答的问题：

- 语义向量能不能把同源章节先找回来
- chunk 路由和 chapter 路由融合后是否能提升召回
- 后续遇到改写、洗稿时，这条链路有没有继续增强的价值

## 4. 为什么语义评估建议用 300 字左右

这不是随便拍的数，而是这次验证里直接跑出来的。

在前 `500` 章、`50` 条样本上，剩余 3 条语义漏召回样本做了 query 长度诊断：

- `query_id=20`
  - `120` 字：未命中
  - `200/300` 字：`rank1`
- `query_id=47`
  - `120` 字：未命中
  - `200` 字：`rank2`
  - `300` 字：`rank1`
- `query_id=2`
  - `120/200` 字：未命中
  - `300` 字：`rank2`

说明问题不主要在“模型完全不懂”，而在“query 给的信息太短”。

`300` 字左右的好处是：

- 能带出人物
- 能带出事件
- 能带出前后因果
- 能减少只凭一句对白造成的误判

这也更接近后续真实输入形态，也就是短剧前几集文案、剧情梗概、剧情摘要，而不只是单句原文。

这个结果说明：

- 当前本地语义链路不是不能用
- 主要问题是以前拿错了评估口径

## 6. 现在该怎么理解产品模式和评估模式

建议把这两组概念彻底分开：

### 6.1 产品模式

- `reuse`
  - 默认模式
  - 输出强文本证据
- `rewrite`
  - 附加模式
  - 在 `reuse` 基础上叠加语义候选

### 6.2 评估模式

- `reuse`
  - 用短 query 测词面复用能力
- `semantic`
  - 用长 query 测语义召回能力

不要把它理解成：

- `reuse` 产品模式只能用 `reuse` 评估
- `rewrite` 产品模式只能看一个混合总分

更合理的理解是：

- 产品上是双模式
- 评估上是双口径
- 两套口径分别回答不同问题

## 7. 当前推荐的评估方式

现阶段建议固定成下面这套：

1. `reuse` 评估
   - 用 `120` 字 query
   - 主要看文本复用链路

2. `semantic` 评估
   - 用 `300` 字 query
   - 主要看向量召回和双路融合

3. 不直接横比两套口径下的绝对分数
   - 因为它们测的不是同一个问题

4. 只在各自口径内部做版本对比
   - 例如：
   - `semantic q300 v1` 对比 `semantic q300 v2`
   - `reuse q120 v1` 对比 `reuse q120 v2`

## 8. 代码层当前已经落地到哪里

当前已落地：

- `service/eval_query_modes.py`
  - 正式定义 `reuse / semantic` 两套评估 query 预设
- `scripts/export_retrieval_eval_queries_v1.py`
  - 支持 `--eval-mode reuse|semantic`
- `scripts/evaluate_retrieval_v1.py`
- `scripts/evaluate_semantic_retrieval_v1.py`
- `scripts/evaluate_global_compare_v1.py`
- `scripts/export_negative_candidate_review_v1.py`

这些脚本现在都能透传 `eval_mode`，避免后续把不同评估口径的结果混在一起看。

## 9. 团队建议结论

当前建议正式定版为：

- `复用检测` 和 `洗稿/语义检测` 继续并行推进
- `复用评估` 和 `语义评估` 必须分成两套口径维护
- `120` 字 query 不再作为语义链路的默认评估口径
- `300` 字 query 作为当前语义评估默认口径

一句话总结：

不是这条语义链路不行，而是之前拿“查原句”的尺子，在量“看剧情是不是同源”。
