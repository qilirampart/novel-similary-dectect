# 大规模源数据向量化方案

更新时间：2026-05-02

## 1. 这份方案要解决什么问题

这份方案不是再讨论“要不要做向量化”，而是回答下面这几个更实际的问题：

- 面对大规模小说源数据，哪些内容值得做向量化，哪些不值得
- 当前更适合走本地模型，还是更适合走外部 API
- 现在这套工程链路，怎样才能从“能跑通”平滑升级到“能回填大规模数据”
- 后续拿到更大规模全量数据后，哪些地方要升级，哪些地方其实不用推翻重来

## 2. 当前已经拿到的真实基线

### 2.1 数据规模基线

当前测试基线见 [12_测试数据基线说明.md](E:/点众/小说库相似度比对服务工作区/docs/12_测试数据基线说明.md)：

- 两批数据合计约 `55.6 万章`
- 正文总字数已经接近 `8.95 亿字`
- 当前这批数据不是最终生产全量，但已经不是“小样本演示”

### 2.2 本地向量化基线

当前本地方案见 [22_中文小说向量化方案与Mac部署说明.md](E:/点众/小说库相似度比对服务工作区/docs/22_中文小说向量化方案与Mac部署说明.md)：

- 路线：`Ollama + qwen3-embedding:8b + Qdrant`
- 当前中尺度真实结果：
  - 前 `500` 章共切出 `2663` 个 `semantic_chunks`
  - 本地 `24G Windows` 上整轮向量化耗时约 `4170s`
  - 折合约 `1.57s / chunk`

这说明：

- 本地路线已经能跑通完整链路
- 但不适合直接拿来做几十万章到上百万 chunk 的全量回填

### 2.3 Gitee API 真实测速基线

当前已完成 Gitee API 的真实批量测速，相关脚本与结果在：

- [benchmark_gitee_embedding_v1.py](E:/点众/小说库相似度比对服务工作区/scripts/benchmark_gitee_embedding_v1.py)
- [sweep_gitee_embedding_limits_v1.py](E:/点众/小说库相似度比对服务工作区/scripts/sweep_gitee_embedding_limits_v1.py)

已经确认的关键事实：

- `Qwen3-Embedding-8B` API 可正常调用
- 支持显式指定 `dimensions`
- 稳定单批上限按 `25` 条处理更安全
- 当前已测稳定甜点区间：
  - `batch_size=24~25`
  - `concurrency=12~24`
- 当前建议默认值：
  - `batch_size=24`
  - `concurrency=12`
- 在该组合下，实测吞吐约 `25.34 向量/秒`

### 2.4 一个必须讲清的边界

当前“效果验证”主结论，来自本地 `Ollama qwen3-embedding:8b` 路线，而不是 Gitee API 路线。

也就是说：

- 我们已经验证过“本地语义链路可用”
- 我们已经验证过“Gitee API 吞吐可用”
- 但还没有正式完成“Gitee API 向量质量是否和当前本地方案一样够用”的 A/B 验证

所以后面的正式大规模方案，应当是：

- 先把 Gitee API 作为大规模回填候选主路线
- 再补一个小规模质量闸门
- 闸门通过后，再切正式全量回填

## 3. 先给结论

当前最适合我们这类大规模源数据的方案，不是“全量全粒度都向量化”，而是下面这套更克制的方案：

### 3.1 当前主方案

- 只做 `semantic_chunks(800/200)` 的全库语义向量化
- 不做 `evidence_windows(200/50)` 的全库向量化
- `chapter` 向量先保留为增强项，不作为当前第一阶段必做项
- 全量回填候选主路线优先考虑 `Gitee Embedding API`
- 主数据和任务状态继续放 `SQLite`
- 向量索引继续放 `Qdrant`

### 3.2 当前默认参数

- 向量模型：`Qwen3-Embedding-8B`
- 请求维度：`1024`
- 语义切片：`800/200`
- 默认回填参数：
  - `batch_size=24`
  - `concurrency=12`
- 当前回填对象：
  - `canonical-only`
  - 也就是先做 exact dedup，再只对 canonical 章节切片和向量化

### 3.3 当前不建议做的事

- 不建议对 `evidence_windows` 做全量向量化
- 不建议继续用 `24G Windows + 本地 Ollama` 暴力跑全量回填
- 不建议一上来把 `chapter` 向量也纳入主回填工作量
- 不建议在未做质量 A/B 前，直接把 Gitee API 当正式主索引来源

## 4. 为什么这样定

## 4.1 为什么只做 `semantic_chunks`

我们现在其实有两套切片：

- 证据窗：`200/50`
- 语义窗：`800/200`

这两者的职责不同：

- `200/50` 适合细比对和展示证据
- `800/200` 适合做语义粗召回

如果把 `200/50` 也拿去做全库向量化，会出现三个问题：

- 数量会膨胀得太快
- 单片语义太碎
- 向量库会变得又大又碎，吞吐和成本都不划算

所以更适合的分工是：

- `evidence_windows` 继续只服务细比对
- `semantic_chunks` 才是全库语义索引主粒度

## 4.2 为什么 `chapter` 向量暂时后放

当前已经验证过：

- `chapter` 向量是有价值的
- 它能补掉一部分 `chunk-only` 的漏召回

但当前更大的现实问题不是“召回一点点不够强”，而是“全量向量化工作量太大”。

在这个阶段，把 `chapter` 向量也一起做进去，会带来三个额外成本：

- 向量总量继续上涨
- 回填工期继续拉长
- 质量融合逻辑也会更复杂

所以当前更合理的取舍是：

- 第一阶段只做 `semantic_chunks`
- 把 `chapter` 向量保留为后续增强选项

## 4.3 为什么大规模回填更适合走 API

本地路线的真实速度大概是：

- `1.57s / chunk`
- 约 `0.64 向量/秒`

如果按当前 `8.95 亿字` 用 `800/200` 做语义切片，粗略估算：

- `chunk` 数量约等于 `总字数 / 600`
- 即约 `149 万 chunk`

那么本地回填工期大概是：

- `149 万 / 0.64 ≈ 233 万秒`
- 约 `650 小时`
- 约 `27 天`

这还没算：

- 重试
- 中断
- 机器被占用
- 长时间运行不稳定

换成当前 Gitee API 的稳定甜点参数：

- 吞吐约 `25.34 向量/秒`

那么同样 `149 万 chunk` 的理论回填时间大概是：

- `149 万 / 25.34 ≈ 16.3 小时`

即使给它留出实际工程缓冲，按 `18~24 小时` 预算也依然是可接受的。

所以从工程现实看：

- 本地路线适合验证链路
- API 路线更适合大规模离线回填

## 4.4 为什么默认先用 `1024` 维

`Qwen3-Embedding-8B` 在 Gitee API 上支持多维输出。

当前优先选 `1024` 维，有三个原因：

- 吞吐更容易打上去
- Qdrant 向量存储体积更可控
- 适合先做大规模回填主线验证

按 `149 万 chunk` 粗估：

- `1024` 维，单向量 `4KB` 左右
  - 纯向量原始体积约 `5.7 GiB`
- `4096` 维，单向量 `16KB` 左右
  - 纯向量原始体积约 `22.8 GiB`

这还没有把 payload、索引和副本开销算进去。

所以 `1024` 维更适合做第一阶段大规模回填默认值。

但要强调：

- `1024` 维是当前默认候选
- 不是不可变真理
- 是否正式采用，必须过质量 A/B 闸门

## 5. 适合大规模源数据的正式向量化范围

| 对象 | 是否做全量向量化 | 当前建议 |
|---|---|---|
| `evidence_windows(200/50)` | 否 | 只用于细比对证据展示 |
| `semantic_chunks(800/200)` | 是 | 当前正式主线 |
| `chapter` 向量 | 暂不全量做 | 保留为后续增强项 |

一句话概括：

- 全库主语义索引 = `semantic_chunks`
- 证据展示 = `evidence_windows`
- 整章语义补强 = `chapter` 向量，后补

## 6. 大规模回填的推荐处理链路

### 6.1 回填前置

先做：

1. 原始数据入库
2. 正文清洗
3. exact dedup
4. 得到 canonical 章节集合

再做：

5. 对 canonical 章节生成 `semantic_chunks(800/200)`
6. 只把待回填 chunk 放入向量化任务范围

### 6.2 向量化执行链路

建议链路如下：

1. 从 `semantic_chunks` 里取未同步记录
2. 按 `batch_size=24` 组装请求
3. 以 `concurrency=12` 并发调用 Gitee API
4. 拿到向量后写入 Qdrant
5. 同步写回本地 `sync_state`
6. 标记这批 chunk 已完成

### 6.3 为什么要保留 `sync_state`

大规模回填一定会遇到：

- 中断
- 失败重试
- 模型参数升级
- 维度切换
- 局部脏数据重跑

所以必须让向量化是“可恢复”的，而不是“一次性脚本”。

推荐最少保留这几个信息：

- `chunk_uid`
- `collection_name`
- `embedding_model`
- `embedding_dim`
- `synced_at`
- 可选：`content_hash`

如果后面补 `content_hash`，就可以更优雅地做到：

- 原文没变，不重算
- 原文变了，只重算受影响 chunk

## 7. 存储设计建议

## 7.1 SQLite 继续做什么

SQLite 继续负责：

- 章节元数据
- 清洗后正文
- `semantic_chunks`
- exact dedup 结果
- 向量同步状态
- 回填任务筛选

它不负责：

- 真正的向量近邻搜索

## 7.2 Qdrant 继续做什么

Qdrant 继续负责：

- 存储 chunk 向量
- 语义 TopK 检索

### 7.3 Collection 建议版本化

不要继续只用过于抽象的固定名字。

更适合大规模长期运行的命名方式是：

- `novel_semantic_chunk_embeddings_qwen3_8b_1024_v1`

名字里最好带上：

- 模型
- 维度
- 主版本

这样后面做这些事会轻松很多：

- `1024` 和 `2048` 的 A/B
- API 路线和本地路线并存
- 老索引回滚
- 灰度切换

### 7.4 Payload 最少建议保留

建议每个向量至少带：

- `chunk_uid`
- `chapter_uid`
- `book_id` 或 `novel_id`
- `dataset_key`
- `chunk_order`
- `start_offset`
- `end_offset`
- `is_canonical`

这样查询后可以直接：

- 回章
- 回书
- 做过滤
- 进细比对

## 8. 大规模回填工期怎么看

## 8.1 当前压力口径下的粗估

按当前测试基线：

- 约 `8.95 亿字`
- `semantic_chunks(800/200)`
- 粗估约 `149 万 chunk`

| 路线 | 速度基线 | 估算工期 | 判断 |
|---|---|---|---|
| 本地 `Ollama 8b` | 约 `0.64 向量/秒` | 约 `27 天` | 不适合全量回填 |
| Gitee API 稳定甜点参数 | 约 `25.34 向量/秒` | 理论约 `16.3 小时` | 适合离线批量回填 |

更务实的工程预算建议：

- 单 worker：按 `18~24 小时` 预估
- 两个独立 worker：可以把工期再往下压

## 8.2 为什么当前测试口径仍有代表性

这一点和 [12_测试数据基线说明.md](E:/点众/小说库相似度比对服务工作区/docs/12_测试数据基线说明.md) 保持一致：

- 当前测试是“书较少，但单书更长”
- 最终生产更像“书更多，但每本只取前 25 章”

这两者都在抬高：

- 参与检索的章节规模
- 语义 chunk 总量

所以当前这套工作，不是在做没有代表性的演示，而是在验证：

- 这条向量化路线是否成立
- 回填工期是否可控
- 向量层是否能跟现有粗召回与细比对链路接上

## 9. 正式切换到 API 前，必须加一个质量闸门

这一步不能省。

因为当前“效果好”的结论，主要来自本地 `Ollama` 路线。

所以在正式用 Gitee API 回填之前，必须补一轮 A/B 验证：

### 9.1 验证对象

- 用 Gitee API 重建一套 `smoke_500` 语义集合
- 至少先测：
  - `1024` 维
- 如果效果不够，再补：
  - `2048` 维
  - `4096` 维

### 9.2 验证脚本

直接复用现有评估链路：

- [evaluate_semantic_retrieval_v1.py](E:/点众/小说库相似度比对服务工作区/scripts/evaluate_semantic_retrieval_v1.py)
- [evaluate_rewrite_smoke_v1.py](E:/点众/小说库相似度比对服务工作区/scripts/evaluate_rewrite_smoke_v1.py)

### 9.3 当前建议的通过标准

可以先按这个口径看：

- `semantic q300` 评估中：
  - `Hit@10` 不低于当前本地主线
  - `Hit@1` 不出现明显台阶式下跌
- `rewrite smoke` 中：
  - 不应大量 fallback
  - `missing_target_count` 应保持为 `0`

如果 `1024` 维过线，就直接用它做正式大规模回填。

如果 `1024` 维不过线，就不要死扛：

- 直接升到 `2048`
- 再不够就升到 `4096`

## 10. 适合当前项目节奏的分阶段方案

### 阶段 A：已经完成

- 本地 `Ollama + Qdrant` 链路跑通
- `rewrite` 语义链路跑通
- Gitee API 吞吐和稳定性摸底完成

### 阶段 B：下一步应该做

- 用 Gitee API 重建 `smoke_500`
- 做 `1024/2048/4096` 的小规模 A/B
- 选出正式回填参数组合

### 阶段 C：通过后正式回填

- 当前测试口径下，先做 `semantic_chunks` 的 canonical-only 全量回填
- 不急着做 `chapter` 向量
- 不急着做 `evidence_windows` 向量

### 阶段 D：后续拿到更大规模全量数据

- 生产口径切到“每本只取前 25 章”
- 重新做：
  - dedup
  - canonical 筛选
  - semantic chunk 生成
  - 增量回填

这一步是“换索引范围”，不是“推翻路线”。

## 11. 当前最推荐的执行顺序

1. 先做 Gitee API 的质量 A/B 验证
2. 验证通过后，正式采用：
   - `semantic_chunks(800/200)`
   - `1024` 维优先
   - `batch_size=24`
   - `concurrency=12`
3. 先完成 canonical-only 的大规模 chunk 回填
4. 等真实短剧样本和洗稿样本更完整后，再决定要不要补 `chapter` 向量
5. 等未来全量数据到位后，再把索引范围收敛到“每本前 25 章”

## 12. 当前阶段结论

当前最合适的大规模向量化方案，不是“本地全扛”，也不是“所有粒度一起做”，而是：

- 先把 `semantic_chunks` 作为唯一全库语义索引主线
- 用 Gitee API 作为大规模回填候选主路线
- 用 `1024` 维作为第一默认值
- 用 `batch_size=24, concurrency=12` 作为当前默认运行参数
- 在正式切主线前，补一个 `smoke_500` 级别的质量闸门

一句话总结：

- 当前最适合我们的，不是最重的方案，而是“语义 chunk 单线先跑起来，先把大规模回填做稳，再逐步补强”的方案

## 13. 2026-05-02 现状修正

上面这份方案描述的是目标形态，但到 `2026-05-02` 为止，当前实库状态还不是“全量 `semantic_chunks` 已经就绪”，这一点需要单独说明。

### 13.2 如果把当前可用正文按 `800/200` 全量切片，量级大概是多少

按现有 `chapter_contents` 粗估：

也就是说，后续真正的大规模回填目标量级，大约是 `158 万` 条语义 chunk，而不是当前库里这 `26708` 条。

### 13.3 当前推荐顺序需要修正为

当前最合理的执行顺序应改成：

1. 先把 canonical 章节的 `semantic_chunks(800/200)` 扩到当前可用正文范围
2. 再用 `Gitee API + Qdrant` 跑正式 chunk 回填
3. 回填完成后再做更完整的检索压测和长跑验证

### 13.4 回填器当前工程状态

- 脚本：`scripts/backfill_gitee_chunks_v1.py`

这说明回填脚本本身已经具备继续往“百万级 chunk”推进的工程形态，当前主阻塞不在 API 回填器，而在 `semantic_chunks` 全量生成尚未完成。
