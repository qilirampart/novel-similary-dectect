# 封面云端存储方案

更新时间：2026-09-13。当前状态：S1、S2、S3 已完成，S4 生命周期进行中。

## 结论

封面图片不应长期保存在应用发布目录，也不应写入 SQLite。云端正式方案采用“私有 OSS 持久化 + 服务器临时审核缓存 + SQLite 保存元数据和对象键”。本地开发继续使用文件系统后端，业务层只依赖统一的封面存储接口。这样既不会让每次 release 重复携带图片，也不会因发布、回滚或服务器磁盘清理丢失侵权证据。

OSS Bucket 必须保持私有。页面查看证据时，后端先校验用户、工作空间、案件和资产归属，再通过应用服务代理读取 OSS 对象；数据库和前端都不保存永久公开 URL，也不把 OSS 内网地址或签名地址暴露给浏览器。ECS 上优先使用实例 RAM 角色取得自动轮换的临时凭证，避免在代码或环境文件中长期保存 AccessKey。

## 数据流

采集器只负责得到 YouTube 封面地址并保存来源 URL。来源 URL 是外部 CDN 地址，只用于追溯和重新采集，不能代替证据文件。下载阶段把图片写入服务器临时目录，完成最终跳转域名、MIME、尺寸、像素、文件大小和 SHA-256 校验后，以内容哈希作为不可变版本写入 OSS。视觉模型读取这份已经校验且完成留证的相同字节，避免“模型看到的图片”和“系统保存的证据”发生变化；SQLite 仅记录来源 URL、`storage_backend`、`storage_key`、内容哈希、媒体类型、尺寸和大小。

建议对象键采用：

```text
cover-monitor/v1/workspaces/{workspace_key}/videos/{video_id}/{sha256}.{ext}
```

同一视频换封面会产生新的哈希对象，不覆盖旧证据；相同内容重复下载时复用同一对象。`workspace_key` 与 `video_id` 必须经过服务端规则校验，不能直接信任外部路径。OSS 上传成功后才允许数据库把资产标记为可用；数据库写入失败时对象可以由孤儿对象清扫任务回收，不能反过来先删本地文件再尝试上传。

## 保留与清理

风险、待复核、整改前后版本和已进入案件时间线的封面属于证据，不参与普通短周期清理。普通安全封面建议保留 60 天，每个视频至少保留最新版本；下载成功但模型处理失败的封面保留 14 天用于重试；服务器临时审核文件成功处理后立即删除，异常退出遗留文件超过 24 小时清理；导出报告保留 30 天。清理采用先生成清单、再标记、最后删除的流程，并记录操作者、对象键、原因和时间。

OSS 生命周期可按对象前缀或标签执行转低频、归档或删除，但规则加载和执行并非实时。因此案件证据不使用简单的统一到期规则，而应通过业务状态打标签或使用独立前缀保护。确有法务不可篡改要求时，再单独评估 WORM 保留策略，不能直接对整个 Bucket 开启后再发现历史对象无法删除。

## 容量预估

本次真实样本 10 张共约 246 KiB，平均约 24.6 KiB，但不能以这个小样本作为上限。按每张 100 至 300 KiB 估算，11.4 万条视频每个版本约占 11 至 34 GiB；换图历史、失败重试和导出会继续增加占用。OSS 方案可以把容量增长从云服务器系统盘中剥离，并通过生命周期降低长期成本。

## 配置与安全

计划新增以下配置，配置文件只保留占位符，不提交真实密钥：

```text
COVER_MONITOR_STORAGE_BACKEND=local|oss
COVER_MONITOR_ASSET_ROOT=/srv/novel-similarity/shared/cover-assets
COVER_MONITOR_STAGING_ROOT=/srv/novel-similarity/shared/cover-staging
COVER_MONITOR_OSS_ENDPOINT=oss-cn-xxx-internal.aliyuncs.com
COVER_MONITOR_OSS_BUCKET=private-bucket-name
COVER_MONITOR_OSS_PREFIX=cover-monitor/v1
COVER_MONITOR_OSS_ECS_ROLE_NAME=role-name
```

同地域 ECS 优先使用 OSS 内网 Endpoint，减少公网流量和延迟。实例 RAM 角色仅授予指定 Bucket 前缀所需的 `PutObject`、`GetObject`、`HeadObject` 等最小权限；批量删除和生命周期配置权限不授予应用进程，交给独立运维任务。

### S1 完成记录

更新时间：2026-09-12。

新增统一 `CoverAssetStorage` 契约，覆盖不可变内容写入、模型审核临时物化和鉴权后证据交付；本地实现 `LocalCoverAssetStorage` 对对象键进行独立校验，阻止绝对路径、反斜杠和 `..` 越界，写入采用同目录临时文件和原子链接，同一对象键不得覆盖不同内容。下载器保持原来的目录参数兼容，同时支持注入存储后端；执行器优先通过存储后端物化图片，旧测试下载器仍可走兼容路径；证据 API 完成案件归属校验后再调用存储交付接口，并拒绝非 HTTPS 的远程交付地址。

本阶段没有修改数据库 schema，也没有切换正式资产目录。现有云端继续使用 local 后端时行为不变，为 S2 接入私有 OSS 保留了明确边界。

### S2 完成记录

更新时间：2026-09-13。

新增阿里云 OSS SDK V2 适配器和 `OssCoverAssetStorage`。新封面先按现有下载边界完成图片校验，再按 SHA-256 对象键写入临时目录和私有 OSS；已存在对象不重复上传。模型审核或证据查看需要文件时，如果临时副本不存在，会从 OSS 内网下载并重新校验内容哈希；临时副本被截断或篡改时会自动丢弃并从 OSS 恢复，不会把错误字节交给模型或用户。

证据接口保持原有登录、工作空间、案件和资产归属校验，校验通过后由应用服务返回本地物化文件，不向浏览器暴露 OSS 地址。部署依赖已固定在 `requirements-deploy.txt`，`.env.cover.example` 只包含占位符；默认后端仍为 `local`，缺少 OSS 配置不会影响现有环境。真实 SDK `alibabacloud-oss-v2 1.4.0` 的请求结构和方法签名已验证，封面专项回归 `101 passed`，项目全量回归 `228 passed`，Python 编译和 `git diff --check` 通过。

本阶段仍未修改数据库 schema，也未切换云端配置。切换到 OSS 前必须先完成 S3，使历史 local 记录和新 OSS 记录能够同时读取，避免启用全局后端后历史证据失效。

### S3 完成记录

更新时间：2026-09-13。

封面数据库 schema 升至 v7，`cover_assets` 新增受约束的 `storage_backend` 字段。新库直接按 v7 建表，已有数据库在初始化时以增量迁移增加字段，所有历史资产自动得到 `local` 默认值；新下载结果从实际存储实例取得后端名称并随资产元数据落库，非法后端值会在业务层和数据库层同时拒绝。

启用 OSS 时，应用构建以 OSS 为写入端、同时注册 local 与 OSS 的混合存储路由。下载器只向当前活动后端写入；模型读取、失败重试和案件证据查看则依据资产行记录的后端选择文件来源，因此切换后不会把历史 local 对象错误地交给 OSS 查询。来源 URL、最终下载 URL 和内容哈希仍按原契约保留。

相同内容在历史上仅保存于 local、随后成功写入 OSS 时，资产元数据会单向升级为 `oss`，避免数据库唯一键继续指向可能已经丢失的本地文件；后续 local 重放不会把已确认的 OSS 记录降级。验证覆盖 v6 旧库迁移、迁移幂等、新资产后端校验、OSS 活动写入、单向升级、历史 local 模型物化和登录后案件证据读取；封面专项回归 `107 passed`，项目全量回归 `234 passed`，Python 编译和 `git diff --check` 通过。云端配置仍保持 `local`，没有执行生产迁移或对象上传。

### S4 子阶段：持久资产 dry-run 清单

状态：已完成。更新时间：2026-09-13。

新增纯判定模块和 `scripts/plan_cover_asset_cleanup_v1.py`，按分页方式读取资产并输出 UTF-8 CSV，不提供删除或应用参数。判定优先保护案件时间线证据、风险/待复核/未知检测以及每部视频最新资产；其余安全资产超过 60 天、无检测结果资产超过 14 天才列为 `delete_candidate`。时间、后端、大小或保护标志异常时统一保守保留为 `invalid_metadata`，单条坏数据不会让整批证据误删。
