## 本轮试验与结论

本轮还额外试过一个更激进但仍然低风险的想法：在导出专用路径里，把 `result_payload.fine.results` 和 `review_rows` 直接裁到 `top1`，希望进一步降低 Workbook 构建成本。

结论是否定的：

- 首轮测量出现明显波动，导出时间一度升到 `3.7s`
- 复跑后虽然恢复稳定，但均值没有显示出可靠收益
- 这说明这刀至少在当前数据和代码结构下，不值得引入额外复杂度

因此该试验已经回退，没有保留在当前版本中。

## 当前判断

当前常用读路径已经很轻：

- 详情接口稳定在 `10ms` 左右
- 结果列表第一页稳定在 `36ms - 38ms`

复核导出也已经压到约 `2.6s / 500条`。这说明 Web 常规读路径和导出链路目前都已经处在可接受区间，继续在这里深挖的边际收益开始变小。

## 下一步建议

下一步不建议继续在导出链路里做更激进的结构改动，除非后面又出现明确的慢点证据。更合理的方向是切回系统级吞吐问题：

1. 继续分析业务库写放大，统计 batch 执行路径里每条 item 和每个 task 的写次数。
2. 设计最小化写解耦方案，把非实时状态写改成缓冲或聚合刷盘。
3. 在写路径压下来后，再做 `2 workers + item_parallelism=2` 的受控基准，验证多消费者是否能稳定成立。
