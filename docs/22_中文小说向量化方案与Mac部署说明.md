# 中文小说向量化方案与节点部署说明

更新时间：2026-05-02

## 1. 这份文档的定位

这份文档不是再讨论“要不要做向量化”，而是说明：

- 这个项目的向量化到底服务哪条链路
- 当前为什么这样切分
- 当前推荐的节点部署方式是什么
- Windows 本机和 Mac 远程节点各自承担什么角色

## 2. 当前业务里，向量化解决什么问题

当前项目里有两条主线：

- `reuse`
  - 负责抓直接复用
  - 核心看词面证据
- `rewrite`
  - 负责补抓改写 / 洗稿
  - 核心看语义接近

如果只做词面检索，会比较擅长抓：

- 原句照搬
- 长段照搬
- 少量改字但句子结构还在的复用

但遇到下面这种情况就容易漏：

- 字面全改了
- 叙述顺序微调了
- 台词换了
- 但人物关系、事件骨架、剧情推进基本还是同源

向量化的作用，就是把这种“字不一样，但意思还很近”的候选先从大库里粗筛出来，再交给后面的 compare 去做证据确认。

一句话理解：

- 词面链路像“查有没有直接抄句子”
- 语义链路像“查是不是在讲同一个剧情”

## 3. 当前正式方案

当前正式方案是：

- 向量模型：`qwen3-embedding:8b`
- embedding 服务：`Ollama`
- 向量存储：`Qdrant`
- 主数据库：`SQLite`

角色分工：

- `SQLite`
  - 存正文、章节、切片、结构化元数据
- `Qdrant`
  - 存向量索引
- `Ollama`
  - 负责把文本转成向量

所以：

- `Ollama` 不是向量库
- `Qdrant` 不是模型
- `SQLite` 也不是语义检索引擎

三者是分工协作关系。

## 4. 当前为什么先用 `8b`

当前选 `qwen3-embedding:8b`，不是因为它最重，而是因为它在当前机器条件下是一个相对平衡点：

- 中文能力够用
- 语义区分度够做第一版验证
- 本地可部署
- 不必把数据外发

同时当前已经拿到本地实测，不是纸面判断：

- Windows 本机 `Ollama + Qdrant` 已跑通
- `qwen3-embedding:8b` 已能正常返回 `4096` 维中文向量
- 前 `500` 章的 chunk 级向量化和语义评估已经跑过

所以现在不是“理论上可行”，而是“真实闭环已跑通”。

## 5. 为什么不把 `150-300` 字证据窗直接全量向量化

这里要把两种切片分清楚。

### 5.1 证据窗切片

当前证据窗是：

- `200/50`
- 也就是约 `150-300` 字的细粒度窗口

它的用途是：

- 细比对
- 展示证据
- 给人工复核看命中片段

它的优点是细、准、可解释。

但它不适合直接做全库主语义索引，因为：

- 数量太大
- 片段太碎
- 单条上下文不完整
- 容易把向量库做得又大又碎

### 5.2 语义切片

当前语义切片是：

- `800/200`

它的用途是：

- 语义粗召回
- 给 `rewrite` 模式提供更完整的剧情级语义信号

它比 `150-300` 字更适合做向量索引，因为：

- 能装下更完整的上下文
- 更能体现人物关系和事件推进
- 语义稳定性更好

所以当前明确分工是：

- `evidence_windows(200/50)` 继续做细比对证据窗
- `semantic_chunks(800/200)` 负责语义召回

## 6. 当前向量粒度怎么设计

### 6.1 章节向量

章节向量的定位是：

- 作为整章级语义粗召回信号
- 弥补 chunk 视角过细时的漏召回

它的价值已经在这轮验证里体现出来了：

- 加入 chapter 路由后，前 `500` 章评估里漏召回从 `4` 条降到 `3` 条

但当前也要讲清楚边界：

- chapter 向量不是当前第一优先主线
- 当前主要瓶颈在 embedding 吞吐，不在 Qdrant 写入
- chapter 路由有价值，但还要控制融合方式，避免同书相邻章节被过度抬高

所以当前结论是：

- `chapter` 向量路线保留
- 但属于后补增强项，不是当前首要扩量对象

### 6.2 语义 chunk 向量

语义 chunk 是当前主线。

原因很直接：

- 比整章更灵活
- 比证据窗更完整
- 已经能稳定给出有效语义召回

当前最重要的实测结论就是：

- `chunk-only` 能跑通第一版语义能力
- 保守双路融合比纯 chunk-only 更稳
- 真正影响评估结果的关键变量之一，是 query 口径，而不是只有模型本身

## 7. 当前评估层最关键的新结论

当前必须和旧认知切开的一个点是：

- 语义评估不能再用和复用评估同一套短 query

当前已经固定成两套评估口径：

- `reuse`
  - 默认 `120` 字 query
- `semantic`
  - 默认 `300` 字 query

在前 `500` 章、`50` 条样本上：

- 短 query 的双路语义结果：
  - `Hit@1 = 0.84`
  - `MRR = 0.878`
- 长 query 的双路语义结果：
  - `Hit@1 = 0.98`
  - `MRR = 0.99`
  - `missing_target_count = 0`

这说明当前不是“语义链路不行”，而是：

- `120` 字更像查原句
- `300` 字更像查剧情同源

详细解释见：

- `docs/25_复用评估与语义评估双口径说明.md`

## 8. 当前节点部署怎么理解

### 8.1 Windows 本机

当前 Windows 本机已经具备完整可运行能力：

- `Ollama`
  - `http://127.0.0.1:11434`
- `Qdrant`
  - `http://127.0.0.1:6333`
- embedding 模型
  - `qwen3-embedding:8b`

已经完成的事实：

- 本机向量化闭环已跑通
- 本机语义召回闭环已跑通
- 本机 `500` 章中尺度评估已跑通

所以当前默认语义节点，不再是“只能依赖 Mac”，而是：

- Windows 本机已经可以作为当前主验证节点

### 8.2 Mac 远程节点

Mac 仍然有价值，但当前角色要说准确：

- 它是可选远程语义节点
- 适合后续做离线批量向量化
- 适合后续做更稳定的长时间任务

之前之所以强调 Mac，是因为：

- 你不想在本机长期压另一个开发项目
- Mac Studio 的 `M2 / 32GB` 更适合单独跑 embedding 服务

但以当前落地状态看：

- 本机已经能跑
- Mac 是增强部署位，不再是唯一可用位

## 9. 当前性能结论怎么理解

当前已经明确：

- Qdrant 不是主要瓶颈
- 主要瓶颈在 `Ollama + qwen3-embedding:8b` 的 embedding 生成

已拿到的中尺度基线：

- 前 `500` 章
- `2663` 个语义 chunk
- 全量写入 `novel_semantic_chunk_embeddings_smoke_500`
- 总耗时约 `4170s`
- 约 `1.57s / chunk`

这说明什么：

- 当前方案适合做路线验证和中小规模实验
- 但不适合直接在这台 `24G Windows` 机器上硬推几十万章全量向量化

所以当前策略合理顺序是：

1. 先把语义路线验证清楚
2. 先用代表性规模做评估
3. 后续再决定是否切到更强节点做大规模离线向量化

## 10. 当前推荐的运行形态

### 10.1 日常开发验证

建议：

- 继续以 Windows 本机为主
- 便于直接改代码、直接回归、直接跑验证

### 10.2 后续大批量离线向量化

建议：

- 迁到专用节点跑
- 可优先考虑公司那台 `M2 / 32GB Mac Studio`

原因：

- 不会压你本机开发环境
- 更适合挂长任务
- 更适合把 Ollama / Qdrant 稳定常驻

## 11. 当前对外最稳的说法

当前比较稳的表述应该是：

- 文本复用检测主链路已经稳定
- 改写 / 洗稿检测已经接入本地语义召回链路
- 当前语义向量方案采用 `Ollama + qwen3-embedding:8b + Qdrant`
- 证据窗和语义窗已分层：
  - `200/50` 负责证据展示
  - `800/200` 负责语义召回
- 当前 Windows 本机已能跑通完整闭环
- 后续如需更大规模离线向量化，可切到专用语义节点执行

## 12. 当前阶段结论

当前可以正式固定的结论是：

- 向量化是为 `rewrite` 语义链路服务，不是替代 `reuse`
- `150-300` 字证据窗不做全库主语义索引
- 当前主语义索引粒度是 `semantic_chunks(800/200)`
- `chapter` 向量路线保留，但作为后补增强项
- 当前默认 embedding 方案是 `qwen3-embedding:8b`
- 当前 Windows 本机已经能承担主验证角色
- Mac 更适合作为后续专用离线语义节点
