# 批量任务统一队列与排队反馈任务板

## 背景

当前云端运行 2 个自动 worker。短剧字幕批量任务由一个 worker 逐条处理，两个短剧任务同时执行时，最多约有 2 条字幕正在检测；其余任务处于排队状态。现有任务领取在各自任务表中按创建时间排序，但小说批量任务会被 worker 优先领取，短剧字幕任务与小说任务之间没有统一的公平调度视图。前端也没有展示用户前方的等待量和预计开始时间。

短剧字幕实测的常规同语言平均耗时约 3 秒/条。考虑语义检索波动、跨语言翻译回退、数据库写入和外部服务抖动，本轮先以 **5 秒/条/worker** 作为保守 ETA 基准；该基准必须集中配置，并保留后续按近期实际完成记录动态校正的接口。

## 目标

在不改变召回和判定策略的前提下，将两类批量任务纳入稳定、可恢复、可观测的统一 FIFO 调度。用户可看到当前是否已领取、前方还有多少任务与字幕条目、按当前容量估算的开始等待时间和完成时间。暂停、继续、取消、删除、worker 中断恢复均不能留下错误的队列占位或重复执行。

## 调度与 ETA 规则

- 所有可执行任务进入同一逻辑队列，按首次入队时间 FIFO 领取；恢复的已暂停任务按恢复时间重新入队，不插队。
- 领取必须使用单个 SQLite `BEGIN IMMEDIATE` 事务完成“选择下一项 + 标记运行”，确保两个 worker 不会领取同一任务。
- 当前运行中的任务按未完成条目数计入等待工作量；取消、暂停和软删除的任务立即从等待量排除。
- 初始预计开始等待：`(运行中剩余条目 + 前方排队条目) / worker 数 × 5 秒`。
- 初始预计完成时间：预计开始等待加上本任务剩余条目按当前 worker 容量的保守处理时间。前端应标为“约”，不承诺精确秒数。
- 若翻译回退、语义服务降级或外部 API 慢请求导致实际耗时偏离，任务实际进度优先于 ETA；后续可使用近期滑动平均替换固定基准。

## 验收标准

- 2 个 worker 同时领取多个任务时，不重复领取、不遗漏、不因数据库短暂锁等待进入永久阻塞。
- 新旧两类任务按统一 FIFO 排队，不再因调用顺序造成一类任务持续饿死。
- 任务上传后即可获得有效条目数和队列反馈；不必等 worker 解析文件后才显示进度分母。
- 暂停、取消、删除、恢复和 worker 中断恢复后，队列位置与 ETA 在下一次查询中正确更新。
- 任务列表轮询不刷新页面、不跳动；仅更新进度、位置和 ETA。
- 所有既有批量导入、导出、复核、用户隔离与任务控制回归通过。

## 本地验证

- 新增统一调度回归：较早创建的小说任务会先于较晚创建的短剧字幕任务领取；第二个 worker 可同时领取后者。
- 新增 ETA 回归：当前方存在 2 条待处理文本、容量为 2 个 worker、基准为 5 秒/条时，短剧任务预计等待 5 秒。
- 新增短剧 stale-worker 恢复回归：运行任务心跳超时后回到队列，随后可被另一个 worker 重新领取。
- 自动 worker、批量任务、短剧任务存储与统一调度相关测试共 53 项通过；前端 TypeScript 与生产构建通过。
