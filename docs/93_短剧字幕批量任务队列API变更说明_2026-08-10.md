# 短剧字幕批量任务队列 API 变更说明

## 目的

短剧字幕批量检测不再是提交后不可见的后台黑盒。服务端现在会对小说批量任务和短剧字幕批量任务使用统一的 FIFO 领取逻辑，并在任务查询接口中返回当前排队位置、前方工作量和保守的等待预估。YouTube 字幕核验端可据此向用户展示“任务已提交、正在排队或正在检测”的真实状态，而不是只显示静态的“处理中”。

本说明面向 `E:\点众\YouTube字幕核验助手工作区` 的接入改造。上传参数、认证 Cookie、任务控制和检测结果结构保持兼容；本次只新增任务查询响应中的 `task.queue` 对象。当前改造已在本地验证，云端发布前可先完成客户端兼容。

## 调用流程

1. 保持现有登录会话，调用 `POST /api/v1/drama-subtitles/tasks` 上传 CSV、XLSX、TSV 或 TXT。
2. 创建成功后，保留响应中的 `task_id`。创建响应不新增队列字段，仍保持现有结构。
3. 以 `2` 至 `3` 秒间隔轮询 `GET /api/v1/drama-subtitles/tasks/{task_id}`；也可通过 `GET /api/v1/drama-subtitles/tasks` 刷新任务列表。
4. 读取 `task.status` 判断任务生命周期，读取 `task.queue` 展示排队或执行反馈。
5. 只有任务进入终态后停止轮询：`completed`、`partial_failed`、`failed`、`cancelled`、`paused`。

创建响应保持不变：

```json
{
  "task_id": "uuid",
  "status": "queued",
  "source_file_name": "youtube_subtitles.xlsx"
}
```

上传时服务端会立即解析可执行字幕条目数，只统计数量，不在上传请求中执行匹配。因此任务详情初次返回时，`task.counts.accepted` 已可用于展示总进度和排队估算。

## 新增 `task.queue` 字段

`GET /api/v1/drama-subtitles/tasks/{task_id}` 的 `task` 对象，以及任务列表中的每一个 `items[]` 对象，都会附带 `queue`。该对象只提供全局聚合数字，不暴露其他用户的任务名、文件名、文本或账号信息。

排队中的示例：

```json
{
  "task_id": "uuid",
  "status": "queued",
  "counts": {
    "accepted": 26,
    "completed": 0,
    "failed": 0
  },
  "queue": {
    "state": "queued",
    "worker_count": 2,
    "seconds_per_item_baseline": 5.0,
    "queue_position": 2,
    "tasks_ahead_count": 3,
    "queued_tasks_ahead_count": 1,
    "running_task_count": 2,
    "items_ahead_count": 42,
    "remaining_item_count": 26,
    "estimated_wait_seconds": 105,
    "estimated_completion_seconds": 235
  }
}
```

| 字段 | 含义 | 客户端建议 |
| --- | --- | --- |
| `state` | `queued`、`running`、`control_pending` 或 `not_queued`。 | 作为队列展示的主状态。 |
| `worker_count` | 当前服务用于批量任务的 worker 数。当前配置为 `2`。 | 可选展示，不应由客户端自行假设。 |
| `queue_position` | 仅在 `queued` 时存在，表示当前任务在未领取队列中的位置，从 `1` 开始。 | 可展示“排队第 N 位”。不包含正在运行的任务。 |
| `tasks_ahead_count` | 当前运行中的任务加上本任务前方排队任务数。 | 推荐直接展示“前方 N 个任务”。 |
| `items_ahead_count` | 当前运行和前方排队任务尚未完成的字幕条目数。 | 用于补充展示和排查等待原因。 |
| `remaining_item_count` | 本任务尚待处理的字幕条目数。 | 与 `counts` 一起展示进度。 |
| `estimated_wait_seconds` | 预计开始检测前的等待秒数，仅在 `queued` 时存在。 | 需加“约”，例如“预计等待约 2 分钟”。 |
| `estimated_completion_seconds` | 从当前时刻到本任务预计完成的总秒数，仅在 `queued` 时存在。 | 可选展示，不要将其视为 SLA。 |
| `estimated_remaining_seconds` | 仅在 `running` 时存在，表示按基准推算的剩余时间。 | 显示“已开始检测，预计剩余约 N 分钟”。 |
| `seconds_per_item_baseline` | 当前 ETA 基准，初始为 `5.0` 秒/条。 | 仅供说明；实际进度优先。 |

执行中的示例：

```json
{
  "status": "running",
  "counts": {
    "accepted": 26,
    "completed": 8,
    "failed": 0
  },
  "queue": {
    "state": "running",
    "worker_count": 2,
    "seconds_per_item_baseline": 5.0,
    "running_task_count": 2,
    "remaining_item_count": 18,
    "estimated_remaining_seconds": 90
  }
}
```

`not_queued` 表示任务已结束、已暂停或尚未进入可运行状态；此时应以 `task.status` 显示“已完成”“已暂停”“已取消”等终态或控制态，不应显示“排队信息加载中”。

## ETA 口径与边界

当前服务端以 `5 秒/字幕条目/worker` 作为保守基准。此前同语言短剧字幕的实测平均约为 3 秒/条；5 秒额外覆盖了语义检索、翻译回退、SQLite 写入和外部服务波动。

排队等待的计算口径为：

```text
(运行中任务的剩余条目 + 前方排队任务的条目) / 当前 worker 数 × 5 秒
```

该数值是用户反馈，不是精确承诺。跨语言翻译回退、外部语义服务慢请求、暂停/取消、其他任务完成和 worker 重启都会改变真实耗时。因此客户端应始终使用“预计”“约”等文案，并在下一次轮询后直接使用服务端最新值，不能在本地自行倒计时或累加。

## 队列与控制规则

服务端以两类批量任务的 `queue_entered_at` 统一排序，并在单个 SQLite `BEGIN IMMEDIATE` 事务中完成“选择最早任务 + 标记运行”。两个 worker 不会领取同一个任务；小说任务也不会再持续优先于短剧字幕任务。

- 新建任务按创建时刻入队。
- 已暂停任务恢复后按恢复时刻重新入队，不会插队。
- 排队中的任务取消或删除后立即不再计入前方工作量。
- 已运行任务在暂停、取消请求后会完成当前字幕条目，再进入对应状态。
- worker 意外中断且心跳超时后，短剧任务会被恢复为排队、暂停或取消状态，避免永久卡在 `running`。

现有任务控制接口不变：

- `POST /api/v1/drama-subtitles/tasks/{task_id}/pause`
- `POST /api/v1/drama-subtitles/tasks/{task_id}/resume`
- `POST /api/v1/drama-subtitles/tasks/{task_id}/cancel`
- `DELETE /api/v1/drama-subtitles/tasks/{task_id}`

控制请求成功后，客户端应立即刷新任务详情；不应只在本地乐观修改状态。暂停或取消请求未完成时，服务端会返回 `pause_requested` 或 `cancel_requested`，`task.queue.state` 为 `control_pending`。

## YouTube 端展示建议

YouTube 端保留当前“上传后轮询任务详情”的结构即可。建议根据以下优先级生成文案：

| 条件 | 建议文案 |
| --- | --- |
| `status=queued` | `排队中：前方 {tasks_ahead_count} 个任务，预计等待约 {estimated_wait_seconds}`。 |
| `status=running` | `正在检测：已完成 {completed}/{accepted}，预计剩余约 {estimated_remaining_seconds}`。 |
| `status=pause_requested` 或 `cancel_requested` | `正在处理暂停/取消请求，将在当前字幕检测结束后生效。` |
| `status=paused` | `任务已暂停，不占用队列。` |
| `status=completed` | `检测完成。` |
| `status=partial_failed` | `检测完成，部分字幕处理失败，可查看失败明细。` |
| `status=failed` 或 `cancelled` | 展示服务端 `status_message` 或错误信息，并提供重试/重新提交入口。 |

轮询只更新当前任务的状态、进度、队列信息和新结果，不应刷新整个页面或重置用户当前选中的视频、筛选条件和复核上下文。

## 兼容性

- 批量上传字段、Excel/CSV 格式和结果明细字段不变。
- 单条 `compare`、视频级 `video-compare` 接口不进入任务队列，仍为同步调用；不要把它们误展示为后台排队任务。
- `task.queue` 是新增可选对象。客户端应在字段不存在时回退为旧版文案，例如“任务已提交，等待服务端处理”，以兼容尚未发布新版本的环境。
- 最终命中判断仍只读取每条结果的 `result_payload_json.decision`。排队字段只说明执行状态，不改变 `confirmed_match`、`translation_assisted_match`、`potential_match` 和 `no_match` 的业务含义。
