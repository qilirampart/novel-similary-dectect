# 视频级字幕匹配接口接入说明

## 目的

`POST /api/v1/drama-subtitles/video-compare` 是面向 YouTube 等视频采集端的字幕匹配接口。调用端提交一条视频的完整字幕和 cue 时间轴；服务端统一负责快速初筛、cue 对齐分段、补检和提前停止。调用端不再维护 320 至 500 字符的分段规则。

当前服务地址：`http://novel-similarity-dev.dzkjm.cn`。

## 执行策略

1. 服务端以完整 `query_text` 先执行一次混合检索。
2. 若初筛为 `confirmed_match`，或为 `content_matched_ambiguous`，直接返回视频级结论，不执行分段。
3. 若初筛为 `potential_match` 或 `no_match`，服务端按 cues 切为约 320 至 500 字符片段，相邻片段重叠一个 cue。
4. 服务端逐段补检。任一片段出现确认命中或内容强命中但剧名不唯一时，立即停止剩余片段。
5. 所有片段仍未确认时，返回最有价值的待复核结果或未命中结论。

这意味着确认命中视频通常只需一次检索；未确认视频才承担完整分段补检成本。该接口不会改变词法、语义和最终判定标准。

## 认证

先调用 `POST /api/v1/auth/login`，后续请求复用服务端返回的 Cookie。认证方式与现有单条、批量字幕接口一致。

## 请求

```json
{
  "query_text": "该视频前 180 秒的完整字幕文本",
  "language_code": "en",
  "semantic_enabled": true,
  "top_k": 10,
  "window_limit": 200,
  "semantic_window_limit": 100,
  "cues": [
    {
      "start_seconds": 0.0,
      "end_seconds": 2.4,
      "text": "First subtitle cue."
    },
    {
      "start_seconds": 2.4,
      "end_seconds": 5.1,
      "text": "Second subtitle cue."
    }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `query_text` | 是 | 完整字幕文本，用于一次快速初筛。 |
| `cues` | 是 | 原始字幕 cue 列表；每项必须有 `start_seconds`、`end_seconds`、`text`。用于服务端补检分段和时间证据。 |
| `language_code` | 否 | `zh`、`en`、`ja`、`ko`。不传则自动识别。 |
| `semantic_enabled` | 否 | 默认启用同语言语义增强。 |
| `top_k`、`window_limit`、`semantic_window_limit` | 否 | 与现有 `/compare` 接口含义一致。 |

服务端会统一清除 `[music]`、`[applause]` 等方括号舞台标签并压缩空白，用于完整字幕初筛和 cue 分段补检。调用端应继续保留原始 cues 和原始文本作展示、溯源证据，不需要自行维护另一套匹配文本清洗规则。

## 响应

```json
{
  "request_id": "uuid",
  "duration_seconds": 1.24,
  "payload": {
    "video_decision": {
      "matched": false,
      "status": "review_required",
      "outcome": "content_matched_ambiguous",
      "content_match_status": "matched",
      "title_resolution": "ambiguous",
      "user_message": "内容已命中：库内多个剧集均存在大段连续台词复用，系统无法自动确认唯一剧名。",
      "strong_match_candidates": [],
      "decision_scope": "video",
      "decision_source": "fast_screen",
      "matched_segment_order": null,
      "video_reason": "fast_screen_definitive"
    },
    "execution": {
      "strategy": "fast_screen_only",
      "fast_screen_duration_seconds": 1.21,
      "segment_count": 0,
      "processed_segment_count": 0,
      "stopped_early": false,
      "fallback_triggered": false
    },
    "fast_screen": {},
    "segments": []
  }
}
```

当进入补检时，`execution.strategy` 为 `fast_screen_then_segment_fallback`，`segments` 返回每个实际执行片段的 `segment_order`、cue 范围、YouTube 时间范围、耗时、`decision`、语义状态和候选证据。`stopped_early=true` 表示在全部片段执行完前已出现确定性结论。

`video_decision` 复用现有最终判定字段。客户端必须优先读取 `outcome`、`content_match_status`、`title_resolution` 和 `user_message`，不得只根据 `matched` 或候选列表判断。

## YouTube 端迁移

1. 保留字幕采集、语言识别、视频来源和 cue 时间轴。
2. 停止在 `workflow._build_batch_items` 中按字符数创建多个待匹配片段。
3. 每条视频调用一次 `/video-compare`，传完整字幕和 cues。
4. 用 `payload.video_decision` 展示视频级结论。
5. 用 `payload.segments` 展示服务端实际补检过的片段与时间证据；未补检的视频不应显示虚假的分段进度。

既有 `/api/v1/drama-subtitles/compare` 与 `/api/v1/drama-subtitles/tasks` 保持不变，其他接入方可继续使用。视频级接口适合需要“每个视频一个最终结果”的场景。
