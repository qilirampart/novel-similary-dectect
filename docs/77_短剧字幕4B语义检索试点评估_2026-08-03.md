# 短剧字幕 4B 语义检索试点评估

## 结论

Qwen3-Embedding-4B 已在本地短剧字幕链路完成小样本验证。试点证明独立 2560 维 collection、同语言 Qdrant 过滤、字幕窗口聚合和 Gitee API 调用可以稳定闭环；语义层能够找回词级四词短语检索完全没有候选的改写查询。

本轮未启动 309198 窗口全量向量化。当前结论是可以进入更大规模试点，但仍需在更多剧集、更多语言和人工复核样本下确认泛题材误报率，再决定全量回填。

## 实施内容

- 新 collection：drama_subtitle_window_embeddings_qwen3_4b_2560_v1。
- 模型：Qwen3-Embedding-4B。
- 向量维度：2560。
- 向量 payload 新增 language_code 与 language_confidence。
- 短剧语义查询强制在 Qdrant 侧使用 language_code filter。
- 新增语义试点评估脚本：evaluate_drama_subtitle_semantic_pilot_v1.py。
- 评估脚本从已同步窗口中按剧集轮询抽样，用交替字幕行模拟不完整输入，输出 Top1、TopK 和跨语言命中统计。

## 试点数据

- 新 collection 当前点数：811。
- 英文窗口：380，来自 11 部剧。
- 中文窗口：329，中文结构性评估覆盖 14 部剧。
- 韩文窗口：80，韩文结构性评估覆盖 3 部剧。
- 日文窗口：22，当前只覆盖 1 部剧。
- 所有向量均使用新 4B 模型写入；未使用或覆盖小说 8B collection，也未覆盖旧短剧 8B 试点 collection。

## 质量结果

### 同语言过滤

在 collection 同时存在 16 个英文窗口和 1 个中文窗口时，对英文查询请求 17 个候选，Qdrant 只返回 16 个英文窗口。候选 payload 的 language_code 均为 en，跨语言命中数为 0。

### 跨剧结构性评估

对 48 个英文窗口运行交替字幕行片段评估，覆盖 11 部剧：

- Top1 回到正确剧集和集数：48/48，100%。
- Top10 包含正确剧集和集数：48/48，100%。
- 跨语言候选：0。

该评估证明索引、过滤、聚合和元数据链路正确，但不等同于真实侵权准确率，因为查询仍来自已知原文窗口。

中文、韩文、日文复用相同评估方法：

- 中文：48 条、14 部剧，Top1 与 Top10 正确剧集回归率均为 100%，跨语言命中为 0。
- 韩文：48 条、3 部剧，Top1 与 Top10 正确剧集回归率均为 100%，跨语言命中为 0。
- 日文：22 条、1 部剧，Top1 与 Top10 正确剧集回归率均为 100%，跨语言命中为 0。

韩文和日文的剧集覆盖仍偏小，只能证明当前管道在该试点范围内正确，不足以代表更广泛的多语言语义质量。

### 改写增益验证

使用不复用原句的英文改写查询：

“一个男人能看到每个人上方显示的背叛伴侣概率。他原本相信一位善良女性忠诚，但该数值突然快速上升。”

词级四词短语检索结果为 0 个候选。4B 语义检索在跨剧样本中将 I Can See Through Hearts (DUBBED) 第 1 集排为 Top1，语义分数为 0.6372。说明语义层能够补齐词级精确匹配无法覆盖的改写表达。

## 吞吐观察

| 批大小 | 新写入窗口 | 本轮耗时 | 观察 |
| --- | --- | --- | --- |
| 4 | 16 | 约 4 秒 | 首次 collection 创建和初始化混入耗时，不作主结论 |
| 8 | 300 | 约 37 秒 | 约 8.1 窗口/秒，成功率 100% |
| 16 | 64 | 约 13.4 秒 | 约 4.8 窗口/秒，未优于 batch 8 |

当前建议后续扩大试点先使用 batch_size=8。单轮数据不足以说明 API 的长期速率上限，正式全量前仍需观察连续运行时的限流、重试和恢复表现。

## 全量时间与并发判断

可进入语义检索的四种语言窗口共 309138 条，当前已同步 811 条，剩余 308327 条。另有 60 条 unknown 语言窗口；由于查询端无法安全路由其语言，正式全量任务应默认跳过这 60 条，而不是写入可检索 collection。

当前向量化脚本的真实并发为 1：每次向 API 提交一个 batch，等待 embedding 返回、Qdrant upsert 和 SQLite 同步状态提交后，才处理下一批。batch_size=8 表示单次请求携带 8 个窗口，不等于有 8 个并发请求。

按本轮 batch_size=8 的 8.1 窗口/秒最佳观测值，剩余数据理论约需 10.6 小时；按较慢试点和 API 波动估算为 14 至 18 小时。正式全量超过 10000 点后还会出现 HNSW 索引构建与优化开销，因此单并发的计划窗口应按 12 至 20 小时预留。

建议先做 10 分钟并发压测，再考虑将 API 请求并发提升至 2。实现应保持 batch_size=8，并使用“两个 embedding 请求在飞 + 单线程 Qdrant 与 SQLite 写入”的有界队列，避免 SQLite 多写者竞争。若吞吐能稳定提升到 8 至 13 窗口/秒，全量预计约 7 至 11 小时。暂不建议直接升到 3 个以上并发，因为当前使用免费 API，尚未验证其 429 限流、长时间错误率和恢复行为。
