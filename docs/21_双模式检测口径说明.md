# 双模式检测口径说明

更新时间：2026-05-02

## 1. 这份文档讲什么

这份文档只回答一个问题：

- 这个服务为什么要做成 `reuse / rewrite` 双模式

它讲的是产品检测口径，不是评估 query 口径。

如果要看“为什么复用评估和语义评估要分两套 query”，请看：

- `docs/25_复用评估与语义评估双口径说明.md`

## 2. 为什么要做成双模式

最终业务场景里，输入通常是短剧前几集文案、剧情整理稿，或者字幕/梗概类文本。

这类输入大致有两种风险：

### 2.1 直接复用

表现是：

- 原句直接搬
- 长片段连续搬
- 少量改字，但主体措辞没变

这类问题更适合走词面链路，强调“证据硬不硬”。

### 2.2 改写 / 洗稿

表现是：

- 字面变了
- 台词变了
- 叙述方式变了
- 但人物关系、剧情顺序、关键事件还是高度对应

这类问题不能只靠词面检索，需要补语义召回。

所以更合理的产品形态不是“一个总模式包打天下”，而是：

- 默认做 `reuse`
- 按需开启 `rewrite`

## 3. 当前双模式怎么定义

### 3.1 `reuse` 模式

目标：

- 稳定发现原句复用
- 稳定发现长片段复用
- 输出适合人工复核的强文本证据

特点：

- 结果更硬
- 可解释性更强
- 适合作为当前默认模式

### 3.2 `rewrite` 模式

目标：

- 保留 `reuse` 的文本证据能力
- 在此基础上叠加语义召回，补抓改写 / 洗稿风险

特点：

- 候选池更大
- 结果结构更丰富
- 更适合作为附加检测模式

一句话理解：

- `reuse` 是“先查有没有直接抄”
- `rewrite` 是“在查抄的同时，再看有没有换说法复用剧情”

## 4. 当前代码里是怎么落地的

当前 CLI：

- `scripts/run_global_compare_v1.py`

当前参数：

- `--detection-mode reuse`
- `--detection-mode rewrite`

当前预设：

- `reuse`
  - `merged_top_k = 20`
  - `compare_top_k = 10`
  - `top_k = 5`
  - `rewrite_detection_enabled = false`
  - `semantic_recall_enabled = false`
- `rewrite`
  - `merged_top_k = 40`
  - `compare_top_k = 20`
  - `top_k = 10`
  - `rewrite_detection_enabled = true`
  - `semantic_recall_enabled = true`

也就是说，`rewrite` 不是只改一个展示名，而是真的会把语义链路打开，并把候选池放大。

## 5. 当前 `rewrite` 的真实状态

这一点要和旧结论区分开。

以前的 `rewrite` 更像预留结构；现在已经不是纯占位了。

当前状态是：

- `rewrite` 已经正式接入语义召回
- 默认会尝试走“词面召回 + 语义召回”并行合并
- 如果语义侧不可用，会自动回退成仅词面召回

当前代码里已经有这些能力：

- `service/semantic_retrieval.py`
- `scripts/semantic_retrieve_v1.py`
- `scripts/run_global_compare_v1.py`

当前测试里也已经固定了这层行为：

- `tests/test_global_compare_smoke.py`

测试断言里已经允许：

- `semantic_ready`
- `fallback_lexical_only`

这说明当前 `rewrite` 的正确理解应该是：

- 不是“还没接语义”
- 而是“已经接上语义，但允许在语义节点不可用时优雅降级”

## 6. 当前两条检测链路怎么分工

### 6.1 `reuse` 主链路

当前主链路仍然是：

- 词面粗召回
- 候选章节现切
- 细比对打分
- 输出强证据结果

这条链路已经比较稳定，适合做第一层业务输出。

### 6.2 `rewrite` 增强链路

当前增强链路是：

- 保留 `reuse` 全部能力
- 额外做 query 向量化
- 去 chapter / semantic chunk 向量索引里召回
- 将语义候选和词面候选做融合
- 再进入后续 compare 和结果整理

所以 `rewrite` 不是替代 `reuse`，而是在其外面再补一层语义粗召回。

## 7. 为什么这样做是合理的

这样设计有三个直接好处。

### 7.1 默认输出更稳

业务最先要的是“能不能给出清楚证据”。

`reuse` 正好承担这个角色：

- 解释最直接
- 误会最少
- 复核成本最低

### 7.2 语义能力可以渐进增强

`rewrite` 现在已经接上语义，但后面还可以继续增强：

- 调 chunk 策略
- 调 chapter / chunk 融合
- 调 topK
- 调向量模型
- 补更贴近真实短剧文案的评估样本

这些增强都不会推翻 `reuse` 已有输出。

### 7.3 更方便对业务解释

双模式比一个混合分数更容易讲明白：

- `reuse` 告诉你“有硬证据”
- `rewrite` 告诉你“除了硬证据，还帮你补看了一层洗稿风险”

## 8. 现在对外怎么说最稳

当前建议对外统一这样表述：

- `复用检测`
  - 已可用于稳定发现原句复用、长片段复用
- `洗稿检测`
  - 已接入语义召回增强链路
  - 当前作为附加模式使用
  - 后续会继续围绕真实短剧文案样本做增强和校准

这样说的好处是：

- 不会把 `rewrite` 说成“还没做”
- 也不会把当前语义能力夸成“已经完全定型”

## 9. 当前阶段结论

当前可以明确定版的产品口径是：

- 产品上继续保持 `reuse / rewrite` 双模式
- `reuse` 作为默认稳定模式
- `rewrite` 作为语义增强模式
- `rewrite` 当前已接入真实语义链路，不再是纯占位结构
- 后续语义优化应继续在 `rewrite` 模式下推进，而不是回头把两种能力重新揉成一个单模式
