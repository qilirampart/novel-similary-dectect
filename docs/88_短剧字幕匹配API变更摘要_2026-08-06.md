# 短剧字幕匹配 API 变更摘要

本文供字幕采集、视频核验等接入项目使用，说明当前短剧字幕匹配 API 的最终判定、候选展示与覆盖率口径。完整接口清单见 `87_短剧字幕匹配API接入说明_2026-08-05.md`。

当前服务地址：`http://novel-similarity-dev.dzkjm.cn`。

## 接入原则

调用方式未变：单条使用 `POST /api/v1/drama-subtitles/compare`，批量使用 `POST /api/v1/drama-subtitles/tasks` 并轮询 `GET /api/v1/drama-subtitles/tasks/{task_id}`。所有调用均需先通过 `POST /api/v1/auth/login` 登录，并复用服务端返回的 Cookie。

接入方不能把 `candidates` 或 Top1 候选直接视为命中。唯一对外结论是 `payload.decision`。批量任务中，该对象位于每条 `items[].result_payload_json.decision`。

## 最终判定改造

此前仅用 `matched` 表达结论时，存在一个无法准确描述的场景：输入字幕与库内多部剧都有大段连续文本复用，但系统无法安全判断唯一剧名。例如原版和 DUBBED 版、同内容的不同上架标题。现在将“内容是否命中”和“剧名能否唯一确定”拆开表达。

| 字段 | 说明 |
| --- | --- |
| `matched` | 严格的唯一剧名确认标志。只有 `true` 才能写成“确认命中某剧”。 |
| `status` | 技术状态：`matched`、`review_required`、`not_matched`。 |
| `outcome` | 面向用户的业务结果：`confirmed_match`、`content_matched_ambiguous`、`potential_match`、`no_match`。 |
| `content_match_status` | `matched`、`uncertain`、`not_matched`，说明内容层面的证据强度。 |
| `title_resolution` | `unique`、`ambiguous`、`unresolved`、`not_applicable`，说明剧名归属是否明确。 |
| `user_message` | 服务端生成的中文原因文案，应直接展示。 |
| `review_feedback` | `review_required` 时返回的结构化复核反馈，包含 `reason_type`、`title`、`summary`、`recommended_action` 与 `signals`。 |

推荐客户端处理方式：

| 条件 | 用户侧结论 |
| --- | --- |
| `content_match_status=matched` 且 `title_resolution=unique` | 已确认命中，展示唯一剧名、集数与证据。 |
| `content_match_status=matched` 且 `title_resolution=ambiguous` | 内容已命中，剧名待确认。展示全部强证据候选及优先级，不能显示为“未命中”。 |
| `outcome=potential_match` | 发现可疑证据，待人工复核。 |
| `outcome=no_match` | 未命中当前字幕库。 |

`content_matched_ambiguous` 下的 `matched=false` 是刻意的兼容与安全设计：内容层面已发现强证据，但系统不替用户猜测唯一 `book_id`。

待复核结果不能只显示状态。客户端应优先展示 `review_feedback.title`、`review_feedback.summary` 与 `review_feedback.recommended_action`。其中局部连续台词复用会给出共享短语数量、输入覆盖率、候选片段覆盖率和语义相似度；纯语义候选会明确说明缺少连续台词证据；多强证据候选会说明剧名归属不唯一。

## 强证据候选与复核排序

当 `outcome=content_matched_ambiguous` 时，读取 `decision.strong_match_candidates`。数组已经按 `review_priority` 排序，接入方应按原顺序展示，至少展示剧名、集数、累计文本覆盖率和语义相似度。

```json
{
  "matched": false,
  "status": "review_required",
  "outcome": "content_matched_ambiguous",
  "content_match_status": "matched",
  "title_resolution": "ambiguous",
  "reason": "multiple_books_with_strong_lexical_evidence",
  "user_message": "内容已命中：库内多个剧集均存在大段连续台词复用，系统无法自动确认唯一剧名。",
  "strong_match_candidates": [
    {
      "review_priority": 1,
      "book_id": "42000002861",
      "book_name": "Loving Me Was His Game, Losing Me Was Mine",
      "matched_episode_order": 1,
      "aggregate_text_coverage_rate": 0.7788,
      "text_coverage_rate": 0.3641,
      "matched_window_count": 5,
      "evidence_coverage_rate": 0.8876,
      "semantic_score": 0.881516
    },
    {
      "review_priority": 2,
      "book_id": "42000005233",
      "book_name": "Loving Me Was His Game, Losing Me Was Mine (DUBBED)",
      "matched_episode_order": 1,
      "aggregate_text_coverage_rate": 0.7788,
      "text_coverage_rate": 0.3594,
      "matched_window_count": 5,
      "evidence_coverage_rate": 0.8966,
      "semantic_score": 0.893378
    }
  ]
}
```

复核优先级按可解释的连续文本证据排序：先比较 `aggregate_text_coverage_rate`，再比较 `text_coverage_rate`、共享短语数量和证据覆盖率，最后才以 `semantic_score` 作为辅助。语义相似度不能单独作为侵权或确认命中的结论。

## 覆盖率口径

英文词法证据的最小单元是连续四词短语；中文、日文、韩文使用连续字符三元词。两个覆盖率的含义不同，客户端不应混用。

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `aggregate_text_coverage_rate` | 同一候选集全部已召回窗口合并后，对整段输入字幕的覆盖率。 | 用户展示、候选排序、人工复核优先级。 |
| `text_coverage_rate` | 最佳单个证据窗口对整段输入字幕的覆盖率。 | 保持既有兼容；服务端保守判定仍依赖该局部可解释证据。 |
| `evidence_coverage_rate` | 最佳证据窗口自身有多少内容能在输入字幕中找到。 | 判断该局部窗口是否为高重复文本。 |
| `matched_window_count` | 该候选集参与累计覆盖计算的已召回窗口数量。 | 辅助理解累计覆盖来源。 |

例如三分钟输入字幕有 1,140 字符，最佳命中窗口约 460 字符时，`text_coverage_rate` 约为 36% 是正常现象；若同集命中 5 个窗口，`aggregate_text_coverage_rate` 可以达到 77.88%。这不改变最终判定阈值，只让展示的覆盖口径更符合人工复核需求。

历史批量任务的 `result_payload_json` 可能早于累计覆盖字段上线。接入方若缺少 `aggregate_text_coverage_rate`，应显示“历史任务未计算”，不要用 `text_coverage_rate` 冒充累计覆盖；重新执行检测后会生成完整字段。

服务端会统一移除 `[music]`、`[applause]` 等不超过 80 字符的方括号舞台标签，并压缩空白后再执行词法和语义检索。接入方可以上传原始字幕，不需要自行删除这些标签；这样单条、批量和视频级接口会使用相同的匹配文本口径。

## 性能与接入建议

累计覆盖不是多次检测：每条输入仍只执行一次词法检索和一次可选语义检索，不增加 Qdrant 查询或外部 Embedding API 调用。服务端只对最终返回候选涉及的窗口合并统计，真实 1,651 字符和 1,140 字符样本相对旧单窗口统计的中位耗时变化分别为 -0.93% 与 +0.74%，可视为无显著额外开销。

批量接入建议保留每个视频的 `source_video_id`、时间范围、字幕语言和原始文本。客户端可按视频聚合：只要有一个片段为 `confirmed_match`，视频级可标为确认命中；只有 `content_matched_ambiguous` 或 `potential_match` 时，应标为待人工复核，并将强证据候选、时间证据和来源信息一并提供给复核界面。

需要展示更完整的原剧台词时，可按候选的 `evidence_window_uid` 调用：

`GET /api/v1/drama-subtitles/evidence-context/{window_uid}?context_chars=2400&before_lines=6`

该接口只读取字幕上下文，不会重新触发召回或语义检索。
