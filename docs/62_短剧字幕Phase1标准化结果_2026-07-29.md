## 本轮口径

本轮不是把所有原始 payload 都直接入库，而是按短剧字幕匹配的实际目标做了一层收敛：

- 原始 JSON 继续保留在 `data_samples/middle_platform_subtitles_20260722_full/raw_books`
- 匹配语料层只保留前 `10` 集
- 只有前 `10` 集里存在可用字幕文本的短剧，才进入本轮结构化库
- 结构化层拆成三层：`drama_books`、`drama_episodes`、`drama_subtitle_lines`

这里的“可用字幕文本”指字幕项中存在可落盘、可参与后续匹配的正文文本，而不是只有空壳字段。

## 为什么不是 7128 本

前面的采集阶段结论是“全剧范围内有真实字幕”的短剧共有 `7128` 本，而本轮 phase 1 最终入库的是 `7108` 本，少了 `20` 本。

这个差值来自本轮的新口径，而不是数据丢失：

- 采集阶段统计的是“全剧范围内是否存在真实字幕”
- 本轮 phase 1 统计的是“前 `10` 集内是否存在可用于匹配的字幕文本”

因此，这 `20` 本大概率属于“全剧后续集数里有字幕，但前 `10` 集没有可用文本”的情况，在当前短剧匹配方案下被有意排除。这是符合当前设计目标的，不是抽取异常。

## 当前库的意义

这套库还不是最终匹配库，而是短剧字幕链路的标准化基础层。它已经完成了三件事：

1. 把原始中台 JSON 转成稳定、可复用、可增量重建的结构化表
2. 把后续匹配真正要用的范围，提前收敛到“前 10 集 + 可用字幕文本”
3. 为下一步“字幕窗口化”和“短剧字幕检索”准备了干净输入
