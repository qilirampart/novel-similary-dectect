# 小说库数据对接会议准备：基础讲解、发言提纲与问题清单

更新时间：2026-04-21

## 1. 文档用途

这份文档用于今天下午和数据侧、技术侧、业务侧开会前做统一准备。

目标不是直接拍板所有技术细节，而是先把三件事讲清楚：

- 这个服务到底要做什么
- `RAG / 向量化 / embedding` 在这个项目里分别是什么角色
- 这次会议最需要确认哪些数据问题

## 2. 一句话结论

本项目不是先做一个“会回答问题的 RAG 系统”，而是先做一个“字幕对小说库的检索比对服务”。

主链路应该是：

`字幕输入 -> 候选召回 -> 细比对 -> 证据输出 -> 人工复核`

其中：

- 数据结构是否规范，比“向量模型选哪个”更重要
- 章节级结构化数据，比整本混合文本更适合长期方案
- 向量检索只适合作为补召回，不适合作为最终定案依据

## 3. 先把这个服务讲清楚

### 3.1 这个服务本质上在做什么

可以把这个服务理解成一个“图书馆检索员 + 证据整理员”。

它要做的事情不是直接判断侵权，而是：

- 接收桌面工具产出的字幕文本和字幕分段
- 在公司小说库里快速找出高可疑候选
- 继续把候选缩小到具体书、具体章节、具体片段
- 输出“视频哪几秒字幕”对应“小说哪一段文本”的证据
- 把结果留给法务或业务同事人工复核

更生活化一点的例子：

- 桌面工具像录音整理员，先把视频里的台词整理成字幕
- 这个新服务像档案室检索员，去十几万本小说里找最像的内容
- 法务同事像最后拍板的人，系统只负责把可疑证据摆出来

### 3.2 它为什么不是一个普通功能页

因为这件事和桌面工具原来的工作方式不一样：

- 桌面工具更像单机工作台，处理单条视频
- 小说比对服务更像后端检索系统，要长期维护大量文本数据和索引
- 两者的部署、数据规模、任务模式、责任边界都不同

所以它更适合做成独立服务，而不是继续塞进桌面工具主仓。

## 4. 用人话理解 RAG、向量化和 embedding

### 4.1 什么是 RAG

`RAG` 可以先简单理解成：

“先查资料，再根据资料回答问题。”

例如：

- 你问“公司报销标准是什么”
- 系统先去知识库里找制度文档
- 再把查到的内容喂给大模型
- 最后大模型给你一段整理后的答案

这就是典型的 `RAG`。

### 4.2 为什么这个项目不能简单等同于 RAG

因为这个项目的核心不是“生成答案”，而是“找候选 + 给证据”。

这里更像：

- 先查档案，找到最像的书和章节
- 再把具体命中的原文和字幕对应出来
- 最后让人去看证据，而不是让模型帮忙下结论

所以这个项目更像“检索比对系统”，不是“问答系统”。

### 4.3 什么是 embedding / 向量化

可以把 `embedding` 理解成：

“把一段文字变成一串数字坐标，让机器能拿这些数字去比较文本之间的语义距离。”

生活中的类比：

- 地图上的每个地点都有坐标
- 两个地点越近，说明它们在地图上越接近
- 文本向量也是类似概念
- 两段话在向量空间里越近，通常说明它们的意思越接近

例如：

- “他非常生气”
- “他气得发抖”

这两句话字面不一样，但意思接近，所以向量可能会比较近。

### 4.4 向量检索在这个项目里能做什么

向量检索适合做：

- 找“意思像”的候选
- 补充发现那些字面改写比较多的内容
- 在粗召回阶段多给一些可疑样本

### 4.5 向量检索在这个项目里不适合做什么

向量检索不适合直接做最终结论，因为：

- 它擅长找“像不像”
- 但不天然擅长给出“具体哪一句对应哪一句”
- 法务和版权流程最终需要的是具体证据片段

所以更稳妥的理解是：

- 向量负责“帮忙找嫌疑人”
- 细比对负责“把证据翻出来”
- 人工复核负责“最后拍板”

## 5. 这个服务第一版应该怎么搭

先不要把系统想得过重，第一版可以按下面几层理解。

### 5.1 原始数据层

职责：

- 原样接收公司侧交付的数据
- 保留原始字段和原始文件
- 方便后续追溯和排查

可以把它理解成“档案室原件柜”。

### 5.2 标准化清洗层

职责：

- 去广告、去声明、去异常空白
- 统一标点和数字格式
- 保留章节边界
- 输出统一标准字段

可以把它理解成“整理车间”。

### 5.3 检索召回层

职责：

- 把章节或片段做成可快速搜索的索引
- 收到字幕后先从全库里找出少量高可疑候选

可以把它理解成“图书馆目录柜”。

### 5.4 细比对层

职责：

- 对召回出来的候选做进一步比对
- 找到最可能命中的章节和片段
- 给出覆盖率、命中次数、命中文本

可以把它理解成“二次筛查台”。

### 5.5 证据输出与复核层

职责：

- 输出字幕命中时间范围
- 输出小说命中文本片段
- 记录人工复核结论

可以把它理解成“办案材料整理区”。

## 6. 为什么当前主线不应该是“直接上向量库”

因为这个项目当前真正的关键点是数据契约，不是模型炫技。

如果公司侧暂时只能提供：

- 一堆零散 `txt/docx/pdf`
- 没有稳定 `book_id`
- 没有稳定 `chapter_id`
- 只有整本正文，没有章节结构

那后面会出现这些问题：

- 很难做长期增量同步
- 很难稳定回溯到具体书和具体章节
- 很难把历史复核结果和当前数据版本对应起来
- 很难产出稳定、可解释的证据输出

所以这次会议最重要的事，不是争论“要不要 RAG”，而是先确认：

- 数据从哪里来
- 是否有稳定主键
- 是否按章节组织
- 是否支持增量同步

## 7. 下午会议发言提纲

以下内容可以按会议中的自然表达去说，不需要逐字照读。

### 7.1 开场对齐

建议表达：

“这次我们不是先讨论一个大而全的 AI 系统，而是先对齐小说库数据怎么接进来，保证后面字幕比对链路能落地。当前上游字幕生产链路已经比较明确，今天更想确认的是小说库侧的数据形态、主键、粒度和同步方式。”

### 7.2 说明当前已有能力

建议表达：

“桌面工具这边已经能完成视频采集、下载、音频提取、ASR 和字幕导出。也就是说，字幕文本和时间轴结果已经能提供出来。下一步缺的是把这些字幕结果和小说库做稳定比对的能力。”

### 7.3 说明新服务的核心职责

建议表达：

“新服务主要负责四件事：第一是接小说库数据，第二是做清洗和标准化，第三是做候选召回和细比对，第四是输出证据片段和复核结果。它不是一个聊天型 RAG 系统，更像一个检索比对服务。”

### 7.4 说明为什么当前最重要的是数据结构

建议表达：

“现在最关键的不是先选模型或者先选向量库，而是先确认公司能不能给到结构化、可持续的数据。如果能按书表加章节表来给，并且有稳定 `book_id` 和 `chapter_id`，后面的系统建设会顺很多。反过来，如果只有零散文件或者没有稳定主键，后面索引、证据、增量同步都会比较痛苦。”

### 7.5 说明当前技术路线

建议表达：

“当前更稳妥的路线还是分层做：先做粗召回，再做细比对，最后输出证据。向量能力后面可以加，但主要是补召回，用来找那些意思接近但字面改写较多的内容，不直接作为最终结论。”

### 7.6 说明当前希望达成的会议结果

建议表达：

“今天如果能把数据来源、最低字段集、章节粒度、样本交付方式、后续是否增量同步这几件事对齐下来，后面我们就可以先拿样本库做验证，不需要一开始就上全量。”

## 8. 会议中可直接抛出的重点问题清单

建议优先围绕数据对接问，不要先陷入模型细节。

### 8.1 数据来源

- 小说正文当前存放在哪个系统里？
- 是业务库、数仓、对象存储、文件服务器，还是其他系统？
- 当前这份数据由哪个团队维护？
- 后续谁能作为稳定对接人？

### 8.2 数据粒度

- 数据当前是按整本存，还是按章节存？
- 如果是整本存，是否能拆出稳定章节结构？
- 是否已经存在章节序号和章节标题？
- 有没有缺章、重复章、空章节这类情况？

### 8.3 主键与字段

- 是否存在稳定的 `book_id`？
- 是否存在稳定的 `chapter_id`？
- 如果没有 `chapter_id`，是否能稳定生成？
- 最低是否能给到 `book_id + book_name + chapter_id + chapter_index + chapter_title + content + updated_at`？
- `updated_at` 表示的是内容更新时间、上线时间，还是别的时间？

### 8.4 数据版本与业务含义

- 当前拿到的是线上最终发布版本，还是原始书稿版本？
- 如果正文后续被修订，旧版本是否还能追溯？
- 是否存在多版本并存或内容回滚的情况？
- 是否存在书名别名、作者别名、渠道别名？

### 8.5 交付方式

- 首次交付最可能是什么形式？
- 是 `CSV`、`XLSX`、`Parquet`、只读库、对象存储，还是共享盘文件？
- 后续交付是人工导出还是系统化同步？
- 单次交付预计的数据量有多大？

### 8.6 增量同步

- 这批数据是一锤子全量给数，还是后续需要按日增量同步？
- 如果做增量，增量依据是什么？
- 是按 `updated_at` 同步，还是按业务变更表同步？
- 删除、下架、合并章节这类操作怎么体现？

### 8.7 数据质量

- 正文里是否常见广告、渠道声明、版权说明、水印文字？
- 简繁体是否混用？
- 标点、空白、章节格式是否统一？
- 是否存在 HTML 标签、富文本残留、异常换行？

### 8.8 权限与合规

- 这批数据的访问权限边界是什么？
- 是否能落本地样本做验证？
- 是否涉及脱敏、审计或访问留痕要求？
- 样本库是否可以用于内部算法测试和调试？

### 8.9 样本验证

- 能否先给一批 `500-2000` 本的样本库做验证？
- 样本是否能覆盖不同题材、不同长度、不同更新状态？
- 是否能给几组已知改编关系的样本，方便验证召回效果？

## 9. 会议中需要避免跑偏的点

- 不要把会议开成“先选哪个 embedding 模型”
- 不要把重点放在“要不要直接做 RAG 问答”
- 不要默认对方一定能给规范章节数据
- 不要一开始就承诺全量十几万本直接上线
- 不要把“语义相似”直接等同于“法律结论”

## 10. 建议的会议收口方式

会议最后最好收成一份明确结论，而不是停留在方向讨论。

建议争取确认以下输出：

- 数据来源系统
- 对接团队和责任人
- 最低字段集
- 样本交付格式
- 是否存在稳定 `book_id` / `chapter_id`
- 是否支持后续增量同步
- 首批样本交付时间

## 11. 可直接复述的总结口径

“我们当前要做的不是一个泛化的 RAG 问答系统，而是一条字幕对小说库的检索比对链路。短期目标是先把结构化数据接进来，跑通样本库的候选召回、细比对和证据输出。向量能力后面可以补，但它主要负责扩大候选范围，不直接作为最终证据依据。今天这次会议最关键的是先把数据粒度、主键、字段和交付方式对齐。”
