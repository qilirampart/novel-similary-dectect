# 项目分享复盘：从短剧采集到小说相似度复核的闭环

更新时间：2026-06-04

这次分享我更想讲清楚两件事。

第一，我们最后做出来的并不只是一个“文本相似度比对页面”，而是一条从短剧线索进入、到人工复核结束的完整工作流。第二，这个项目中途最难的部分，很多时候也不是算法本身，而是数据理解、链路稳定性和真实业务使用方式。

如果用一句话概括当前成果，可以这样说：现在已经能从短剧作者主页出发，完成素材采集、台词转写、批量检测、人工复核和结果导出，形成一条可重复执行的内部闭环；当前真正限制继续扩大的，主要已经不是功能能不能跑，而是源数据覆盖够不够。

## 一、项目现在到底在做什么

项目的目标很直接，就是把短剧台词或文案，和已有小说库做相似度比对，帮助筛出高风险疑似改编或复用内容。为了让这件事能真的落地，我们没有把它做成一个单点脚本，而是拆成了两段能力。

前一段是采集侧，也就是素材分析助手。它负责从抖音主页或分享链接拿到短剧视频，完成下载、音频提取、ASR 转写，再把结果导出成结构化 Excel。后一段是检测侧，也就是小说相似度比对系统。它负责接收 Excel、拆成批量任务、做候选召回、做证据级比对、沉淀复核状态，并导出最终结果。

这两段串起来之后，业务上就不是“找到一段台词，手动丢进脚本里试一下”，而是“拿到一个作者主页，跑出一批待复核结果，再把能用的证据导出来”。

## 二、全链路现在是怎么跑通的

当前最典型的入口，是一条待排查作者的抖音主页链接。先由采集软件批量提取主页下可处理的短剧视频链接，再完成视频下载、音频抽取和语音识别。我们现在重点使用的是短剧首集内容，因为首集最容易暴露核心剧情设定、人物关系和关键冲突，也最适合拿来和小说原著建立第一轮证据关系。

转写完成后，采集软件会导出一份结构化 Excel。这个表里不只是字幕文本，还会保留短剧名、集数、作者、平台、分享链接、展示标题等溯源字段。这样做的价值很实际，后面进入检测和复核环节时，不会只剩下一段孤立文本，而是能知道这段文本具体来自哪部短剧、哪一集、哪个作者、哪条原始链接。

检测系统接到这份 Excel 后，会自动识别字段并拆成批量任务。主链路不是单靠一种检索方式，而是“词法粗召回 + 证据级精排 + 语义补召回”。词法层先用 FTS5 章节索引把候选范围拉出来，精排层再用 `200/50` 证据窗口做细比对，给出真正能落到文本片段上的证据分数；如果开启改写检测，则会在原有链路上叠加 `800/200` 语义切片的向量补召回，语义索引落在 Qdrant，中间用的是 `Qwen3-Embedding-8B` 1024 维向量。

最后进入复核页。现在复核页已经不是单纯看“命中了哪本书”，而是把短剧名、集数、作者、查询台词、命中小说、候选片段、分数、处理状态和导出动作放到同一个工作台里。复核后，还可以按“确认高风险”“继续跟进”“标记误报”等状态导出结果，方便后续继续跟进。

## 三、项目里真正卡过的点，以及最后怎么解决

### 1. 一开始最难的不是召回，而是对“中台可查”的理解有偏差

项目前期有一个一直绕不过去的问题，就是有一批线索表里的数据明明标了“中台可查”，但我们在现有数据里就是查不到。最开始很容易把这件事理解成：另一边有一套我们没拿到的数据，所以他们能查，我们不能查。

后来和法务侧进一步对齐后，情况才变清楚。那个“中台可查”标记，并不等于另一边已经有一套稳定自动检出的强系统，很多结果其实是通过现有小说软件或数据中台人工搜索台词确认出来的。另一边当前本身也主要还是在同样的短篇数据范围内做排查，100 条数据大约要 5 小时，实际也只查到了几十本小说。

这一步非常关键，因为它把问题从“是不是我们系统能力不行”拉回到了“我们对业务标签理解错了”。后面又对那 740 条数据做了源表级复核，最终确认它们确实不在当前两份源数据表覆盖范围内。也就是说，真正的瓶颈不是导入漏了，而是底层数据还不够全。

### 2. 有些“未召回”并不是真没召回，而是上游数据书名和正文错位

后面在做 26 条真实样本复测时，还遇到过另一类更隐蔽的问题：数据库里能找到同名书，但实际正文内容和书名根本对不上。这种情况下，前台看上去像“系统没把正确小说召回出来”，但继续往下查会发现，问题并不在召回逻辑，而是在上游数据质量。

这类问题最后的处理方式不是继续硬调阈值，也不是盲目改算法，而是把它单独归类成“源数据内容错位”。这样做的好处是，我们终于把真正该优化的部分和根本不该由召回系统背锅的部分分开了。否则后面很容易在错误方向上反复花时间。

### 3. 语义检测看起来“失效”，根因很多时候只是依赖服务没起来

项目做了语义补召回后，最早有过几次看起来像“改写检测失效”或者“结果突然变差”的情况。后来排查发现，其中一类根因很朴素，就是 Qdrant 没起来，或者部署环境前后端版本不同步，导致系统实际上回退成了词法链路。

这个问题后面是从三个层面收口的。第一，把 Qdrant 的位置、启动方式和依赖关系明确记录下来，避免每次重启机器都靠猜。第二，前后端都显式暴露语义状态，能让人一眼看出当前是 `semantic_ready` 还是 `fallback_lexical_only`。第三，允许系统在语义侧不可用时自动降级，但不能静默降级到用户完全无感。这样既保住了可用性，也保住了判断依据。

### 4. 批量任务早期能跑，但一上量就暴露出吞吐和交互问题

单条检测阶段，很多问题并不明显；真正把任务量提到 500 条以后，问题一下子就都出来了。最早版本基本是严格串行执行，整批 500 条在语义正常时大约要 24 分 27 秒。速度不是唯一问题，另一个更糟糕的点是，前端进度体验也很差，用户经常看到的只有 0% 和 100%，中间过程不清晰。

后来没有靠砍召回口径换速度，而是改执行策略。批量执行器做成了更保守的任务内并发，默认 2 槽并发；同时补了 ETA、单条耗时、实时进度刷新和任务看板。这样之后，500 条批量任务的墙钟时间压到了 16 分 27 秒，降幅大约 32.72%，而语义状态仍然保持 `500/500 semantic_ready`。这一步很重要，因为它说明吞吐提升不是拿准确性换来的。

### 5. 复核页最初更像结果列表，不像真正的复核工作台

复核页前期也踩过很多坑。最早的问题不是功能没有，而是页面根本不适合做长时间复核。证据文本太短，查询文本和候选文本长度不一致，很多空间被辅助信息占掉，真正该看的对比区域反而小；再加上不同屏幕比例下排版容易变形，一旦到别人电脑上打开，核心对比区甚至会被挤到下方。

这一轮后面做了几件比较关键的调整。第一，证据文本改成长上下文展示，不再只给一个短摘要。第二，复核区、队列区和详情区重新做了固定高度和对齐，减少页面空洞和布局漂移。第三，按任务作用域筛复核结果，支持单任务复核，不再把所有历史结果混在一起。第四，复核结果默认按分数降序，并加展示阈值，但底层仍然保留完整结果，避免前端把低分结果直接吃掉。这样之后，复核页才真正从“能看结果”变成了“能舒服地做判断”。

### 6. 复核加载慢，不是因为算法慢，而是前后端请求方式不对

后来还有一个很典型的问题：检测本身挺快，但一跳到复核页却很慢。这件事最开始容易让人怀疑是后台整体慢了，但真查下来，问题主要出在页面进入时拉得太多，尤其是在证据上下文变长之后，如果还是按全量思路取数据，前端首屏就会明显变重。

后面的解法也比较直接，就是把“证据展示更长”和“页面请求更轻”同时做。结果详情改成长文本没问题，但请求必须走分页、走范围、走按需加载，不能一口气全取。同时，批量页轮询也做了修正，避免一个正在运行的大任务被反复全量请求，把单进程 API 压住。这个问题修完之后，系统整体的体感才真正稳定下来。

### 7. 云端问题很多时候不是功能没写，而是前后端版本没同步

项目上云之后，又暴露出另一类问题。比如云端一度出现过“前端已经有暂停按钮，但点了没反应”，或者“任务显示取消中，但一直卡着不动”。这种问题如果只看页面，很容易判断成“功能坏了”，但实际根因往往是部署不一致，前端已经更新，后台接口却还没跟上，或者发布时正好把运行中的任务中断了。

这类问题后面做了两层修复。一层是发布流程上更强调前后端成套同步，尤其是涉及任务状态机的接口，不允许只发页面不发后台。另一层是后台加了中断任务恢复逻辑。这样即使服务重启时任务正跑到一半，也能把 `running`、`pause_requested`、`cancel_requested` 这些状态重新修复回可继续处理或可正确收尾的状态，而不是留下“假卡死”任务。

### 8. 采集表和检测表最初并不是天然对得上的

从业务角度看，真正要做成闭环，最关键的一步其实是采集软件导出的 Excel 能不能被检测系统直接吃进去。这个问题看起来像小事，实际上很容易变成长期手工清洗的入口。一旦字段不统一，后面就会一直靠人去搬运和修表。

所以后面专门做了一轮 Excel 适配，把采集软件导出的剧名、集数、作者、链接、台词文本这些字段和检测系统导入逻辑对齐。这样现在已经可以做到：采集侧导出的表，检测侧直接导入就能跑，不需要额外写临时转换脚本。这个改动本身不炫技，但它决定了整条链路到底是不是工程化的。

### 9. 采集端最早更像单机工具，不像能稳定跑批的前置工作台

如果只盯着检测系统，很容易忽略前面还有一个更早的瓶颈，就是采集软件自己能不能稳。最初采集端在小批量手工处理中没太大问题，但一旦开始连着下载、转写、导出，马上就会暴露出批任务状态不清、暂停语义不完整、重启后恢复能力弱这些问题。对真实业务来说，这种问题很致命，因为前面的数据准备一旦断掉，后面的检测链路就根本接不上。

后面在采集侧也补了一轮任务化改造，包括批任务面板、暂停和继续、阶段级落盘、重启恢复、实时日志心跳，以及大列表场景下的局部刷新优化。这样现在采集侧不再只是“能把视频转成文字”，而是已经更接近一个可持续跑批的前置工作台。

### 10. 采集链路里，ASR 不是锦上添花，而是稳定性的硬依赖

全链路能不能成立，一个很现实的前提是台词文本得先拿到。早期如果只依赖单一 ASR 通道，一旦服务波动，就会直接卡住整批任务。这个问题不算复杂，但如果不提前补，就会在业务现场反复出问题。

所以采集侧后面做成了多 Provider 结构，至少保留腾讯 ASR 和豆包 ASR 两条通道，并加了优先级、失败熔断和自动切换。这样做的意义不在于“模型更高级”，而在于前置转写这一步终于不再是单点风险。对整条闭环来说，这种稳定性比局部多提几个点的识别效果更重要。

## 四、现在这套系统到了什么阶段

如果只看功能，当前已经不是原型状态，而是可以支撑真实业务试跑的阶段。现有测试基线覆盖约 55.6 万章正文，累计约 8.95 亿字；正式语义索引已经完成 1,580,083 条 canonical semantic chunk 的向量化回填；在当前配置下，单条检测基本稳定在约 3 秒。

从验证样本看，当前已正式确认 77 条“中台可查且数据库已有”的有效样本，其中 26 条保留了可直接实测的真实台词。这 26 条现在仍然是最适合做系统效果验证和方案展示的一批核心样本。与此同时，还有 740 条虽然在线索表中被标成“中台可查”，但并不在现有源数据覆盖范围内。这组数字其实已经很说明问题了：系统主链路已经能跑，接下来最大的增量空间，取决于还能不能拿到更多对得上的小说源数据。

从能力形态看，现在也已经具备了几项真正能让人用起来的东西。批量任务支持进度、暂停、继续、删除和恢复；复核页支持长证据、任务作用域和状态导出；结果可以按处理结论导成结构化表格；云端也已经有可访问的隔离预览环境。换句话说，这套系统现在最大的价值，不是“某个算法分数更高了一点”，而是它已经能把采集、检测、复核、导出这几个原本散开的动作串成一条业务闭环。

## 五、这次复盘后，我对后续工作的判断

第一，后面如果要继续推进，重点不应该再放在反复重写已有链路上。词法粗召回、证据精排、语义补召回、批量执行、复核导出这些骨架已经搭起来了，继续大改主链的性价比不高。

第二，下一阶段最值得投入的地方，还是数据。因为现在已经很清楚，很多表面上的“系统查不到”，最后追根溯源都落回了两件事：一是源数据根本没有，二是源数据内容错位。如果上游数据质量和覆盖范围不继续补，后面系统能力再往上抬，也会遇到明显上限。

第三，从工程角度看，这个项目最有价值的不是某一个页面，而是已经把整条流程打通了。现在已经可以从抖音主页进，到 Excel 出，再到检测、复核、结果导出收口。这意味着后面不管是继续扩数据、补更多平台，还是继续做更稳定的任务调度，都是在一套已经成立的骨架上往前加，而不是再从零搭一遍。

## 六、如果明天只做一个简短分享，可以这样讲

可以先用一句话开场：我们现在已经不只是做了一个小说相似度比对页面，而是把“短剧采集 -> 台词转写 -> 批量检测 -> 人工复核 -> 结果导出”这条链路真正串起来了。

接着讲两个最关键的认知变化。第一，之前一直以为那 740 条“中台可查”是因为另一边有更全的数据，后来确认不是，核心还是现有源数据覆盖不足。第二，很多看上去像算法问题的现象，最后查出来其实是上游数据质量、依赖服务状态或者批量运行机制的问题。

最后落在现状上：现在系统主链路已经跑通，现有数据量下基本能做到约 3 秒一条，500 条批量任务也已经完成一轮不牺牲语义召回的提速；下一阶段真正限制继续扩大的，主要是源数据能不能继续补齐。
