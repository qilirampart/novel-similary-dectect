# 两条未召回样本根因排查结论

更新时间：2026-05-07

## 1. 结论先说

这次用户关注的 3 条样本里，只有 2 条属于“真未召回”：

- `丧尸末日，女友为等竹马拦我生路`
- `他与春风皆过客`

另一条：

- `产房外，婆婆逼我给小叔子凑彩礼`

并不是漏召回，而是已经在 `rewrite` 链路里召回到了目标书，当前复跑结果是 `rewrite_expected_rank=2`。

这 2 条真未召回样本，当前更接近“目标书正文内容与样本台词不是同一版本/同一剧情”，而不是“语义召回链路挂了”。

## 2. 已确认不是环境问题

- 当前默认语义链路已经统一到本机：
  - API：`127.0.0.1:8001`
  - Qdrant：`127.0.0.1:6333`
  - embedding：`Gitee Embedding API`
  - model：`Qwen3-Embedding-8B`
  - chunk collection：`novel_semantic_chunk_embeddings_qwen3_8b_1024_v1`
- `rewrite` 复跑状态正常，可进入 `semantic_ready`
- 本机 Qdrant collection 正常存在

## 3. 已确认不是“目标书没入库”

这两本书都能在 SQLite 库里找到：

- `丧尸末日，女友为等竹马拦我生路`
  - `book_ext_id=11010352605`
  - `chapter_count=26`
- `他与春风皆过客`
  - `book_ext_id=11010284708`
  - `chapter_count=22`

同时也能确认：

- 这两本书的 chunk 向量已经入 Qdrant
- 原始下载目录存在：
  - `raw/batch_20260428_online_owned/txt/11010352605`
  - `raw/batch_20260428_online_owned/txt/11010284708`
- `manifest.csv` 里的 `book_ext_id / chapter_ext_id / txt 路径` 映射是完整的

所以不是“书没进库”或者“向量没建出来”。

## 4. 已确认不是“chapter first 压掉了正确结果”

做过 `chunk-only` 复跑后，这两条样本仍然找不到目标书。

这说明问题不在于：

- `chapter` 召回把正确结果压掉
- merge 策略把正确结果冲掉

而是在更前面：

- 目标书正文和样本台词本身就缺少足够相似度

## 5. 库内正文与样本台词的直接对照

### 5.1 `丧尸末日，女友为等竹马拦我生路`

用户样本台词核心情节：

- 丧尸爆发后的第七天
- 最后一批救援直升机撤离
- 女友堵门等竹马

但库内这本书的首章正文开头实际是另一套剧情：

- 冰河末日
- 极寒缺粮
- 妻子与邻居
- 儿子被冻死

原始下载 txt 与 SQLite 正文是一致的，不是落库后二次写坏。

同时，这本书虽然也出现过：

- `直升机`
- `救援`

但整本书完全不出现：

- `丧尸`
- `竹马`

这说明它和用户样本不是同一套故事设定，只是都带“末世+撤离+救援”外壳。

### 5.2 `他与春风皆过客`

用户样本台词核心情节：

- 选夫宴
- 十三皇子
- 送去当质子
- 威远王府

但库内这本书的首章正文开头实际是：

- 攻略顾淮安
- 车祸捐肾
- 白月光
- 婚后第三年

原始下载 txt 与 SQLite 正文同样一致，不是落库后二次写坏。

同时，这本书整本都不出现：

- `选夫宴`
- `十三皇子`
- `威远王府`
- `质子`

这已经不是“改写力度大”的问题，而是时代背景、人物关系、剧情主线都不一致。

换句话说，它更像“同名映射到了另一版正文”或“用户样本对应的是别的原著版本”，而不是召回系统完全失效。

## 8.1 对上游导入源的进一步确认

这两本问题书都来自同一批导入源：

- 源文件：`线上自有小说.xlsx`
- batch：`batch_20260428_online_owned`
- manifest：`raw/batch_20260428_online_owned/manifest/manifest.csv`

进一步核查后可以确认：

- `11010352605` 在这份源表里只对应一个书名
- `11010284708` 在这份源表里也只对应一个书名
- 当前这两本书在该源表中都不是“同书名对应多个 `book_ext_id`”的那类重复项

这说明当前这两个问题样本，至少不是本次导入脚本把“同名多书号”压错了。

更可能的情况是：

- 上游提供给这两个 `book_ext_id` 的正文内容本身就不是用户短剧台词对应的版本
- 或者业务侧“原著书名”与实际引用的原著版本并不是同一个文本实体

## 8.3 已补齐到“源 Excel -> manifest -> 下载 -> 入库”的本地证据链

这次又继续往上游补了一层，当前已经能把这两本问题书的本地链路闭到：

- `线上自有小说.xlsx`
- `raw/batch_20260428_online_owned/manifest/manifest.csv`
- `raw/batch_20260428_online_owned/logs/download_results_*.csv`
- `raw/batch_20260428_online_owned/txt/<book_ext_id>/<chapter_ext_id>.txt`
- SQLite `chapters / chapter_contents`

并且每一层都能对上。

### 8.3.1 源 Excel 里已经直接带了这两个 `book_ext_id` 的 signed url

在 `线上自有小说.xlsx` 中，能直接找到：

- `11010284708 / 他与春风皆过客`
- `11010352605 / 丧尸末日，女友为等竹马拦我生路`

例如首章行里已经明确写着：

- `11010284708 -> .../11010284708/583693846.txt`
- `11010352605 -> .../11010352605/594063748.txt`

而且这份源表中，这两本书一共对应 `48` 行章节记录：

- `11010284708`：`22` 章
- `11010352605`：`26` 章

这和本地实际下载章节数、SQLite 中的 `chapter_count` 是一致的。

### 8.3.2 `manifest` 只是把源 Excel 的 signed url 解析展开，没有改书号或换对象

`scripts/build_manifest.py` 的行为很直接：

- 从 Excel 读取 `book_name / chapter_name / chapter_id / signed_url`
- 直接从 `signed_url` 的 path 中解析出：
  - `object_key`
  - `book_ext_id`
  - `chapter_id`
- 再写入 `manifest.csv`

也就是说，`manifest` 并不是“重新查一遍书号对应什么正文”，只是把 Excel 里那条 url 展开成结构化字段。

当前 `manifest.csv` 中，这两本书也都明确指向：

- `11010284708 -> data/cppartner/.../11010284708/583693846.txt`
- `11010352605 -> data/cppartner/.../11010352605/594063748.txt`

### 8.3.3 下载脚本只是按 signed url 原样下载，没有正文改写或重映射

`scripts/download_raw_txt.py` 的逻辑是：

- 从 `manifest.csv` 取 `signed_url`
- 直接 `GET signed_url`
- 保存到 `raw_rel_path` 对应的本地 txt 文件

脚本里没有：

- 重新按书名查对象
- 重新按 `book_ext_id` 映射别的文件
- 对正文做内容级改写

下载日志也能对上，例如：

- `583693846,11010284708,downloaded,...\\txt\\11010284708\\583693846.txt`
- `594063748,11010352605,downloaded,...\\txt\\11010352605\\594063748.txt`

说明本地确实是把 `manifest` 里的那批对象原样下载到了对应目录。

### 8.3.4 入库脚本只是落映射、同步路径和状态，没有串书逻辑

后续本地导入也看过两段脚本：

- `scripts/import_manifest_to_db_v2.py`
- `scripts/sync_downloaded_files_v2.py`

它们做的事主要是：

- 把 `manifest` 里的 `book_ext_id / chapter_ext_id / object_key / signed_url` 落到 `books / chapters / raw_manifest_rows`
- 把本地实际存在的 txt 路径、文件大小、下载状态同步回 `chapters`

这里也没有看到：

- 按书名二次匹配章节
- 用别的章节正文覆盖当前章节
- 把某本书的 txt 同步到另一本文档名下

所以从本地链路上看，当前没有证据支持“是我们下载或入库时把正文串错了”。

## 8.4 当前能下的最强结论

在现有本地证据范围内，已经可以把结论再收紧一步：

- 不是本地语义召回链路挂了
- 不是本地下载脚本把正文下错了
- 不是本地导入脚本把书号和正文串档了

更强的判断应当是：

- 问题已经出现在 `线上自有小说.xlsx` 这一层，或者更早的 signed url / OSS 对象层
- 也就是：本地拿到的“这两个 `book_ext_id` 对应正文版本”本身就不是用户台词对应的那版原著

但要注意，当前仍然**没有直接拿到更上游业务接口返回快照**，所以最后一句不能写成 100% 的绝对断言：

- 目前最稳妥的表述是：**强证据指向上游文本版本错位，且本地链路未发现串档。**

## 9. 当前可执行结论

当前不建议继续把主要时间花在：

- 盲目调大 `candidate_limit`
- 继续放宽 `merged_top_k`
- 继续调相似度阈值

因为这两条样本的主因已经更偏向数据问题，而不是召回链路问题。

更合理的后续动作是：

1. 回查这两本书在更上游源里的正文版本是否正确
2. 确认用户样本对应的“原著书名”是否其实指向另一版小说
3. 若业务上允许多版本同名书，需要补版本级主键或版本映射表，而不是只靠 `book_name`
4. 如果还要继续取证，需要上游接口返回记录、对象生产链路，或更早期的源表快照；仅靠本地现有库基本已经查到头了

## 10. 顺手修掉的一个真实缺陷

虽然这两条漏召回的主因不是它，但当前代码里确实存在一个会放大长文本误差的设计问题，已经修掉：

- 文件：`service/semantic_retrieval.py`
- 原行为：`chapter` 语义召回只使用长 query 切块后的第一段向量
- 新行为：每个 query chunk 都会独立参与 `chapter` 语义召回，再统一聚合

这个修改能减少长文本只被首段主导的问题，但不会改变上面两条样本的根因判断。
