## 2. 数据量级

按实际落盘 txt 统计：

- `self_short_novels`：约 `917.91 MB`
- `online_owned_novels`：约 `1599.88 MB`
- 两批合计：约 `2517.79 MB`

按章节量统计：

- 两批合计约 `55.6 万章`

结论：

- 对“下载、清洗、切分、建索引”来说，这个量级不算大，单机可以承接。
- 对“全量两两暴力比对”来说，这个量级已经偏大，后续必须先做切片和粗召回，不能直接全量互比。

## 3. 当前基线用途

这两批数据后续统一作为：

- 清洗脚本验证基线
- 切分脚本验证基线
- 粗召回第一版验证基线
- 样本评测的主测试集

## 4. 当前不做的事

当前阶段不基于这两批数据直接做：

- 全量向量化
- 全量语义检索
- 全量两两比对

原因：

- 先把下载、清洗、切分、粗召回链路跑通更重要
- 向量层和语义层应在 V1 粗召回跑通后再追加

## 5. 后续引用规则

后续只要提到“当前测试数据”或“测试基线”，默认指这两批：

- `self_short_novels`
- `online_owned_novels`

除非后续新增批次并明确写入新的基线说明。

## 6. 当前测试口径为何有代表性

当前测试数据不是最终生产全量数据。

最终真实场景更接近：

- 小说总量更大
- 原始全量源文件可能达到 TB 级
- 但检索侧不是吃整本全量，而是每本小说只取前 `25` 章

所以后续真正决定检索压力的，不是“原始文件总量是不是 TB”，而是：

- 参与检索的书本数
- 每本实际纳入索引的章节数
- 章节平均字数
- 去重后的 canonical 章节数
- 查询并发数

这也是为什么当前阶段选择：

- 先用现有书量跑全本正文
- 先把清洗、去重、索引、粗召回、候选现切、细比对链路跑通

这样的测试口径虽然和最终生产口径不完全相同，但仍然有代表性。

原因有三条：

### 6.1 当前是在主动把数据压力往上拉

当前两批测试数据虽然书本数还不是最终规模，但因为先吃了全本正文，所以：

- 总章节数已经达到 `55.5 万章`
- 正文总字数已经接近 `8.95 亿字`

这意味着当前测试不是“小样本功能演示”，而是在几亿字、几十万章级别上验证：

- 单机入库是否稳定
- 文本清洗是否稳定
- exact dedup 是否稳定
- 章级粗召回是否稳定
- 候选章节现切是否稳定
- 细比对链路是否能接上

换句话说，当前是在用“较少的书 + 更长的正文”提前暴露容量和性能问题。

### 6.2 最终生产口径更像“更多书，但每本更短”

后续真实生产场景中，虽然书本数会继续上升，但每本只取前 `25` 章。

这会把压力从：

- “单本正文长度”

转移成：

- “书本数更多，跨书竞争更强”

因此当前测试口径和最终生产口径的差别，不是“现在完全没参考价值”，而是：

- 当前更像“单书更长”
- 最终更像“书更多、每书更短”

两者都在增加章级索引规模，只是增长形态不同。

所以当前工作验证的是：

- 方案逻辑是否成立
- 数据结构是否合理
- 召回与细比对链路是否可落地

这些结论后续不会因为书本数上涨而失效。

### 6.3 当前验证的是路线，不是最终单机上限

当前阶段真正要验证的是：

- `schema_v2` 是否合理
- 分数据集管理是否合理
- exact dedup + canonical-only 是否合理
- 分数据集建索引、查询时统一合并是否合理
- “章级粗召回 -> 候选现切 -> 细比对” 这条路线是否合理

这些属于架构路线判断。

后续即使生产规模更大，可能需要升级的通常只是：

- 底层索引引擎
- 索引分片方式
- 部署方式
- 并发承载方式

而不是推翻当前已经验证通过的整条处理链。

## 7. 当前测试口径的结论

当前可以明确下一个判断：

- 现在先用“较少的书 + 全本正文”把数据压力做上去，是合理策略
- 这套测试口径对验证全流程是有意义的
- 后续拿到全量数据后，再按“每本前 `25` 章”的真实生产口径重跑一次去重、建索引和压测即可

也就是说：

- 当前阶段验证“路线是否走得通”
- 后续阶段验证“真实生产口径下是否需要升级底层实现”
