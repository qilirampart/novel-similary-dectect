# V2 数据库结构设计

更新时间：2026-04-29

## 1. 设计目标

`schema_v2` 解决的是一个很具体的问题：

- 当前已经不止一批小说数据
- 不同批次之间已经出现 `book_ext_id` 和 `chapter_id` 重叠
- 所以不能再用“单列外部 ID”直接当业务主表主键

这一版的目标不是做复杂架构，而是把多批次共库存储这件事做对。

## 2. 一句话设计思路

把“数据集”“导入批次”“外部 ID”“内部主键”四层彻底拆开。

简单理解：

- `dataset_key`
  - 表示“这是哪一类数据”
  - 例如：`self_short_novels`、`online_owned_novels`
- `batch_id`
  - 表示“这是哪一次导入”
  - 例如：`batch_20260428_online_owned`
- `book_ext_id / chapter_ext_id`
  - 表示上游给的外部编号
- `book_uid / chapter_uid`
  - 表示我们库内自己的稳定主键

生活类比：

- `dataset_key` 像仓库分区
- `batch_id` 像这次入库单号
- `book_ext_id / chapter_ext_id` 像供应商贴在箱子上的编号
- `book_uid / chapter_uid` 像我们自己重新编的库内货号

## 3. V1 的核心问题

当前 `schema_v1` 的问题不是字段少，而是主键边界错了：

- `books.book_ext_id` 直接做主键
- `chapters.chapter_id` 直接做主键
- `chapter_contents.chapter_id` 也跟着绑定

这在单批数据时能跑，但一旦多批数据共库，就会遇到：

- 两批数据外部 ID 重叠
- 后导入批次覆盖前导入批次
- 后续切片、索引、证据表都跟着主键混淆

## 4. V2 的设计原则

### 4.1 外部 ID 只做业务属性，不直接做主键

以后统一约定：

- `book_ext_id`
- `chapter_ext_id`

都表示“上游给的外部编号”，不再直接充当主键。

### 4.2 业务主表统一使用内部代理主键

以后统一约定：

- `book_uid`
- `chapter_uid`

作为内部稳定主键。

### 4.3 所有业务唯一性都要带上 `dataset_key`

例如：

- 同一本书的唯一性：`dataset_key + book_ext_id`
- 同一章节的唯一性：`dataset_key + chapter_ext_id`

这样即使不同数据集复用了相同外部 ID，也不会撞库。

### 4.4 `dataset_key` 和 `batch_id` 必须分开

不能把这两个概念混成一个字段。

原因：

- 同一个数据集后续可能反复导入
- 同一个 `dataset_key` 可能有很多次 `batch_id`

所以：

- `dataset_key` 是逻辑数据集
- `batch_id` 是某次导入事件

## 5. V2 主要表设计

### 5.1 `datasets`

记录逻辑数据集。

核心字段：

- `dataset_key`
- `dataset_label`
- `source_scope`
- `source_file_name`
- `source_file_sha256`

作用：

- 让 `self_short_novels` 和 `online_owned_novels` 变成显式的一等对象

### 5.2 `ingest_batches`

记录每次导入批次。

核心字段：

- `batch_id`
- `dataset_key`
- `source_file_name`
- `source_row_count`
- `manifest_path`
- `batch_status`

作用：

- 记录“某个数据集的某一次导入”

### 5.3 `raw_manifest_rows`

继续保留原始清单明细，但补上 `dataset_key`，并把 `chapter_id` 改名为 `chapter_ext_id`。

核心字段：

- `batch_id`
- `dataset_key`
- `book_ext_id`
- `book_name`
- `chapter_ext_id`
- `chapter_name`
- `chapter_order`
- `signed_url`
- `raw_rel_path`

作用：

- 保存“原始下载任务边界”
- 后续一切追查都能回到这一层

### 5.4 `books`

业务主书表，改为内部主键。

核心字段：

- `book_uid`
- `dataset_key`
- `book_ext_id`
- `book_name`

唯一性：

- `UNIQUE(dataset_key, book_ext_id)`

### 5.5 `chapters`

业务主章节表，改为内部主键。

核心字段：

- `chapter_uid`
- `dataset_key`
- `book_uid`
- `chapter_ext_id`
- `chapter_name`
- `chapter_order`
- `raw_file_path`
- `download_status`
- `content_sha256`

唯一性：

- `UNIQUE(dataset_key, chapter_ext_id)`

说明：

- 后续所有正文、切片、检索、证据表都要挂在 `chapter_uid` 上

### 5.6 `chapter_contents`

正文表，主键改成：

- `chapter_uid`

而不是旧版的：

- `chapter_id`

### 5.7 `terminal_failures`

新增终端失败表，专门记录稳定 `404` 这种源端缺失。

核心字段：

- `dataset_key`
- `chapter_ext_id`
- `book_ext_id`
- `failure_type`
- `error_message`
- `raw_rel_path`

作用：

- 不让终端缺失继续卡死下载队列
- 也不把“源端不存在”误记成“脚本没跑好”

### 5.8 `semantic_chunks`

切片表以后统一引用：

- `chapter_uid`

### 5.9 `evidence_windows`

证据滑窗表以后统一引用：

- `chapter_uid`

## 6. 和当前两批测试数据的适配关系

### `self_short_novels`

- `dataset_key=self_short_novels`
- `batch_id=batch_20260428`

### `online_owned_novels`

- `dataset_key=online_owned_novels`
- `batch_id=batch_20260428_online_owned`

这两批已经确认：

- `chapter_id` 重叠 `23`
- `book_ext_id` 重叠 `2`

所以这套 `dataset_key + ext_id` 的唯一性边界不是“保险起见”，而是当前就已经必须。

## 7. V2 对脚本的影响

### 需要改的脚本

- `scripts/import_manifest_to_db.py`
- `scripts/sync_downloaded_files.py`
- `scripts/load_raw_contents.py`

### 改动方向

#### `import_manifest_to_db.py`

需要改成：

- 先写 `datasets`
- 再写 `ingest_batches`
- 再写 `raw_manifest_rows`
- 再按 `dataset_key + book_ext_id` upsert `books`
- 再按 `dataset_key + chapter_ext_id` upsert `chapters`

#### `sync_downloaded_files.py`

不能再只靠：

- `book_ext_id + chapter_id`

而要明确：

- `dataset_key + book_ext_id + chapter_ext_id`

或者先定位 `chapter_uid` 再更新。

#### `load_raw_contents.py`

不能再直接拿：

- `chapter_id`

做主键，而要改成：

- 先查 `chapter_uid`
- 再写 `chapter_contents`

## 8. 当前阶段的落地建议

当前不建议直接在老 `novel_similarity.sqlite3` 上硬改。

更稳的方式是：

1. 新建 `schema_v2.sql`
2. 新建一份新的 V2 数据库文件
3. 先把两批测试数据重新导入 V2 库
4. 导入成功后，再把清洗、切片、召回链路迁到 V2

## 9. 本步结论

`schema_v2` 的核心不是“加更多表”，而是把主键体系理顺：

- `dataset_key` 管逻辑数据集
- `batch_id` 管导入事件
- `book_ext_id / chapter_ext_id` 管外部编号
- `book_uid / chapter_uid` 管内部主键

后续只要沿着这个边界走，新增小说批次就不会再撞库。
