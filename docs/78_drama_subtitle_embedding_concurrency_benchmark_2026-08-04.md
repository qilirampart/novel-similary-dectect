# 短剧字幕 4B 向量化并发测试记录

## 结论

本轮先测试 2 并发，确认 API 请求、Qdrant 写入和 SQLite 断点同步稳定后，再测试 4 并发。两轮均处理 160 条未同步英文字幕窗口，没有出现 API 错误、任务中断或同步数量漂移。当前脚本默认并发已调整为 4，正式全量任务仍建议先观察运行日志和服务资源，再决定是否长期保持该配置。

## 测试结果

| 配置 | 批次大小 | 测试数量 | 耗时 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 2 并发 | 8 | 160 | 17.1 秒 | 成功，SQLite 与 Qdrant 数量一致 |
| 4 并发 | 8 | 160 | 8.1 秒 | 成功，SQLite 与 Qdrant 数量一致 |
| 6 并发 | 8 | 160 | 7.6 秒 | 成功，SQLite 与 Qdrant 数量一致 |
| 8 并发 | 8 | 160 | 10.6 秒 | 成功，但吞吐下降，SQLite 与 Qdrant 数量一致 |

2 并发测试前英文窗口同步数为 380，完成后为 540，Qdrant 点数由 811 增至 971。4 并发测试后英文窗口同步数为 700，Qdrant 点数为 1131。每轮都增加了准确的 160 条，说明断点状态只在 Qdrant upsert 成功后提交，没有出现 SQLite 已标记但向量未写入的情况。

随后两轮测试继续使用新的未同步英文窗口。6 并发完成后 Qdrant 点数为 1291、SQLite 英文同步数为 860；8 并发完成后 Qdrant 点数为 1451、SQLite 英文同步数为 1020。两轮都准确增加 160 条，没有出现 429、5xx、超时或同步数量漂移。

## 实现边界

并发只作用于 embedding API 请求，最多同时保持配置数量的请求在途。Qdrant upsert、SQLite 同步状态写入和进度文件更新仍由主线程串行执行，以避免 SQLite 单写者竞争和断点状态不一致。单个请求失败时，该批次不会写入同步状态，已完成批次可以安全续跑。

`batch_size` 仍保持 8。此前测试显示单纯将批次调整到 16 未带来收益，因此没有用增大请求体替代并发。未识别语言的窗口默认不进入语义向量化，避免后续查询无法进行可靠的同语言路由。

## 后续建议

6 并发虽然比 4 并发略快，但收益有限；8 并发已经出现吞吐下降。因此正式配置保持 4 并发，必要时可人工使用 6 并发做短时吞吐测试，不建议使用 8 并发。正式全量前仍需观察 4 并发下的 429、5xx、超时、磁盘占用和 Qdrant 索引构建开销；若出现限流，优先退回 2 并发，不改变词法召回和语义准确性策略。
