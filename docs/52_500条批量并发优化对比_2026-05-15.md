# 500 条批量并发优化对比

更新时间：2026-05-15

## 一、本次改动范围

本次没有改召回算法，也没有改 `rewrite` 的排序逻辑，只改了批量任务执行器的调度方式。

改动目标是：

- 保持单条比对结果口径不变
- 保持语义链路可用时的召回能力不变
- 在同一批任务内部引入保守并发
- 先只开 `2` 槽，不做激进并发

本次改动后：

- `execute_claimed_task()` 支持按 `item_parallelism` 并发执行
- API 自动 worker 默认读取 `NOVEL_SIMILARITY_TASK_ITEM_PARALLELISM`
- 当前默认值已切到 `2`

## 二、对比对象

### 基线版本

- 任务 ID：`f7437cde-a65f-478e-b7a7-2d36b412ab2e`
- 执行模型：单 worker + 单任务内串行
- 测试文档：`docs/51_500条批量压测基准_2026-05-15.md`

### 并发优化版本

- 任务 ID：`d3470b5d-b523-4989-a316-1abede8b3082`
- 执行模型：单 worker + 单任务内 `2` 槽并发
- 本地状态消息可见：`Processing item x/500. In flight 2.`

两轮测试都满足：

- 输入文件相同
- 参数相同
- 模式相同，均为 `rewrite`
- 本地 `Qdrant` 正常可用
- `500/500` 都是 `semantic_ready`

## 三、结果总览

### 3.1 墙钟耗时

- 基线版本：`1467s`
- 并发版本：`987s`
- 节省时间：`480s`
- 提速比：`1.486x`
- 墙钟耗时下降：`32.72%`

折算后：

- 基线版本：约 `24分27秒`
- 并发版本：约 `16分27秒`

### 3.2 墙钟口径下的单条平均

- 基线版本：`2.934s/条`
- 并发版本：`1.974s/条`

这个口径更适合前台 ETA 和“用户实际要等多久”的判断。

### 3.3 数据库记录的单条 `duration_seconds`

- 基线版本平均：`2.882s`
- 并发版本平均：`3.638s`

这里看起来并发版反而更高，但这并不代表它更慢。原因是：

- `duration_seconds` 记录的是“单条任务从进入 running 到完成”的耗时
- 并发后两个任务槽会共享 CPU、Qdrant 查询和 embedding 请求带宽
- 所以单条内部 duration 可能略有上升
- 但因为两条同时跑，整体墙钟时间仍然明显下降

所以评估批量体验时，应优先看：

- 总墙钟耗时
- 每条墙钟均摊时间

而不是只看单条 `duration_seconds`

## 五、并发效果判断

本次 `2` 槽方案可以视为有效，理由有三点。

第一，召回链路没有退化。本次并发版仍然是 `500/500 semantic_ready`，说明不是靠关闭语义或回退词法来换速度。

第二，总耗时下降是稳定的，不是误差级波动。从 `24分27秒` 到 `16分27秒`，节省了整整 `8` 分钟，已经足够构成版本级收益。

第三，系统没有出现失败数抬升、导出缺失或任务状态异常。任务、导出和结果落库都完整。

## 六、当前结论

当前可以先把这个版本视为“安全可用的第一档提速”。

也就是说，现阶段可以先接受：

- 单任务内部并发：`2`
- 默认执行模型：保守并发，而不是串行

这个版本已经比之前更适合处理 `500` 条级别的批量任务。

## 七、下一步建议

下一步不要立刻继续把并发度抬到 `4` 或更高，建议按下面顺序走。

1. 先观察这版在真实前台批量使用中的稳定性，确认不会引发新的波动或错误。
2. 如果后续 `500` 条以上任务仍是高频场景，再单独做 `4` 槽实验。
3. `4` 槽实验必须继续坚持两个前提：
   - 不能牺牲召回准确率
   - 不能把本地语义资源打穿，导致回退增多
