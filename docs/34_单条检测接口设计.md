# 单条检测接口设计

## 1. 目标

为 Web 可视化系统 V1 提供一个稳定的“单条检测”接口。

这个接口的目标不是覆盖全部离线能力，而是先承接最核心的在线使用场景：

- 输入一条短剧文案
- 选择 `reuse` 或 `rewrite`
- 返回候选小说、章节、证据片段和结果标签

## 2. 接口定义

- 方法：`POST`
- 路径：`/api/v1/compare/single`

## 3. 请求体

### 3.1 必填字段

- `query_text`
  - 类型：`string`
  - 含义：待检测的短剧文案或字幕文本

- `detection_mode`
  - 类型：`string`
  - 可选值：`reuse` / `rewrite`

### 3.2 可选字段

- `top_k`
  - 类型：`integer`
  - 含义：前端最终展示的 top 结果数量

- `compare_top_k`
  - 类型：`integer`
  - 含义：进入细比对的候选章节数

- `merged_top_k`
  - 类型：`integer`
  - 含义：词面召回和语义召回合并后的候选规模

### 3.3 第一版暂不对前端开放的参数

下面这些仍然由后端统一控制，第一版不暴露给普通页面：

- `window_size`
- `step_size`
- `ngram_size`
- `max_query_ngrams`
- `weight_coarse`
- `seed_term_count`
- 语义模型和 Qdrant 连接参数

原因：

- 这些参数是系统级参数
- 如果过早放给前端，会让页面复杂度和误操作风险明显升高

## 4. 请求示例

```json
{
  "query_text": "皇帝翻遍后宫，只为找出酒后爬龙床的宫女……",
  "detection_mode": "rewrite"
}
```

## 5. 响应结构

### 5.1 顶层字段

- `request_id`
  - 本次请求唯一 ID

- `query_text`
  - 原始输入文本

- `detection_mode`
  - 当前检测模式

- `detection_mode_label`
  - 模式中文名

- `detection_mode_description`
  - 模式说明

- `params`
  - 本次实际生效参数

- `capabilities`
  - 当前能力开关状态

- `coarse`
  - 粗召回结果

- `reuse_detection`
  - 复用检测结果

- `rewrite_detection`
  - 洗稿检测结果

- `fine`
  - 细比对结果

## 6. 关键响应字段说明

### 6.1 `capabilities`

用于前端判断当前结果是：

- 只走了词面链路
- 还是同时走了语义链路

关键字段：

- `reuse_detection_enabled`
- `rewrite_detection_enabled`
- `semantic_recall_enabled`

### 6.2 `coarse`

用于展示粗召回阶段发生了什么。

关键字段：

- `target_count`
  - 当前全库涉及的索引数量

- `index_summaries`
  - 每个索引各自拉回了多少候选

- `semantic`
  - 当前语义召回状态

- `merged_results`
  - 融合后的候选列表

### 6.3 `reuse_detection`

这是前端默认应该展示的“最硬结果”。

关键字段：

- `result_count`
- `strong_evidence_count_in_pool`
- `results`
- `strong_evidence_results`

### 6.4 `rewrite_detection`

这是 `rewrite` 模式下的附加视图。

关键字段：

- `status`
  - `semantic_ready / fallback_lexical_only / disabled`

- `message`
  - 当前语义状态说明

- `semantic_candidate_count`
  - 语义候选规模

- `results`
  - 可疑结果列表

### 6.5 `fine`

这是页面详情区最重要的数据来源。

关键字段：

- `candidate_count`
  - 进入细比对的候选数量

- `sliced_candidate_count`
  - 实际切窗后的候选数量

- `compared_candidate_count`
  - 实际参与细比对的数量

- `results`
  - Top 结果

- `review_rows`
  - 扁平化导出结构

## 7. `fine.results[]` 单项结构

每个结果项建议前端重点展示这些字段：

- `book_name`
- `chapter_name`
- `fine_score`
- `review_label`
- `confidence_label`
- `coarse_rank`
- `coarse_final_score`
- `best_match`

其中 `best_match` 里前端最有用的字段是：

- `candidate_window_order`
- `candidate_start_offset`
- `candidate_end_offset`
- `exact_substring_hit`
- `longest_match_len`
- `longest_match_ratio`
- `ngram_recall`
- `ngram_precision`
- `jaccard`
- `sequence_ratio`
- `matched_substring`
- `query_text_preview`
- `candidate_text_preview`
- `candidate_text`

## 8. 第一版前端展示建议

### 8.1 列表卡片

列表页先显示：

- 书名
- 章节
- `fine_score`
- `review_label`
- `coarse_rank`
- `semantic status`

### 8.2 详情抽屉

展开后显示：

- 输入文案片段
- 命中文本片段
- 匹配子串
- 证据窗 offset
- 相似度指标

## 9. 状态码约定

### 200

请求成功，正常返回结果。

### 400

请求参数不合法，例如：

- `query_text` 为空
- `detection_mode` 不支持

### 500

后端内部异常。

### 503

依赖不可用，例如：

- 语义节点不可达

说明：

第一版即使语义侧不可用，也不一定直接返回 503，因为 `rewrite` 模式允许优雅降级成 `fallback_lexical_only`。

## 10. 第一版实现原则

这个接口第一版应坚持 3 点：

- 不通过 subprocess 调脚本
- 直接复用 Python service 层能力
- 保持返回结构尽量贴近当前 `run_global_compare_v1.py` 的 JSON 结果

这样做的好处是：

- 现有测试可以最大程度复用
- CLI 和 API 结果结构更一致
- 后面前端联调最省力

## 11. 当前定版结论

当前可以正式定下的 V1 单条接口结论是：

- 先做一个稳定的 `POST /api/v1/compare/single`
- 页面第一版默认围绕它开发
- 批量任务接口后续单独设计，不和单条接口混用
