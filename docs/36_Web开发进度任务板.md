# Web 开发进度任务板

更新时间：2026-05-09

## 1. 任务状态定义

- `已完成`：功能已落地，并完成基础联调或 smoke 验证
- `进行中`：已经进入实现阶段，当前版本可见但还未收口
- `待开始`：范围和目标已明确，尚未进入实现
- `待验证`：代码或方案已具备，但还缺浏览器实测、回归测试或真实数据验证
- `有风险`：当前能用，但存在明显性能、稳定性或体验风险

## 2. 当前整体判断

当前项目已经完成了“从 0 到可演示”的阶段，但还没有完成“从可演示到可稳定使用”的阶段。

### 2.1 已经具备的能力

- 后端主链路已经打通：
  - 单条比对可用
  - 批量任务创建、执行、取消、重试可用
  - 结果列表、详情、复核、导出可用
  - 系统状态接口可用
  - API 内嵌自动 worker 可消费本地任务
- 前端主工作流已经打通：
  - 总览看板可查看全局摘要
  - 单条比对可输入文本并查看候选、证据、指标
  - 批量任务可上传文件并跟踪任务
  - 结果复核可选中结果并提交复核结论
  - 任务记录可查看历史任务与导出状态
  - 系统状态页可查看核心运行信息

### 2.2 当前最明显的问题

- 页面之间的首屏加载策略不统一，仍有个别页面会出现“列表和详情一起卡住”的体验
- 一些模块还只是占位页，没有进入真实功能阶段
- 单条比对和批量任务的候选展示口径还未完全统一
- 大列表页面已经能用，但分页、筛选、密度、导出联动仍偏初版
- 系统状态接口偏慢，容易影响看板和状态页的响应体验
- 测试覆盖以 smoke 为主，回归保护还不够
- 批量任务结果明细缺少单条耗时展示，当前只能看到结果，难以快速判断慢样本
- 复核页左侧结果列表在选中或保存后存在定位不稳定问题，会跳回第一页或第一行附近
- 复核页主空间仍被摘要卡和指标区占用，核心“文本对比”区域不够大，不利于高频复核操作

### 2.3 当前结论

- 后端基础主流程：`已完成`
- 前端核心工作台：`进行中`
- 前后端口径统一：`进行中`
- 性能与稳态：`有风险`
- 占位模块补齐：`待开始`

## 4. 当前可优化点分析

## 4.1 前端体验层

### 现状

- 主要工作流已可用，但页面体验收口程度不一致
- 看板、批量任务、复核页已经开始按“列表先出、详情后补”的方向优化
- 任务记录页仍沿用较早的同步加载方式
- 多个页面还可以继续压缩空白、统一空态、统一加载态和表格交互

### 主要问题

- `任务记录` 页仍会先拉列表再拉详情，交互感受和其他页面不一致
- 列表页普遍还缺真正的分页控件与翻页状态管理
- 多页面按钮、空态、加载态的文案和位置还不完全统一
- 当前部分参数和技术字段直接暴露给用户，可继续做中文说明和分组

### 优化方向

- 统一所有列表页的首屏策略：列表先出，详情异步补齐
- 统一表格行点击选中模式，减少额外按钮
- 统一固定高度内容区，降低布局跳动
- 统一中文文案、空态文案、错误提示样式

## 4.2 功能完整度层

### 现状

- 主要工作流页面已接真实接口
- `规则配置`、`检索库管理`、`日志中心` 仍是占位页

### 主要问题

- 当前控制台还不能完成规则配置、库管理、日志诊断这三个典型后台动作
- 用户从导航进入这些页面时，会感知到“系统看起来完整，但功能未接通”

### 优化方向

- 先把占位页从“纯占位”升级为“最小可用页”
- 规则页优先承接检测口径和阈值配置
- 检索库页优先承接基础库信息、索引状态和数据量展示
- 日志页优先承接最近任务失败、错误摘要、worker 异常信息

## 4.3 前后端口径一致性层

### 现状

- 单条比对已经支持 `candidate_display_score_threshold`
- 批量任务创建链路、任务落表、worker 执行链路已经支持同一候选展示阈值
- 批量任务页可以查看当前任务实际生效的候选展示阈值

### 主要问题

- 当前主要风险已从“阈值没透传”转为“更多统计摘要和展示口径仍可继续统一”
- 后续如果继续新增筛选、分页和统计卡片，仍要避免单条页和批量页各自定义口径

### 优化方向

- 继续统一列表页统计字段含义
- 继续统一结果筛选、分页和导出提示语义

## 4.4 性能与稳态层

### 现状

- `tasks`、`results` 接口响应相对较快
- `system/status` 接口明显偏慢
- 自动 worker 当前采用线程轮询模型

### 主要问题

- 看板和系统状态页容易被慢接口拖慢
- 任务规模变大后，列表查询、详情拉取、导出文件生成、worker 轮询策略都可能成为瓶颈
- 失败任务的错误诊断信息还可以更结构化

### 优化方向

- 拆分或缓存 `system/status` 中耗时统计项
- 评估列表接口字段裁剪与更细粒度分页
- 为任务失败增加结构化错误字段和最近异常摘要
- 为 worker 补充更清晰的心跳、重试、取消与回压观测点

## 4.5 测试与回归保护层

### 现状

- 当前已有若干 smoke 测试覆盖主链路
- 但页面级交互和边界回归仍偏薄

### 主要问题

- 页面首屏体验优化、参数透传、导出状态、分页筛选等改动，缺少自动回归保护
- 后续继续迭代 UI 和任务链路时，容易出现“修一处坏一处”

### 优化方向

- 补前端页面级 smoke
- 补参数透传回归测试
- 补分页、筛选、导出、失败、取消、重试链路测试

## 6. 建议开发顺序

1. 先做 `复核页选中态稳定化`
   - 原因：这是当前最直接打断复核效率的问题，用户每次切项都可能被列表跳转打断，必须优先收口

2. 再做 `批量任务结果表补充单条耗时展示`
   - 原因：这是低成本高收益项，后端字段已具备，补上后能立刻提升任务结果可观测性

3. 然后做 `复核页信息架构重构 + 版面压缩`
   - 原因：当前复核页最大问题不是功能缺失，而是主区域给错了内容，应该把空间重新让给文本对比

4. 最后做 `复核页文本对比增强`
   - 原因：在布局和交互稳定后，再做高亮、并排和证据视窗这类深层体验优化，返工最少
